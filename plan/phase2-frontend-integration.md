# 2차 작업 계획 — 화면·통합

**2026-11-12 `D-20` 이 썼다.** [phase2.md §5.3](phase2.md)(화면에 미치는 것)과 §5.4(동시성과 측정)를 화면 항목(`F-07` 부터)과 통합 항목(`I-06` 부터)으로 쪼개고, 2차 전체(B·AU·M·F·I)의 순서를 한 표로 묶는다(§1). **board 항목(`B-14` 부터)은 [phase2-board.md](phase2-board.md)에, auth·member 항목(`AU-12`·`M-14` 부터)은 [phase2-auth-member.md](phase2-auth-member.md)에 있다** — 이 문서의 입력은 두 문서의 「넘기는 것」 절(board §4.1·§4.2, auth·member §5.1·§5.2)이다. 설계의 정본은 그 절들과 §5.3·§5.4 가 가리키는 곳이고, 완료 기준에 보이는 값은 확인할 자리를 짚으려는 것이다 — 정본과 어긋나면 정본이 이긴다. **화면 고유의 결정은 `sp-frontend` 의 `CLAUDE.md` 가 갖는다**([phase2.md §7](phase2.md)) — 아래 항목이 내리는 결정도 거기에 적는다. 항목 ID 는 `F-06`·`I-05` 다음 번호이고 재사용하지 않는다([README.md](README.md)의 항목 ID 규칙). **상태는 적지 않는다** — `F` 는 `yuno110/sp-frontend`, `I` 는 `yuno110/sp-board` 의 `docs/checklist.md` 가 갖는다([README.md](README.md)의 상태의 위치).

## 1. 2차 전체의 단계와 병렬

### 1.1 단계

| 단계 | 항목 | 성격 | 함께 도는 것 |
| --- | --- | --- | --- |
| **기반** | B-14~B-16, AU-12~AU-15, M-14 | 스키마·엔티티·에러 코드·예외 매핑·경로 선언·설정을 먼저 끝낸다(이유는 각 계획의 §1.1) | 세 저장소가 서로 기다리지 않는다. 화면의 F-07 |
| **결함 수정** | B-17, B-18 | 1차 board 코드의 자리를 고친다 — 그 1차 항목의 완료 기준과 먼저 대조한다([phase2-board.md §1.1](phase2-board.md)) | B-17 은 의존이 없지만 B-14 와 `Comment` 를 함께 고쳐 같이 돌리지 않는다([phase2-board.md §1.2](phase2-board.md)). B-18 은 B-14 뒤다 |
| **기능** | B-19~B-24, AU-16~AU-21, M-15·M-16 | 기반 산출물을 읽고 자기 기능을 만든다 | 저장소끼리 함께 돈다 — AU-16 은 F-08 과 한 번에 커밋된다(아래 문단, §1.4). 저장소 안은 각 계획의 §1.2 |
| **화면** | F-07~F-16 | 서버의 기능 항목을 따라간다. **기반·기능 구분을 쓰지 않는다** — 한 워커가 의존 열을 따라 한다([phase2.md §7.2](phase2.md)의 이유와 같다) | 서버 항목과 함께 돈다. F 끼리는 순차다(§1.2) |
| **통합** | I-06~I-10 | 2차 서버 항목이 모두 `done` 인 뒤 세 서비스를 함께 띄워 잰다 | F 와 함께 돌 수 있지만 같은 서비스 인스턴스에 동시에 걸지 않는다. I 끼리는 순차다(§1.3) |

**단계는 성격이지 시각이 아니다.** 저장소마다 워커가 따로 돌므로 board 의 기능 단계와 auth 의 기반 단계가 함께 돌 수 있고, 화면 항목은 서버 의존이 끝나는 대로 시작한다. 서버 항목 사이의 의존과 병렬은 각 계획의 §1.2 가 갖는다.

**AU-16 과 F-08 이 저장소를 잇는다.** 두 항목은 오케스트레이터가 한 번에 커밋하므로(§1.4) AU-16 은 리뷰 APPROVED 를 받아도 F-08 이 APPROVED 를 받을 때까지 `done` 이 아니다. 그동안 auth 의 다른 항목은 멈추고 — AU-16 의 커밋 전 코드가 auth 의 작업 트리에 있다 — I-06 은 이 경로로 F-07·F-08 을 기다린다(§1.3). 그 코드로 띄운 auth 에서는 실제 서비스 e2e 가 가입에서 `AU006` 을 받으므로, AU-16 은 F-07 이 `done` 이고 진행 중인 F 항목이 없을 때 배정하고 그 사이 F 는 F-08 만 한다(§1.4).

```
기반       B-14 B-15 B-16     AU-12 ~ AU-15     M-14
결함 수정  B-17 B-18
기능       B-19 ~ B-24        AU-16 ~ AU-21     M-15 M-16
화면       F-07                    (서버를 기다리지 않는다)
           AU-16 == F-08           (한 번에 커밋 — §1.4)
           AU-17 -> F-09
           AU-18 AU-19 M-15 -> F-10
           AU-20 M-16 -> F-11
           B-19 -> F-12            B-19 B-20 B-21 -> F-13
           B-22 -> F-14            B-23 B-24 -> F-15
           F-08 ~ F-15 -> F-16
통합       B·AU·M 모두 done -> I-06 -> I-07 ~ I-10 (순차)
```

### 1.2 화면 항목의 의존

**F 끼리는 순차다.** 여러 항목이 같은 화면 파일(예: 라우터, `src/lib/api/client.ts`, 글 상세·작성 화면)을 고치므로 한 워커가 의존 열을 따라 한다([phase2.md §7.2](phase2.md)). 그래서 「같은 파일」 열을 두지 않는다. **서버 의존이 끝나지 않은 항목은 건너뛰고 의존이 끝난 다음 항목을 고른다**([README.md](README.md)의 작업 시작 규칙) — ID 순서는 서버 항목이 대략 그렇게 끝난다고 보고 붙였을 뿐이다. 예외는 AU-16 의 코드가 auth 작업 트리에 있는 동안이다 — 그때는 F-08 만 한다(§1.4).

| 항목 | 서버 의존 | 화면 의존 | 맞물림 |
| --- | --- | --- | --- |
| F-07 | 없음 | 없음 | 정본 §8 의 새 코드는 2026-11-11 `D-18`·`D-19` 가 더했다 |
| F-08 | AU-16 — `done` 이 아니라 리뷰 APPROVED 를 받은 커밋 전 코드(§1.4) | F-07 | **오케스트레이터가 AU-16 과 한 번에 커밋한다**(§1.4) |
| F-09 | AU-17 | F-08 | |
| F-10 | AU-18, AU-19, M-15 | F-08, F-09 | `AU006`·`AU005` 의 복구 링크가 F-08·F-09 의 화면으로 간다 |
| F-11 | AU-20, M-16 | 없음 | 둘 다 있어야 합친다([phase2-auth-member.md §1.3](phase2-auth-member.md)) |
| F-12 | B-19 | F-07 | |
| F-13 | B-19, B-20, B-21 | F-12 | B-21 이 실제 서비스 e2e 의 관측 하나를 무르게 한다(§1.4) |
| F-14 | B-22 | F-07 | |
| F-15 | B-23, B-24 | F-07, F-12 | 글 작성 폼을 F-12 다음에 고친다 |
| F-16 | F-08~F-15 의 서버 의존 | F-08~F-15 | 마지막이다 — 앞 항목이 바꾼 흐름을 잠근다 |

**F 와 서버 항목은 저장소가 달라 함께 돈다.** 서버 항목이 화면 항목의 커밋을 기다리는 자리는 §1.4 가 적는다(예: AU-16).

### 1.3 통합 항목의 의존과 실행 조건

**I 는 순차다**([integration.md](integration.md)의 머리 — 세 서비스가 모두 떠 있어야 한다). 측정이 DB·로그·제한기 카운터를 함께 쓰므로 I 끼리도 동시에 돌리지 않는다.

| 항목 | 의존 | 재는 것을 만든 항목 |
| --- | --- | --- |
| I-06 | 2차 B·AU·M 항목 모두 | 전부 — 기동과 흐름 |
| I-07 | I-06 | B-17, B-20~B-24 |
| I-08 | I-06 | AU-12, AU-16~AU-19 |
| I-09 | I-06 | B-15, B-16, B-21, B-23, AU-14~AU-17, AU-19, M-15 |
| I-10 | I-06 | B-15, AU-13, AU-19, AU-20, M-14~M-16 |

- **I 는 F 를 의존으로 두지 않는다** — 재는 것이 서버의 성질이다. 브라우저로 재는 줄(I-10)도 수단을 그 항목이 고른다. 그래도 I-06 은 AU-16 을 거쳐 F-07·F-08 을 기다린다 — AU-16 은 F-08 과 한 번에 커밋된다(§1.1·§1.4). **다만 같은 서비스 인스턴스·DB 에 F 의 실제 서비스 e2e 와 I 의 측정을 동시에 돌리지 않는다** — e2e 의 요청이 집계·로그 수준·제한기 카운터의 측정에 섞인다
- **측정이 정본의 기대와 다르면 코드를 고치지 않고 보고한다.** 고치는 항목은 계획을 먼저 개정해 세운다([README.md](README.md)의 항목 ID 규칙) — 1차의 B-10 이 그렇게 생겼다([phase1.md §7](phase1.md)). 정본이 「측정이 뒤집으면 바꾼다」 고 적은 자리(예: 조회수 판정의 순서 — [phase2-board.md §4.1](phase2-board.md))도 바꾸는 것은 측정 뒤의 항목이다
- **측정은 코드·스키마·seed 를 바꾸지 않는다**([integration.md](integration.md) I-04 의 블록인용). 1차 I-04 와 달리 측정에만 쓰는 설정의 덮음(예: 한도에 닿을 수 있는 요청 수 제한)은 허용한다 — 그 실행의 덮음이고, 커밋하지 않고 보고에 적는다
- **정본이 기대를 정하지 않은 줄은 관측값을 적는다** — 예: `account.email` 의 콜레이션이 같다고 보는 표기(I-08). 그 값을 통과·실패로 적지 않는다

### 1.4 저장소 밖과 맞물리는 때

- **AU-16 과 F-08 은 오케스트레이터가 한 번에 커밋한다.** AU-16 이 커밋되면 계정을 만든 직후의 로그인이 403 `AU006` 이다. 지금 화면의 가입(계정 → 바로 로그인 → 프로필, `F-04`)과 실제 서비스 e2e 의 모든 흐름이 그 응답을 받는다 — 흐름마다 가입으로 시작한다(sp-frontend `CLAUDE.md` 「실제 서비스와의 e2e」). 둘 중 하나만 커밋된 상태를 두지 않는다. **그래서 F-08 의 의존은 AU-16 의 `done` 이 아니라 리뷰 APPROVED 를 받은 커밋 전 코드다** — [../process/dev-workflow.md §3.1](../process/dev-workflow.md)의 예외다. F-08 은 그 코드로 띄운 auth 에 대해 확인하고, F-08 이 APPROVED 를 받으면 오케스트레이터가 두 항목을 한 번에 커밋한다([phase2-auth-member.md §1.3](phase2-auth-member.md)). AU-16 의 APPROVED 는 상태 원본에 드러나지 않는다 — `review` 는 고치는 중도 뜻한다. F-08 은 오케스트레이터가 그 판정을 확인하고 배정한다. AU-16 의 코드가 auth 작업 트리에 있는 동안(구현부터 두 항목의 커밋까지) 그 auth 로 돈 실제 서비스 e2e 는 가입에서 `AU006` 을 받는다. 그래서 오케스트레이터는 F-07 이 `done` 이고 진행 중인 F 항목이 없을 때 AU-16 을 배정하고, 그 사이 F 는 F-08 만 한다.
- **서버 항목이 로컬 기동 조건을 바꾼다.** AU-14 뒤 auth 의 `local` 기동에 메일 설정이, AU-19·M-15 뒤 한도를 덮는 줄이, B-16 뒤 board 의 `ATTACHMENT_STORAGE_ROOT`·`VIEW_COUNT_HMAC_SECRET` 이 있어야 한다. 실제 서비스 e2e 는 서비스를 띄우지 않으므로(같은 절) 그 값은 각 서비스의 로컬 설정에 있어야 한다 — 값과 옮길 줄은 그 서비스의 `application-local.yml.example`·`README.md` 와 그 항목의 완료 보고가 갖는다([phase2-auth-member.md §1.3](phase2-auth-member.md), [phase2-board.md](phase2-board.md) B-16). 그 서버 항목이 병합된 뒤에 도는 F 항목은 그 설정으로 띄운다. 화면 저장소의 `README.md` 는 F-08(Mailpit)과 F-16(나머지)이 고친다
- **B-21 이 병합되면 실제 서비스 e2e 의 관측 하나가 힘을 잃는다 — 빨개지지는 않는다.** `e2e/live/flows.spec.ts` 의 `detailDrawn` 은 「상세 조회는 조회수를 올린다」 에 기대어 다시 받은 응답이 그려졌는지 본다(2026-11-12 코드 읽기, 그 함수의 주석). B-21 뒤 같은 조회자의 재조회는 24시간 안이면 조회수를 올리지 않으므로([../requirements/board.md §9](../requirements/board.md)) 받아 둔 것과 다시 받은 것이 같은 값이 되고, 그 단언은 받아 둔 것으로도 통과한다. F-13 이 고친다 — 그 사이에 돈 실제 서비스 e2e 에서 그 단언의 통과를 근거로 삼지 않는다
- **무인증 경로에서 필터가 끊는 토큰은 401 로 본다** — AU-13·M-14 가 묶는다(근거는 프레임워크 동작의 코드 읽기, [../requirements/board.md §9.1](../requirements/board.md)). 화면이 그 경로에 Access Token 을 싣는지 F-08 이 확인한다([phase2-auth-member.md §5.2](phase2-auth-member.md)). 싣는 동작은 정본이 정하지 않았다(§5)

## 2. 화면 항목의 공통 기준

F 항목마다 되풀이하지 않는다. **규칙의 정본은 sp-frontend `CLAUDE.md` 다** — 여기는 2차 항목에서 걸리는 자리를 가리키기만 하고, 둘이 어긋나면 그쪽을 따른다.

- **순서** — `CLAUDE.md` 「작업 규칙」 의 순서다(구현·테스트에서 `pnpm test:e2e:live` 까지, 리뷰를 통과하기 전에 커밋하지 않는다). `pnpm test:e2e:live` 앞에 세 서비스를 그때 병합된 서버 항목의 기동 조건으로 `local` 로 띄운다 — 테스트는 띄우지 않는다(§1.4). AU-16 의 코드가 auth 작업 트리에 있는 동안은 F-08 만 그 auth 로 돈다(§1.4)
- **오류 문장** — 사전의 기본 문장은 F-07 이 둔다. 엔드포인트마다의 뜻(`describeError` 의 `meanings`)과 복구 링크(`Recovery`)는 그 화면을 만드는 항목이 붙인다(「화면 문구와 오류 표시」)
- **문구 검사** — 새 문구가 보이는 상태를 `src/pages/userCopy.test.tsx` 에 더한다. 그 테스트에 없는 상태의 문구는 검사되지 않는다(같은 절)
- **라우트와 상태** — 라우트를 더하면 `e2e/routes.ts`·`e2e/screens.spec.ts` 의 상태·스텁(`e2e/api.ts`)을 함께 고친다(「접근성과 반응형」). 스텁의 경로와 응답 모양은 [../api-contract.md](../api-contract.md)에서 온다
- **비밀번호를 싣는 화면** — 그 요청의 실패를 쥐는 자리는 본문을 비운 사본을 쥐고, `src/pages/signupWithdrawal.test.tsx` 의 검사에 그 화면을 더한다(「가입과 탈퇴」). 예: 재설정(F-09)
- **인가** — 버튼 숨김은 편의이고 판정은 서버다(「경계」). 숨긴 동작의 거부(예: `P003`·`A004`·`P002`)도 화면에 보인다
- **경로 접두어** — 새 접두어는 런타임 배정(`src/lib/api/services.ts`)과 dev 프록시(`vite.config.ts`)를 함께 고치고 CSP(`csp.ts`)도 본다(「서비스 주소와 CORS」, 「경계」의 CSP 줄). 예: `/api/v1/attachments`(F-15)
- **반증** — 전부 통과한 테스트는 변이를 넣어 실패하는지 먼저 본다(「작업 규칙」, [../process/review-policy.md §4.1](../process/review-policy.md)). 「그런 것이 없다」 를 단언하는 검사는 변경 전 화면에서 잡히는 것을 보인다([phase2.md §7.2](phase2.md)의 「범위는 성질로 정한다」)
- **마이그레이션** — F·I 항목에는 없다. 화면은 DB 를 갖지 않고(sp-frontend `CLAUDE.md` 머리), 통합 항목은 코드·스키마를 바꾸지 않는다(§1.3)

- [ ] 업로더·지우기는 작성자에게만 그린다 — 판정은 서버의 403 `P002` 다(§2). 지운 첨부는 갤러리에서 사라진다

| | |

**H2 는 MySQL 의 락과 격리 수준을 재현하지 않는다**([phase2.md §5.4](phase2.md)). B 항목의 테스트가 H2 에서 강제로 끼워 넣은 경합을 여기서는 실 MySQL 에 동시 요청으로 건다. **결함과 한계를 가른다** — 집계가 근거 행과 어긋나는 것(소실 갱신·중복 증감)과 상한을 넘는 것은 결함이고, 같은 행의 교착은 1차처럼 한계로 둔다(§5.4, [../nfr.md §1](../nfr.md)). 다만 판정 순서가 만드는 교착은 정본이 측정 대상으로 남겼다 — 예: 조회수 판정의 순서([../requirements/board.md §9.3](../requirements/board.md)), B-17 이 바꾼 댓글 삭제의 순서.

**완료 기준**
- [ ] **작업 시점에 [phase2-board.md §4.1](phase2-board.md)의 실 MySQL 줄과 아래 검증표를 대조한다** — 그 표에 있고 여기 없는 줄은 더해 잰다. 표가 바뀌었으면 그 표를 따른다
- [ ] 줄마다 방법(동시 요청의 수와 반복 수)과 결과를 보고에 적는다 — 한 번의 통과로 경합이 없다고 적지 않는다
- [ ] **집계가 근거 행과 같다** — 예: `comment_count` 대 활성 댓글, `like_count` 대 `post_like` 행, `attachment_count` 대 활성 첨부. 상한을 넘지 않는다
- [ ] 교착이 나면 횟수와 그때의 응답·집계를 적는다
- [ ] **상세 응답의 `viewCount` 가 판정의 커밋을 보는가를 MySQL 의 반복 읽기에서 잰다** — B-21 이 잰 H2 의 격리 수준과 나란히 적는다
- [ ] 경합의 UNIQUE 충돌이 남기는 로그 수준을 `GlobalExceptionHandler` 가 남긴 줄과 그 밖(예: Hibernate 의 `SqlExceptionHelper`)으로 갈라 센다 — 전체 로그로 세면 틀린다([integration.md](integration.md) I-04 의 로그 수준 줄). ERROR 가 있으면 [../conventions.md §6.1](../conventions.md)과 어긋나는지 보고한다
- [ ] 결과가 정본의 기대와 다르면 코드를 고치지 않고 보고한다(§1.3)

**검증** — 기대는 정본의 것이다

| 케이스 | 기대 |
| --- | --- |
| 같은 댓글의 동시 삭제 | 성공 1, 나머지 404 `CM001`, `comment_count` 는 한 번만 준다 |

- [ ] `account.email` 의 콜레이션이 대소문자 말고 같다고 보는 표기를 관측해 적는다(예: 악센트 변형) — 이메일 키 제한은 그것을 다른 키로 센다([../security.md §10.1](../security.md)). 정본이 통과·실패를 정하지 않은 줄이다(§1.3)
- [ ] 비ASCII 표기(예: U+0130 `İ`)가 계정 조회와 같은 키로 합쳐지는지 관측해 적는다 — 키는 ASCII 대문자만 소문자로 바꾼다([../requirements/member.md §12.1](../requirements/member.md))
- [ ] 100자를 넘는 이메일 입력이 계정에 닿지 않는다(예: 끝 공백을 붙인 이메일)
- [ ] 결과가 정본의 기대와 다르면 코드를 고치지 않고 보고한다(§1.3)

**검증**

| 케이스 | 기대 |
| --- | --- |
| 같은 이메일, 시도 수가 한도 미만인 동시 첫 실패 | `failed_count` + WARN 수 = 시도 수, 전부 `AU003`. WARN 은 세지 못한 실패의 줄이다 |
| 같은 이메일, 시도 수 − WARN 수가 한도 이상인 동시 실패 | 잠금이 한 번 걸리고 `failed_count` 는 0 이다 — 잠그는 실패가 0 으로 되돌리고, 잠긴 뒤의 실패는 세지 않고 `AU005` 다([../domain-model.md §2.5](../domain-model.md)의 갱신 문장). `AU003` 은 (한도 − 1) + WARN 수, 나머지는 `AU005` |
| 같은 인증 토큰의 동시 확인 | 204 하나, 나머지 400 `AU007` |
| 같은 재설정 토큰의 동시 확인 | 204 하나, 나머지 400 `AU007`. 비밀번호가 한 번 바뀐다 |
| 두 컬럼의 콜레이션 (`information_schema`) | 같다 |
| ASCII 대소문자만 다른 표기로 번갈아 실패 | 한 키로 센다 |
| 악센트 변형·`İ` 표기 | 관측값 — 계정 조회와 잠금 키가 같은 계정으로 모이는가 |
| 끝 공백을 붙여 100자를 넘긴 이메일로 로그인 | 401 `AU003`, 계정에 닿지 않는다, `login_attempt` 행이 생기지 않는다 |

- [ ] 같은 방법으로 board 의 비로그인 조회 판정 키가 같다(B-16·B-21) — [phase2-board.md §4.1](phase2-board.md)이 「제안」 으로 넣은 줄이다
- [ ] 재설정 요청·재발송의 응답 시간이 계정 유무로 갈리지 않는지 잰다 — 요청 스레드가 계정을 조회하지 않는 설계다([../requirements/member.md §11.3](../requirements/member.md)). 반복 수와 분포로 적는다
- [ ] SMTP 가 응답하지 않을 때 API 응답이 늦어지지 않는지 잰다 — 연결을 받고 답하지 않는 SMTP 가 필요하다. Mailpit 을 끄는 것은 연결 거부라 다른 경우다(I-06). 수단을 보고에 적는다
- [ ] 한도에 닿아야 하는 측정은 닿을 수 있는 설정으로 띄운다 — 로컬 템플릿은 한도를 크게 덮는다([../tech-stack.md §4.6](../tech-stack.md)). 쓴 설정을 보고에 적고 커밋하지 않는다(§1.3)
- [ ] 결과가 정본의 기대와 다르면 코드를 고치지 않고 보고한다(§1.3)

### I-10 2차 응답의 서비스 간 비교와 I-04 문장의 시점

| | |
| --- | --- |
| 상태 원본 | `yuno110/sp-board` 의 `docs/checklist.md` |
| 의존 | I-06 |
| 마이그레이션 | 없음 (§2) |
| 측정 대상의 출처 | [phase2-auth-member.md §5.1](phase2-auth-member.md)의 429 줄과 둘째 표, [phase2-board.md §4.1](phase2-board.md)의 multipart 매핑 줄, [integration.md](integration.md) I-04 |
| 참조 | [../api-contract.md §8.1](../api-contract.md)·§7.1·§2.5·§3.2, [../conventions.md §6.1](../conventions.md)·§7.2, [../security.md §1.1](../security.md)·§10, [../adr/0007](../adr/0007-shared-code-policy.md) |

**1차 I-04 의 2차판이다.** 세 서비스가 같은 표를 따로 구현했으므로([../conventions.md §6.1](../conventions.md)) 실제로 같은지 응답으로 본다. **먼저 그 경로가 있는지 본다** — 없는 경로를 요구하면 측정이 불가능하거나 소스 비교로 채운 공허한 충족이 된다([integration.md](integration.md) I-04 의 블록인용).

**완료 기준**
- [ ] **multipart 매핑이 세 서비스에서 같다** — 실서버에 한도를 넘는 multipart 를 보내 413 `C008`, 그 밖의 multipart 오류는 400 `C001`, 셋 다 `fieldErrors` 가 빈 배열이고 로그는 `warn` 이다. auth·member 는 multipart 를 받지 않지만 같은 핸들러를 갖는다([../api-contract.md §8.1](../api-contract.md)의 `C008` 문단). 그 예외에 닿는 실서버 경로가 없는 서비스는 그 사실을 적는다. 로그 수준은 `GlobalExceptionHandler` 가 남긴 줄로 센다
- [ ] **`C009` 를 auth·member 가 같게 낸다** — 상태·본문·`fieldErrors`·`Retry-After`, 그리고 허용 오리진에서 온 429 의 CORS 헤더와 `Retry-After` 의 노출([../security.md §1.1](../security.md)). 갈리는 것이 있으면 갈린 헤더까지 적는다 — 1차 I-04 의 `Content-Type` 처럼
- [ ] **브라우저가 직접 호출 모드의 화면 오리진에서 429 의 `Retry-After` 를 읽는다** — 수단은 이 항목이 고른다(예: F-10 의 화면을 띄워 그 안내를 본다, 그 오리진의 페이지에서 `fetch` 로 헤더를 읽는다)
- [ ] **페이징 응답을 auth 와 board 가 같게 낸다** — AU-20 의 계정 목록과 board 의 목록이 [../api-contract.md §7.1](../api-contract.md)의 키를 낸다. member 의 일괄 조회는 페이징 응답이 아니다(§3.2 의 `members` 배열). 계정 목록은 ADMIN 토큰으로 부른다([../api-contract.md §2.5](../api-contract.md)) — ADMIN 토큰은 로컬 seed 의 비밀번호를 사용자에게 받아 쓰고 남기지 않는다. 받지 못하면 그 줄은 BLOCKED 로 보고한다
- [ ] 2차 코드가 서비스 사이에 섞이지 않았다 — 1차 I-04 의 같은 줄을 2차 코드로 다시 본다. 예: `P003`·`CM003`·`AT001`~`AT003` 은 board 에만, `AU005`~`AU007` 은 auth 에만, `C009` 는 auth·member 에만 있다([../api-contract.md §8.1](../api-contract.md)의 `C009` 줄)
- [ ] **[integration.md](integration.md) I-04 에서 auth·member 에 목록·페이징 응답과 `C002` 의 변환 지점이 없다고 적은 문장들, board 에 필수 파라미터 누락 경로가 없다고 적은 문장들이 시점을 가졌는지 본다.** 1차 I-04 실측이고 AU-20 뒤 auth 에 대해, B-23 뒤 board 에 대해 낡는다 — `D-20` 이 그 시점을 붙였다. 시점이 없는 문장이 남았거나 위 페이징 비교의 결과와 어긋나는 문장이 있으면 그 자리를 보고한다 — 고치는 것은 sp-docs 의 문서 작업이다

**검증**

| 케이스 | 기대 |
| --- | --- |
| 세 서비스에 한도를 넘는 multipart | 413 `C008`, `fieldErrors: []`, 핸들러의 `warn` — 닿는 경로가 없으면 그 사실 |
| 세 서비스에 깨진 multipart | 400 `C001`, `fieldErrors: []` |
| auth·member 의 429 | 상태·본문이 같다. `Retry-After`, 허용 오리진의 CORS 헤더와 노출 |
| 브라우저에서 받은 429 | `Retry-After` 를 읽는다 |
| auth 계정 목록(ADMIN 토큰) 대 board 목록 | 페이징 키가 §7.1 의 집합으로 같다 |
| auth 계정 목록(ADMIN 토큰)에 틀린 `sort` | 400 `C002`, `fieldErrors` — 1차 I-04 에서 auth 의 `C002` 는 도달 불가였다 |
| 각 서비스의 `ErrorCode` 열거 | 다른 서비스 전용 코드가 없다 |

## 5. 정본 개정으로 넘기는 것

이 문서를 쓰며 찾은 정본의 공백이다. **이 문서는 정본을 고치지 않는다**([phase1.md](phase1.md) `D-20`) — 받을 항목은 계획을 먼저 개정해 세운다([README.md](README.md)의 항목 ID 규칙). board·auth·member 쪽은 각 계획의 같은 이름의 절이 갖는다([phase2-board.md §4.3](phase2-board.md), [phase2-auth-member.md §5.3](phase2-auth-member.md)).

- **무인증 요청에 Access Token 을 싣는 화면 동작** — 정본은 무인증 경로에서 필터가 끊는 토큰의 응답만 적고([../requirements/board.md §9.1](../requirements/board.md)) 화면이 그 경로의 요청에 토큰을 싣는지는 정하지 않았다(2026-11-12 읽기). F-08 이 지금의 동작을 확인하고 화면의 결정을 sp-frontend `CLAUDE.md` 에 적는다(§1.4). 그 결정을 정본으로 올릴지는 이 계획이 정하지 않는다
