# 2차 작업 계획

**절마다 상세화 여부가 다르다.** 작업 항목(`####` 절)을 가진 절은 작업 지시이고, 갖지 않은 절은 개요다.

개요로 남은 절은 그 범위를 고를 때 상세화한다. 미리 쓰지 않는 이유는 1차 결과를 반영해 쓰기 위해서다. 예를 들어 Outbox 테이블 설계는 1차의 트랜잭션 경계가 실제로 어떻게 잡혔는지 보고 정해야 한다. 지금 쓰면 다시 써야 한다.

## 1. 우선순위

| 순서 | 범위 | 선행 조건 | 근거 |
| --- | --- | --- | --- |
| 1 | 컨테이너화 (Docker) | 1차 완료 | [../adr/0005](../adr/0005-no-docker-in-mvp.md) |
| 2 | Kafka + 닉네임 동기화 | 컨테이너화 | [../adr/0010](../adr/0010-kafka-for-nickname-sync.md) |
| 3 | API Gateway | 1차 완료 | [../adr/0009](../adr/0009-gateway-deferred.md) |
| 4 | 기능 확장 (좋아요·첨부·카테고리·대댓글) | 1차 완료 | [../requirements/](../requirements/) |
| 5 | 운영 강화 (Resilience4j, 분산 추적) | 3 이후 | [../nfr.md §3](../nfr.md) |
| 6 | **프론트엔드 제품 품질** | 1차 완료 | [phase1.md](phase1.md) D-09 · 아래 §7 |

1과 2를 묶어서 진행한다. Kafka가 컨테이너를 필요로 하는 지점이기 때문이다.

> **I-04 는 이미 `done` 이다.** §8 이 "I-04 가 `done` 이 되면 상세화한다" 고 적었고 그 조건은 2026-10-18 에 충족됐다. **사용자가 2026-10-27 에 6(프론트엔드)을 먼저 하기로 정했다** — 그 절(§7)부터 상세화했다. **위 표의 순서는 처음 계획한 우선순위이고 진행 순서가 아니다.** 진행 순서는 사용자가 범위를 고를 때 정한다. **사용자는 2026-11-11 에 4(기능 확장)를 시작했다**(§5).

## 2. 컨테이너화

**전제**: 1차에서 환경 의존 값이 설정으로 외부화되어 있어야 한다([../tech-stack.md §4.3](../tech-stack.md)). 되어 있지 않으면 이 작업 전에 먼저 처리한다.

| 산출물 | 위치 |
| --- | --- |
| `Dockerfile` | 각 서비스 저장소 |
| `docker-compose.yml` | 문서 저장소 또는 별도 인프라 저장소 (도입 시 결정) |

**애플리케이션 코드는 그대로이고 설정값이 바뀐다.** 예를 들어 DB 접속 주소다 — `localhost:3306` → `mysql:3306`.

부수 효과로 서비스 디스커버리가 DNS 기반이 된다([../architecture.md §6](../architecture.md)). `http://localhost:8081`을 `http://member-service:8081`로 바꾸면 된다. **이 설정을 갖는 것은 board 하나뿐이다.**

**주의**: 컨테이너의 기본 시간대는 UTC다. **`ENV TZ=Asia/Seoul`을 반드시 넣는다.** JVM 시간대를 코드·빌드가 아니라 실행 환경이 정하기로 했으므로([../adr/0011](../adr/0011-timezone-from-environment.md)), 이 한 줄이 빠지면 로그와 `LocalDateTime.now()`가 UTC가 된다. 컨테이너에서 `TimeZone.getDefault()`가 `Asia/Seoul`인지 확인하는 것이 이 단계의 검증 항목이다.

**프론트엔드의 배포 오리진을 이 단계가 받는다**(§7.2). 배포할 곳이 생기면 그 오리진을 세 서비스의 `cors.allowed-origins` 에 더하고 — 그 값은 환경이 정한다([../security.md §1.1](../security.md)) — `sp-frontend` 의 부채 목록에서 그 줄을 지운다.

## 3. Kafka와 닉네임 동기화

목표는 [../adr/0003](../adr/0003-writer-snapshot.md)에서 포기했던 정합성을 되찾는 것이다.

```
member-service                              board-service
  [닉네임 변경 커밋]
  MemberNicknameChangedEvent --> Kafka --> 구독
       { accountId, nickname }              UPDATE post SET writer_nickname=?
                                            WHERE writer_id=?
```

**이벤트 키는 `accountId`다.** 전역 식별자가 `account.id`이기 때문이다([../adr/0012](../adr/0012-auth-as-separate-service.md) §1).

**필수 설계 요건** — 이것을 빼면 안 된다.

| 요건 | 이유 |
| --- | --- |
| Transactional Outbox | DB 커밋과 이벤트 발행의 원자성. 커밋 후 발행 실패하면 영원히 어긋난다 |
| 소비자 멱등성 | Kafka는 최소 1회 전달이다. 같은 이벤트를 두 번 받아도 결과가 같아야 한다 |
| `idx_post_writer_id` | 1차에서 이미 만들어 둠. 일괄 갱신 쿼리를 뒷받침한다 |

**이벤트 종류**

| 이벤트 | 발행 시점 | 소비 동작 |
| --- | --- | --- |
| `MemberNicknameChangedEvent` | member의 닉네임 변경 | `post`·`comment`의 `writer_nickname` 갱신 |
| `MemberWithdrawnEvent` | member의 프로필 탈퇴 | `writer_nickname`을 "탈퇴한 회원"으로 갱신 |
| `AccountWithdrawnEvent` | **auth의 계정 탈퇴** | member가 구독해 프로필을 soft delete. 탈퇴 2단계를 서버가 책임진다 |

세 이벤트 모두 페이로드의 식별자는 `accountId`다.

**1차 코드에 발행 훅을 미리 넣지 않는다.** YAGNI. Outbox 테이블과 함께 추가한다.

### 3.1 탈퇴 2단계를 서버로 옮긴다

1차의 탈퇴는 클라이언트가 2단계를 호출하고, 서버는 완주를 강제하지도 관측하지도 못한다([../architecture.md §4.4](../architecture.md)). `AccountWithdrawnEvent`가 이것을 해소한다.

```
auth: [계정 삭제 + RefreshToken 삭제 + outbox INSERT]  <- 한 로컬 트랜잭션
        --> Kafka --> member 구독 --> 프로필 soft delete (멱등)
```

**추가 요건**

| 요건 | 이유 |
| --- | --- |
| 삭제 이벤트가 프로필 생성보다 먼저 도착하는 경우 | member에 삭제 표식을 남겨야 한다. "삭제할 프로필 없음"으로 끝내면 뒤늦은 생성 요청이 통과한다 |
| 탈퇴 완료의 의미 | auth에서 계정이 막힌 시점인지, member 삭제까지 반영된 시점인지 API가 구분해야 한다. 비동기 정리 중인데 "완료"라고 응답하면 계약이 거짓이 된다 |
| 장기 실패 탐지 | outbox에 쌓인 채 전달되지 않는 이벤트를 관측할 수 있어야 한다 |

## 4. API Gateway

Spring Cloud Gateway를 도입한다. Boot 버전과 호환되는 릴리스 트레인을 확인해 고정한다.

| 담당 | 내용 |
| --- | --- |
| 라우팅 | [../api-contract.md §1](../api-contract.md)의 경로 표가 그대로 명세가 된다 |
| CORS | 각 서비스의 개별 설정을 게이트웨이로 이관 |
| `/internal/**` | **라우팅에서 제외**해 외부 노출을 차단 |
| 1차 JWT 검증 | 게이트웨이에서 한 번, 각 서비스에서 한 번 더 (Zero Trust) |

각 서비스의 독립 검증을 제거하지 않는다. 게이트웨이 우회 호출 가능성을 배제하지 않는다.

### 5.1 사용자가 정한 것 (2026-11-11)

| 물음 | 결정 |
| --- | --- |
| 첨부(P-10) — 저장소 | **저장소 인터페이스 + 로컬 디스크 구현으로 시작한다.** S3 는 컨테이너화·다중 인스턴스 때 다시 본다 |
| 첨부 — 보이는 자리 | **글 하단 갤러리.** 본문은 평문 그대로다 |
| 첨부 — 한도와 형식 | 글당 최대 10개, 개당 5MB, JPEG·PNG·GIF·WebP(SVG 금지). **형식은 파일 내용(매직 바이트)으로 판정한다** |
| 첨부 — EXIF | **제거하지 않는다** |
| 조회수 어뷰징(24시간 1회) — 구분 | 로그인 사용자는 accountId, 비로그인은 **접속 IP 의 HMAC** 으로 구분한다 |
| 조회수 — 판정 저장 | **DB 테이블.** Redis 를 들이지 않는다 |
| 카테고리(P-11) | 공지/자유/질문. **선택하지 않으면 자유, 기존 글은 자유** |
| 카테고리 — 공지 권한 | **공지는 ADMIN 만 쓰고, 공지로 바꾸거나 공지에서 뺄 수 있다** — 아니면 403 |
| 카테고리 — 공지 고정 | 전체 목록 첫 페이지 위에 최근 공지를 고정해 보인다. **화면이 공지를 따로 조회한다** |
| 대댓글(C-05) | **1단계.** 답글이 달린 댓글을 지우면 답글은 남고 부모 자리에 「삭제된 댓글입니다」 를 보인다(활성 답글이 있을 때만). **삭제된 댓글에는 새 답글을 달 수 없다** |
| 이메일 인증 | **로그인을 막는다.** 인증 전에는 로그인할 수 없고, 비밀번호가 맞은 뒤에만 '인증 필요' 를 드러낸다 |
| 메일 발송 | 운영은 SMTP(접속 정보는 환경변수, 기본값 없음), 로컬·e2e 는 Mailpit(단일 실행 파일, Docker 아님). **커밋 뒤 비동기로 보낸다** |
| 로그인 잠금 | 이메일(소문자 정규화) 단위로 **연속 5회 실패 시 15분 잠금.** 자동으로 풀리고 비밀번호 재설정으로도 풀린다. 잠기면 **401 새 코드**로 알린다 — 없는 이메일도 똑같이 잠기므로 존재가 새지 않는다. IP 요청 제한을 보조로 둔다 |
| 계정 열거 방어 | **가입의 409 `AU002` 를 유지하고 IP 단위 요청 수 제한(429)을 건다.** 이것이 열거를 막지 못하고 비용만 올린다는 것을 정본에 정직하게 적는다 |

**이 표가 사용자의 결정이고, 아래 기본값은 오케스트레이터가 board 설계에 둔 것이다** — 사용자가 따로 정하지 않은 자리를 메웠다. 자리마다의 근거는 가리키는 정본 절이 적는다.

| 자리 | 오케스트레이터 기본값 |
| --- | --- |
| API 버전 | **v1 안에 둔다.** 댓글 목록 밖의 변경은 추가형이다([../adr/0008](../adr/0008-api-versioning.md)의 하위 호환 변경). **댓글 목록은 구조·의미의 변경이지만 예외로 v1 에 둔다** — 근거와 재검토 조건은 그 ADR 의 2026-11-11 블록인용. 카테고리는 작성 때 고르는 선택 필드이고 글 작성 요청은 JSON 그대로다 |
| 카테고리 저장·조회 | `VARCHAR(20)` enum, 목록의 선택 파라미터 `category`, 공지 권한 위반은 새 코드 `P003` |
| 조회수 판정 | 선택적 인증(익명이면 계정 없음, 잘못된 토큰은 401), 비로그인 식별 비밀키는 환경변수이고 설정 문자열의 UTF-8 바이트가 32 이상이다, `X-Forwarded-For` 를 믿지 않는다, 오래된 판정 행은 주기적으로 지운다. **판정은 조건부 UPDATE 를 먼저 하고**, 0행이면 판정 행이 있는지 읽어 없을 때만 INSERT 한다. 집계의 +1 은 판정 트랜잭션 안이고, 응답의 `viewCount` 는 판정 커밋 뒤에 시작된 읽기에서 얻는다 |
| 좋아요 | 취소할 수 있다. `PUT`·`DELETE …/like` 둘 다 멱등이고 상태를 돌려준다. **프로필이 필요 없다.** 자기 글도 된다. 좋아요순 정렬은 이번 범위 밖. **`like_count` 의 좁은 UPDATE 를 먼저 해 `post` 행의 배타 락을 잡고 `post_like` 쓰기를 나중에 한다** — 근거 행이 새로 생기거나 지워지지 않으면 트랜잭션을 되돌린다 |
| 대댓글 | 최상위 댓글을 페이징하고 답글은 각 최상위 아래에 전부 싣는다. 응답에 `deleted` 를 더한다. `comment_count` 는 답글을 포함한다 |
| 첨부 흐름 | 글을 만든 뒤 파일마다 업로드한다. 서빙은 board 가 스트리밍한다. 형식 판정에 의존성을 더하지 않는다. 에러 접두어 `AT`. 글을 지우면 그 첨부의 내려받기는 404 다. 어느 행도 가리키지 않는 파일의 정리는 이번 범위 밖이다. 개수 상한은 `attachment_count` 의 조건부 UPDATE 가 판정하고, 삭제는 첨부 행의 조건부 전환(활성일 때만)이 0행이면 되돌린다 |
| multipart 예외 | 세 서비스가 같은 매핑을 갖는다([../conventions.md §6.1](../conventions.md)) |

**두 표에 없는 값은 `D-18` 이 정했다** — 예: 새 에러 코드의 번호·HTTP 상태·메시지, multipart 한도와 캐시 헤더, 조회자 판정 키의 모양, 답글 자리의 가림. 값마다 아래 §5.2 의 정본 절이 적고, 사용자 결정이 아니므로 근거가 바뀌면 정본 개정으로 바꾼다.

### 5.2 board 설계의 정본 위치

### 5.3 프론트엔드에 미치는 것

**화면 고유의 결정은 `sp-frontend` 의 `CLAUDE.md` 가 갖는다**(§7). 여기는 이 설계가 화면에 요구하는 것을 설계 수준으로 적고, 항목은 `D-20` 이 세운다.

- **목록** — 카테고리 탭과 공지 배지. 전체 목록 첫 페이지 위에 최근 공지를 고정한다(예: 최근 3개, `GET /api/v1/posts?category=NOTICE&page=0&size=3`). 서버는 전체 목록에서 공지를 빼지 않으므로 고정 영역과 아래 목록에 같은 글이 함께 보일 수 있다 — 어떻게 보일지는 화면이 정한다
- **작성·수정 폼** — 카테고리 선택. 공지는 ADMIN 일 때만 고를 수 있게 그리되 **최종 판정은 서버의 `P003` 이다**
- **상세** — 좋아요 버튼(`liked`·`likeCount`, 비로그인이면 로그인 안내), 글 하단 갤러리, 작성자에게만 보이는 업로더. 글 작성은 글을 만든 뒤 파일마다 업로드를 보내므로 **일부 파일만 실패한 상태**를 화면이 다룬다
- **댓글** — 최상위 댓글에만 답글 쓰기, 삭제된 부모 자리의 「삭제된 댓글입니다」
- **CSP** — 직접 호출 모드에서는 갤러리 이미지가 board 오리진에서 오므로 `img-src` 에 그 오리진이 있어야 한다(프록시 모드는 `'self'`). 지금 정책은 `default-src 'self'` 에 기대므로 직접 모드에서 그 이미지가 막힐 것으로 본다 — 업로더가 미리보기를 `blob:` URL 로 그리면 그것도 필요하다
- **업로드 요청의 헤더** — 화면의 API 클라이언트가 기본 헤더로 `Content-Type: application/json` 을 둔다. 그 헤더가 `FormData` 본문을 JSON 으로 바꾸거나 multipart 경계(boundary)를 빠뜨리게 할 것으로 **추정한다 — 측정 대상이다.** 업로드 요청은 브라우저가 경계를 붙인 `Content-Type` 을 보내야 한다
- **경로 배정** — 새 접두어 `/api/v1/attachments` 를 board 에 배정해야 한다. 배정하는 자리는 그 저장소 `CLAUDE.md` 의 「서비스 주소와 CORS」 가 적는다
- **에러 문장** — 이 설계가 [../api-contract.md §8](../api-contract.md)에 더한 코드에 문장이 있어야 한다. 화면의 코드 사전 테스트(`F-03`)는 §8 을 손으로 옮긴 목록과 비교하므로, 정본에 코드가 더해져도 빨개지지 않는다(그 테스트 파일의 주석이 그렇게 적는다). 고치기 전까지 화면은 사전에 없는 코드를 서버 메시지와 코드로 보인다 — 옮긴 목록과 사전을 함께 고치는 것을 `D-20` 이 세울 화면 항목의 완료 기준에 둔다. 업로드 화면의 `C008` 은 그 자리의 뜻(파일 크기 한도)으로 안내한다
- **조회수** — 댓글을 쓴 뒤 화면이 상세를 다시 받으면서 조회수가 오르던 동작이 사라진다. 같은 계정의 재조회가 24시간 안이기 때문이다([../requirements/board.md §9](../requirements/board.md))

### 5.4 동시성과 측정

**`post` 행을 바꾸는 좁은 UPDATE 가 집계마다 하나씩 있다** — `comment_count`(1차 B-10)·`view_count`(1차 B-11)에 `like_count`·`attachment_count` 가 더해진다. 모두 같은 행의 락을 다툰다. 같은 행의 교착은 [../nfr.md §1](../nfr.md)이 1차의 한계로 남긴 것과 같은 종류이고 이 범위에서도 한계로 둔다 — 다만 **집계가 근거 행과 어긋나는 것(소실 갱신·중복 증감)과 상한을 넘는 것은 결함이다**([../domain-model.md §6](../domain-model.md)).

**동시성에서만 드러나고 H2 가 MySQL 의 락을 재현하지 않는 성질은 실 MySQL 에서 잰다** — 집계 컬럼이 근거 행의 수와 같은가(같은 근거 행의 동시 삭제가 집계를 두 번 바꾸지 않는가 — 1차의 댓글 삭제 경로를 포함한다, [../domain-model.md §6](../domain-model.md)), 원자적 상한이 지켜지는가, 판정 순서가 교착을 만드는가, 그리고 실서버에서만 거치는 한도(servlet multipart·Tomcat)가 계약대로 응답하는가. 예: 같은 글에 대한 동시 좋아요·취소, 같은 글의 동시 첫 조회, 동시 답글, 같은 부모에 대한 답글 작성과 부모 삭제, 동시 업로드의 개수 상한, 한도를 넘는 업로드. **격리 수준이 H2 와 다를 수 있는 것도 같이 잰다** — 상세 응답의 `viewCount` 가 판정의 커밋을 보는가([../requirements/board.md §9.3](../requirements/board.md)). 경합의 UNIQUE 충돌이 어느 로그 수준으로 남는지도 잰다(같은 절). **`D-20` 이 이것을 통합 항목으로 세운다.**

## 7. 프론트엔드 제품 품질

`yuno110/sp-frontend` 는 2026-10-20 에 **확인용 도구로 만들어져 같은 날 제품 화면으로 승격됐다**([phase1.md](phase1.md) D-08·D-09). **승격은 분류만 바꿨다** — 그 항목이 품질 작업을 범위에서 뺐고 **여기가 그것을 받는 자리다.** 넘긴 쪽이 받을 자리를 적지 않으면 그 문장이 공허해진다.

받는 것은 그 저장소의 `CLAUDE.md` 가 **"제품으로서 비어 있는 것"** 으로 적어 둔 목록이다. **그 목록이 정본이고 여기에 옮겨 적지 않는다.** 아래 항목은 그 목록의 줄을 묶은 것이고, 항목이 끝나면 **그 목록에서 해당 줄을 지운다.** **이 절은 `F-xx` 가 모두 `done` 이면 끝난다** — 배포 오리진 줄은 남고 §2 가 받는다.

**화면 전용 요구사항 문서는 만들지 않는다.** 기능은 [../requirements/member.md](../requirements/member.md)·[../requirements/board.md](../requirements/board.md)가 정하고 화면이 그것을 따른다(D-09 의 결정). **화면 고유의 결정은 그 저장소의 `CLAUDE.md` 가 갖는다** — 아래 항목이 내리는 결정도 거기에 적는다.

### 7.1 사용자가 정한 것 (2026-10-27)

| 물음 | 결정 |
| --- | --- |
| 요청 기록 패널·`/tokens` 화면 | **개발 빌드에서만 둔다.** 프로덕션 빌드에서 빠진다 |
| 토큰 보관 | **Access Token 은 메모리에만, Refresh Token 은 `sessionStorage`** 에 두고 **CSP 를 더한다.** 백엔드와 정본 계약은 바꾸지 않는다 |
| 에러 문구 | **사용자용 문장과 필드별 안내로 다듬는다.** 코드는 버리지 않는다 |
| 화면의 확인용 문구 | **걷는다.** 버튼은 사용자 말로 바꾸고, 정본 인용과 토큰 claim 표시는 개발 빌드에서만 보이게 한다 |
| 탈퇴 | **한 동작으로 합친다.** 비밀번호를 한 번 확인하고 화면이 두 단계를 순서대로 부른다. "토큰 비우기" 버튼은 없앤다. 서버 계약은 그대로다 |
| 가입 | **한 흐름으로 합친다.** 계정을 만들면 방금 입력한 비밀번호로 화면이 바로 로그인하고 프로필 등록으로 넘어간다. 서버 계약(3단계)은 그대로다 |

에러 문구·확인용 문구·탈퇴·가입은 부채 목록에 없던 것이라 **그 목록에 줄을 더했다.**

> **확인용 문구는 사용자가 `F-01` 에 넣기로 골랐지만, 버튼 문구는 `F-03` 으로 옮겼다.** 사용자에게 보이는 문구를 한 항목이 모두 맡아야 두 항목의 문구 고치기가 겹치지 않는다(D-12 2라운드 리뷰의 제안). 정본 인용과 claim 표시를 개발 빌드로 가르는 것은 `F-01` 에 남는다. 결정의 내용은 바뀌지 않았고 배치만 바뀌었다.

> **Refresh Token 을 `httpOnly` 쿠키로 두는 쪽은 택하지 않았다.** 가장 안전하지만 auth 의 로그인·재발급·로그아웃 응답과 그 경로의 CORS — [../security.md §1.1](../security.md)의 `allowCredentials = false` — 그리고 CSRF 대책이 함께 바뀐다. **남는 위험을 숨기지 않는다** — `sessionStorage` 의 Refresh Token 은 스크립트가 읽을 수 있으므로 XSS 가 있으면 탈취된다. CSP 는 그 위험을 줄이지 없애지 않는다.

### 7.2 항목

항목 ID 는 **`F-xx`** 이고 상태 원본은 `yuno110/sp-frontend` 의 `docs/checklist.md` 다([README.md](README.md) §상태의 위치). **한 워커가 의존 열을 따라 한다** — 여러 항목이 같은 화면 파일을 고치기 때문이다. 그래서 `F-xx` 는 [phase1.md §1.1](phase1.md)의 단계 구분을 쓰지 않는다 — 그 표의 기능 단계는 기반 산출물을 읽기만 하고 자기 파일을 만드는데, `F-xx` 는 같은 화면 파일을 고치므로 그 성질이 성립하지 않는다. e2e 가 마지막인 것은 앞 항목이 바꾼 화면 흐름을 잠그기 위해서다.

**배포 오리진은 항목으로 세우지 않는다.** 배포할 곳이 생겨야 정할 수 있고 §2 가 받는다.

**범위는 성질로 정한다.** 아래 기준이 "그런 문구가 없다" 를 요구하는 곳에서는 **구현자가 검사 목록을 정해 테스트로 단언하고, 그 목록이 변경 전 화면에서 실제로 잡히는 것을 보인다**(양성 대조). 이 계획이 문구를 하나하나 열거하지 않는 이유는 열거가 빠진 것을 범위 밖으로 읽히게 하기 때문이다([../process/review-policy.md §8.1](../process/review-policy.md)).

> **`F-02`·`F-03`·`F-04` 의 문장 일부는 그 항목들을 구현한 뒤에 고쳤다** — 2026-11-09 에 `sp-frontend` `42176d8` 이 바꾼 동작에 맞췄다([phase1.md](phase1.md) `D-16`).

**산출물**
- Access Token 을 **메모리에만** 둔다. 영속하는 것은 Refresh Token 하나다
- **새로고침하면 Refresh Token 으로 재발급한 뒤** 보호된 화면을 그린다. **같은 Refresh Token 으로 동시에 일어나는 재발급을 하나로 합친다** — React 의 StrictMode 는 개발 중 효과를 두 번 실행한다. 보낸 Refresh Token 이 지금 값과 다른 재발급은 기다리지 않는다
- **재발급이 거부되면**(401 `A002`·`A003` — [../api-contract.md §2.1](../api-contract.md)) 재발급을 기다리는 사이 Refresh Token 과 세션이 그대로였을 때 토큰을 지운다. 그 밖의 실패(예: 5xx, 응답 없음, 토큰이 빠진 2xx)는 토큰을 지우지 않는다 — 새로고침이 auth 를 거치므로 지우면 auth 의 장애가 로그아웃이 된다
- 재발급이 실패해 로그인 상태를 잇지 못하면 **보호된 경로에서만** 로그인으로 보낸다 — 새로고침에서는 어느 실패든 그렇고(거부가 아니면 다음 새로고침이 다시 묻는다), 쓰는 중에는 거부가 그렇다. 공개 경로는 비로그인 상태로 그대로 보이고 **그 이유를 그 자리에서 보인다**
- 로그아웃이 **성공하면** 영속된 Refresh Token 까지 지운다. **실패하면 지우지 않고** 그 실패를 보인다 — 그 실패에 이어진 재발급이 거부됐으면 위의 거부대로 세션이 끝난다. 로그아웃을 기다리는 사이 세션이 끝났거나 다른 세션이 시작됐으면 그 응답으로 토큰을 지우거나 화면을 옮기거나 실패를 보이지 않는다
- **프로덕션 빌드의 `index.html` 에 CSP 를 넣는다.** 개발 서버에는 넣지 않는다 — React 플러그인의 Fast Refresh 가 인라인 스크립트를 쓴다
- `sp-frontend/CLAUDE.md` 의 토큰 보관 서술을 고치고 **남는 위험(위 §7.1 블록인용)을 그 「경계」에 적는다.** 부채 목록의 그 줄은 지운다
- **정본 개정이 함께 필요하다.** 새로고침마다 재발급하면 [../requirements/member.md §6.2](../requirements/member.md)의 "자동 재발급은 1초 창에 들어가지 않는다" 가 거짓이 된다 — 로그인 직후 새로고침하면 같은 초에 재발급한다. **구현 워커는 정본을 고치지 않는다**([../process/review-policy.md §8](../process/review-policy.md)). 오케스트레이터가 이 항목을 받아들일 때 `D-xx` 로 그 줄을 고친다

**완료 기준**
- [ ] 로그인 뒤 `sessionStorage` 에 **Access Token 이 없다**
- [ ] 새로고침 뒤에도 로그인 상태가 이어지고 **재발급 요청이 한 번** 나간다 — **StrictMode 에서도 한 번이다.** 같은 Refresh Token 으로 두 번 재발급하면 회전의 조건부 UPDATE 에 지고(§2.1), 실패 처리가 첫 번째가 받은 새 토큰까지 지운다(`F-02` 전의 실패 처리다 — 지금은 그 실패가 먼저 도착하면 세션이 끝난다, [phase1.md](phase1.md) `D-13`). 둘째가 `A002` 를 받고 그 실패 처리가 첫 번째의 새 토큰까지 지우는 것은 2026-11-11 `D-17` 전의 서버다 — 그 뒤로는 회전에 지더라도 10초 안이면 유예로 200 이다([../requirements/member.md §6.3](../requirements/member.md)). 이 기준의 요구(요청 한 번)는 바뀌지 않는다
- [ ] Refresh Token 이 없거나 거부되면 **보호된 경로**는 그려지지 않고 로그인으로 간다. 공개 경로는 보인다
- [ ] 재발급이 거부가 아닌 이유로 실패하면 Refresh Token 이 남는다. 재발급이 실패해 로그인 상태를 잇지 못하면 공개 경로는 그 자리에 이유를 보인다
- [ ] 로그아웃을 기다리는 사이 세션이 그대로였으면, 성공할 때 `sessionStorage` 에 토큰이 남지 않고(탈퇴는 `F-04` 가 본다) 실패할 때 토큰이 남고 그 실패가 보인다. 기다리는 사이 다른 세션이 시작됐으면 로그아웃이 어떻게 끝나든 그 세션의 토큰이 남는다
- [ ] 프로덕션 `index.html` 의 CSP 가 `script-src` 에 `'unsafe-inline'`·`'unsafe-eval'` 을 갖지 않고, `connect-src` 가 **세 서비스의 환경값 주소**를 갖는다(프록시 모드면 `'self'`)

**검증**

| 케이스 | 기대 |
| --- | --- |
| 로그인 뒤 영속 저장소 | Refresh Token 만 있다 |
| 부트스트랩 재발급을 동시에 두 번 호출 | 요청은 한 번이고 두 호출이 같은 결과를 받는다 |
| Refresh Token 없음 / 재발급 거부(401 `A002`·`A003`) — 보호된 경로 | 로그인으로 간다. 보호된 화면이 그려지지 않는다 |
| 같은 경우 — 공개 경로 | 비로그인 상태로 보인다. 재발급 거부면 그 자리에 이유가 보인다 |
| 새로고침의 재발급이 거부가 아닌 실패(예: 5xx, 응답 없음) | Refresh Token 이 남는다. 보호된 경로는 로그인으로 가고 공개 경로는 그 자리에 이유가 보인다 |

| 로그아웃을 기다리는 사이 다시 로그인 | 로그아웃이 어떻게 끝나든 새 세션의 토큰이 남고, 화면을 옮기지 않고 실패가 보이지 않는다 |
| CSP 변환 결과(빌드 모드) | 위 기준의 지시어를 갖는다. 개발 모드에서는 넣지 않는다 |

**실제 브라우저에서 CSP 위반이 없는지는 `F-05` 가 본다.**

> **로그아웃 요청의 모양은 2026-11-11 `D-17` 이 바꿨다** — 본문에 그 세션의 Refresh Token 을 싣는다([../api-contract.md §2.1](../api-contract.md)). 이 항목의 기준과 표는 화면이 토큰을 언제 지우는지를 적고 그 판정은 바뀌지 않는다. 표의 「로그아웃을 기다리는 사이 다시 로그인」 에서 서버의 행은 `D-17` 전에는 옛 세션의 로그아웃이 늦게 처리되면 지워질 수 있었다 — 화면에 새 세션의 토큰이 남아도 서버에서는 그 세션이 끝나 있을 수 있었다. 화면 쪽 변경은 `D-17` 의 산출물이다([phase1.md](phase1.md) `D-17`).

#### F-03 화면 문구를 사용자용으로 바꾼다

| | |
| --- | --- |
| 저장소 | `yuno110/sp-frontend` |
| 의존 | `F-01` (개발 전용 표시가 갈린 뒤의 화면을 고친다) |
| 참조 | [../api-contract.md §8](../api-contract.md), 코드의 뜻이 엔드포인트마다 갈리는 곳은 그 엔드포인트의 절(예: §3.1 의 `M001`), `sp-frontend/CLAUDE.md` 의 불변식 9 |

**대상은 사용자에게 보이는 문구 전부다** — 예를 들어 버튼 라벨, 패널 제목, 링크, 입력 안내, 에러 문구. **고칠 성질은 하나다: 사용자에게 내부 구조를 설명하지 않는다.** 예를 들어 서비스 이름, HTTP 메서드·경로, 에러 코드 체계와 상태 코드의 설명, 정본 문서, API 필드 이름이다.

본문 DTO 의 필드 오류 문장은 사용자용이다(예: "제목은 1~200자여야 합니다."). 게시글·댓글 목록의 `page`·`size` 하한 위반은 검증기 기본 문장이 나가지만, 화면이 그 값을 사용자에게 받지 않으므로 이 항목이 다루지 않는다.

**산출물**
- 버튼 라벨과 입력 안내를 사용자 말로 바꾼다
- 에러 코드마다 사용자용 문장을 둔다. **같은 코드가 엔드포인트마다 다른 뜻을 가지면 그 뜻을 따른다** — 뜻은 이 계획이 아니라 [../api-contract.md](../api-contract.md)가 정한다
- 복구 동작이 있는 경우 그 동작을 안내한다
- 필드 오류를 **해당 입력칸 옆에** 보여준다
- 부채 목록에서 해당 줄을 지운다

**완료 기준**
- [ ] **사용자에게 보이는 문구에 내부 구조를 설명하는 것이 없다.** 위 「범위는 성질로 정한다」의 방법으로 단언한다
- [ ] [../api-contract.md §8](../api-contract.md)의 **모든 코드**에 사용자용 문장이 있다 — 코드 사전과 문장의 코드 집합이 같다는 것을 테스트가 단언한다
- [ ] **복구 동작을 안내한다** — 프로필이 아직 없다는 뜻이면 프로필 등록으로, 인증이 끝났거나 실패한 경우(`A001`·`A002`·`A003`)는 로그인으로, 연동 실패(`S001`)는 잠시 후 다시 시도로. 같은 코드라도 다른 뜻으로 쓰인 자리(예: 남의 프로필 조회의 `M001`)에서는 그 안내를 하지 않는다. **내 프로필이 탈퇴한 상태면** 프로필 등록이 아니라 다른 이메일로 새 계정을 만들도록 안내한다 — `M007` 이 그렇고, `M001`·`S002` 는 미등록과 탈퇴를 가르지 않으므로 공개 조회(`GET /api/v1/members/{accountId}`)의 `deleted` 로 가른다([../api-contract.md §3.1](../api-contract.md)). 가르기 전이나 가르지 못했으면 프로필 등록으로 안내한다. 계정 탈퇴가 끝나고 프로필 탈퇴가 남은 상태를 보이는 안내는 만료(`A003`)를 로그인으로 안내하지 않는다 — 탈퇴한 계정은 로그인할 수 없다
- [ ] **모르는 코드는 버리지 않는다.** 서버 메시지와 코드를 그대로 보여준다
- [ ] **코드가 화면에서 사라지지 않는다.** 실제로 난 오류의 코드는 보조 정보로 남긴다(불변식 9 — 다듬는 것과 버리는 것은 다르다)
- [ ] 입력칸이 없는 필드의 오류는 요약에 남는다 — **어느 필드 오류도 버려지지 않는다**
- [ ] 응답이 없는 실패(연결 거부·CORS·타임아웃)는 업무 오류와 다른 문장이고, **그 문장도 내부 구조를 설명하지 않는다**

**검증**

| --- | --- |
| 화면마다 보이는 문구를 검사 목록으로 | 걸리는 것이 없다 |
| 코드 사전과 문장의 코드 집합 | 같다 |
| 복구 안내가 있는 경우마다 | 그 안내가 보인다 |
| 같은 코드의 다른 뜻(남의 프로필 조회 `M001`) | 프로필 등록 안내가 없다 |
| 탈퇴한 내 프로필의 `M001`·`S002`(공개 조회가 `deleted: true` 를 답한 뒤)·`M007` | 프로필 등록 안내가 없고 새 계정 안내가 보인다 |
| 계정 탈퇴 뒤 프로필 탈퇴가 남은 상태를 보이는 안내의 `A003` | 로그인 안내가 없다 |

#### F-04 가입과 탈퇴를 사용자 흐름으로 합친다

| | |
| --- | --- |
| 저장소 | `yuno110/sp-frontend` |
| 의존 | `F-02` (토큰을 만들고 지우는 시점), `F-03` (실패를 알리는 문구) |
| 참조 | [../api-contract.md §9.1](../api-contract.md)·§9.1.1·§2.2·§3.1, [../architecture.md §4.4](../architecture.md) |

**서버 계약은 그대로다.** 가입은 계정 → 로그인 → 프로필, 탈퇴는 계정 → 프로필이고 **순서를 바꾸지 않는다.** 바뀌는 것은 화면이 그 단계를 사용자 단계로 드러내지 않는다는 것뿐이다.

**산출물**
- **가입** — 계정을 만들면 방금 입력한 비밀번호로 바로 로그인하고 프로필 등록으로 넘어간다. 계정은 만들어졌는데 로그인이 실패하면 그 사실을 알리고 로그인 화면으로 보낸다 — 1단계만 끝난 상태는 정상이다(§9.1)
- **멈춘 가입** — 가입을 낸 뒤 로그아웃이나 다른 로그인이 시작됐으면 나중에 시작한 쪽이 이긴다. 가입은 계정을 만든 뒤로 나아가지 않는다 — 로그인을 보내지 않거나 그 응답을 쓰지 않고(세션으로 삼지도, 실패를 남기지도 않는다) 화면을 옮기지 않으며 다른 세션을 건드리지 않는다. 가입 화면이 아직 떠 있으면 만든 계정의 이메일과 그 이메일로 로그인하라는 안내·링크를 보이고 계정 만들기를 막는다. 화면을 떠났으면 알리지 않는다. 1단계만 끝난 상태는 정상이다(§9.1)
- **탈퇴** — 비밀번호를 한 번 받아 계정 탈퇴 → 프로필 탈퇴를 순서대로 부른다. 프로필 탈퇴는 계정 탈퇴와 같은 로그인의 Access Token 으로 부른다(§9.1.1, [../requirements/member.md §8](../requirements/member.md))
- **첫 단계가 실패하면 둘째를 부르지 않는다** — 비밀번호가 틀리거나(`AU004`) 비어 있는 경우(`C001`)를 포함한다
- **둘째 단계의 404 `M001` 은 끝난 것으로 본다.** 프로필이 아예 없는 계정이고(§3.1 — 그 경우는 멱등의 대상이 아니다) 지울 것이 없다
- **둘째 단계가 다른 이유로 실패하면** 그 사실을 알리고 다시 시도하게 한다. 다시 시도는 첫 단계부터 부르고, 그때도 비밀번호를 받는다 — 이미 탈퇴한 계정은 비밀번호가 틀려도 204 지만(§2.2) **빈 값은 빈 값 검사(`@NotBlank`)에 먼저 걸린다**
- **예외 — 탈퇴를 기다리는 사이 다시 로그인해 다른 세션이 시작됐으면** 그 세션은 건드리지 않는다. 둘째 단계는 탈퇴를 시작한 로그인의 토큰으로 나가고([../requirements/member.md §8](../requirements/member.md)) 끝나도 토큰을 지우거나 화면을 옮기지 않는다. 그 둘째 단계가 실패하거나 토큰을 알 수 없어 보내지 않으면 탈퇴를 시작한 계정의 프로필이 남고 화면은 그 사실을 알리지 못한다 — 알릴 화면은 이미 내려갔고 새 세션의 일이 아니다. 사용자가 2026-11-09 에 이 경우를 정본에 예외로 적기로 정했다([phase1.md](phase1.md) `D-16`). 위의 실패 처리와 아래 완료 기준의 알림·다시 시도·끝난 뒤의 상태는 이 경우를 빼고 읽는다
- **두 단계가 끝난 뒤에 탈퇴를 시작한 로그인의 토큰을 지운다** — 둘째 단계가 실패하면 남은 그 토큰으로 다시 시도한다. 그 사이 이 탭의 로그인이 끝나도(예: 로그아웃) 둘째 단계는 탈퇴를 시작한 로그인의 토큰으로 나간다
- "토큰 비우기" 버튼을 지운다(§7.1)
- 부채 목록에서 해당 줄을 지운다

**완료 기준**
- [ ] 가입 화면에서 사용자가 누르는 제출이 계정 정보와 닉네임 둘이고, 그 사이에 로그인 요청이 나간다(멈춘 가입은 제외)
- [ ] 계정 생성 뒤 로그인이 실패하면 로그인 화면으로 가고 그 사실이 보인다(멈춘 가입은 제외)
- [ ] 탈퇴 동작 하나가 두 요청을 **계정 → 프로필** 순서로 보낸다
- [ ] 첫 단계가 실패하거나 둘째 단계를 보낼 토큰을 알 수 없으면([../requirements/member.md §8](../requirements/member.md)) 둘째 요청이 없다
- [ ] 둘째 단계가 404 `M001` 이면 탈퇴가 끝난 것으로 처리된다
- [ ] 둘째 단계가 다른 이유로 실패하면 **탈퇴를 시작한 로그인의 Access Token 이 남아 있는 동안** 다시 시도할 수 있다
- [ ] 다시 시도할 수 없게 되면(아래 블록인용) 그 사실이 보인다 — 위 예외는 빼고
- [ ] "토큰 비우기" 버튼이 없다
- [ ] 이 항목이 새로 쓴 문구(실패·재시도 안내)도 `F-03` 의 문구 검사를 통과한다
- [ ] 끝나면 탈퇴를 시작한 로그인의 토큰이 남지 않는다. 그 사이 다른 세션이 시작되지 않았으면 로그인 상태가 아니다 — 시작됐으면 위 예외대로 그 세션을 건드리지 않는다

> **다시 시도할 수 없게 되는 경우가 있다.** 첫 단계가 Refresh Token 을 지웠으므로 **Access Token 을 잃으면** 재발급도 안 된다 — 만료와 탭 닫기가 그렇고, `F-02` 뒤에는 Access Token 이 메모리에만 있으므로 **새로고침도 그렇다.** 둘째 단계가 401 `A003` 이고 재발급이 거부되어(401 `A002`·`A003`) 토큰이 비워지는 것도 같은 경우다. 1차의 알려진 제약이고([../architecture.md §4.4](../architecture.md)) 이 항목이 풀지 않는다. 화면은 그 경우를 숨기지 않고 알린다. 탈퇴를 기다리는 사이 다른 세션이 시작된 경우는 위 예외다 — 화면이 알리지 못한다.

**검증**

| 케이스 | 기대 |
| --- | --- |
| 가입 — 세 요청 모두 성공 | 계정 → 로그인 → 프로필 순서이고 로그인 상태로 끝난다 |
| 가입 — 계정 성공, 로그인 실패(멈춘 가입은 제외) | 로그인 화면으로 가고 실패가 보인다 |
| 가입 — 계정 생성이나 그 뒤의 로그인을 기다리는 사이 로그아웃·다른 로그인(계정 생성은 성공) | 가입이 멈추고 다른 세션을 건드리지 않는다. 가입 화면이 떠 있으면 만든 계정의 이메일과 로그인 안내가 보이고 계정 만들기가 막힌다 |
| 탈퇴 — 두 단계 모두 204(위 예외는 빼고) | 요청 순서가 계정 → 프로필이고 끝난 뒤 토큰이 없다 |
| 탈퇴 — 첫 단계 `AU004` / `C001` | 둘째 요청이 없다 |
| 탈퇴 — 둘째 단계 404 `M001` | 끝난 것으로 처리된다 |
| 탈퇴 — 둘째 단계 그 밖의 실패 | 탈퇴를 시작한 로그인의 Access Token 이 있으면 다시 시도할 수 있다 |
| 탈퇴 — 다시 시도할 수 없는 경우(위 예외는 빼고) | 그 사실이 보인다 |
| 탈퇴 — 첫 단계를 기다리는 사이 다른 계정으로 로그인 | 둘째 요청이 1단계가 보낸 토큰으로 나가고 새 세션은 그대로다. 둘째가 실패해도 알리지 않는다(위 예외) |
| 다시 시도 | 첫 단계부터 다시 부른다 |

#### F-05 접근성과 반응형

| | |
| --- | --- |
| 저장소 | `yuno110/sp-frontend` |
| 의존 | `F-01`~`F-04` (화면이 바뀐 뒤에 잰다. `F-02` 가 로그인 상태를 만드는 방식을 바꿔 테스트 준비가 달라진다) |
| 참조 | `sp-frontend/CLAUDE.md` 「제품으로서 비어 있는 것」 |

**프로덕션 빌드를 백엔드 없이 잰다.** `vite preview` 로 띄운 빌드에 브라우저 테스트가 API 를 스텁으로 응답시킨다 — 개발 서버를 재면 개발 전용 표시가 검사에 섞이고, 빌드를 재면 같은 스텁으로 **CSP 위반**도 함께 본다. 세 서비스를 띄우지 않으므로 이 PC 의 메모리 부담이 작다.

**산출물**
- Playwright(jworksuite6 이 쓴다)와 **axe-core**(`@axe-core/playwright`)를 들인다
- `vite preview` 를 **3000 번**에 띄우게 설정한다 — 세 서비스의 CORS 오리진이 그 주소이고 `F-06` 이 같은 설정을 쓴다. preview 는 개발 서버의 포트를 물려받지 않는다
- 검사가 찾은 것을 고친다
- 부채 목록에서 해당 줄을 지운다

**완료 기준**
- [ ] **개발 전용이 아닌 모든 라우트**에서 axe-core 의 serious·critical 위반이 0건이다
- [ ] 360px 폭에서 **모든 라우트에 가로 스크롤이 없다** — 문서뿐 아니라 **스크롤 컨테이너**(본문을 감싼 영역)도 잰다. 본문이 넘치면 문서가 아니라 그 안에서 스크롤된다
- [ ] 가입·로그인·글 작성을 **키보드만으로** 끝낼 수 있다. Tab 으로 포커스를 옮긴 요소의 `outline`·`box-shadow` 계산값이 **포커스 전과 달라진다**
- [ ] **어느 라우트에서도 CSP 위반이 콘솔에 나오지 않는다**(`F-02` 가 넘긴 것)
