# 계정·회원 기능 요구사항

담당 서비스: **auth-service** (`yuno110/sp-auth`) + **member-service** (`yuno110/sp-member`)

**요구사항은 사용자가 보는 기능 단위다.** 가입·탈퇴처럼 한 기능이 두 서비스에 걸치므로 문서를 나누지 않는다. 어느 서비스가 구현하는지는 아래 표의 "담당" 열과 [../plan/phase1.md](../plan/phase1.md)의 작업 항목(`AU-xx` / `M-xx`)이 정한다.

서비스 경계의 근거는 [../adr/0012](../adr/0012-auth-as-separate-service.md)다. **계정**(이메일·비밀번호·권한)은 auth, **프로필**(닉네임)은 member가 소유한다.

**담당 열에 서비스가 둘 적힌 기능은 두 서비스에 걸친다** — 화면이 두 서비스를 차례로 부르거나(MR-01·MR-10) 두 번 불러 합친다(MR-07·MR-13). 나머지는 한 서비스 안에서 끝난다.

> **이 문장의 앞 판은 「MR-01·MR-07·MR-10 셋이 두 서비스에 걸친다」 였다.** 1차의 표에 대해 참이었고, 2026-11-11 `D-19` 가 MR-13 을 auth·member 로 나누며 그 수가 낡았다. 걸치는 기능은 표의 담당 열로 센다. **MR-13 의 앞 판은 담당이 member 하나였다** — 계정 목록에 필요한 값(이메일·권한·탈퇴·인증·잠금)이 모두 auth 에 있어 나눴다(§13).

## 2. 입력 검증

| 항목 | 규칙 | 메시지 |
| --- | --- | --- |
| email | 이메일 형식, 최대 100자 | "올바른 이메일 형식이 아닙니다." |
| password | 8~20자, 영문·숫자·특수문자 각 1자 이상. 아래 집합 참고 | "비밀번호는 8~20자의 영문, 숫자, 특수문자 조합이어야 합니다." |
| nickname | 2~10자, 한글/영문/숫자. 아래 범위 참고 | "닉네임은 2~10자여야 합니다." |

검증 실패는 `C001`(400)로 응답하고 `fieldErrors`에 필드별 메시지를 담는다. **`rejectedValue`를 담지 않는다** — 비밀번호 검증 실패 시 평문이 응답에 실린다([../api-contract.md §7](../api-contract.md)).

### 2.0 "이메일 형식"이 무엇인가

**Hibernate Validator의 `@Email` 기본 구현을 쓴다.** 정규식을 직접 쓰지 않는다.

그 구현의 실제 동작을 적어 둔다. 8.0.3으로 측정한 결과이고, **구현자가 놀라는 지점이 셋 있다.**

| 입력 | 판정 |
| --- | --- |
| `user@example.com` | 통과 |
| 로컬 파트 64자 | 통과 |
| **로컬 파트 65자** | **거부** — 전체가 100자 이하여도 거부한다 |
| **`user@example`** (TLD 없음) | **통과** |
| **`사용자@example.com`** (비ASCII 로컬) | **통과** |
| `user@`, `userexample.com`, 공백 포함, `user..name@…` | 거부 |

- **로컬 파트 64자 제한은 `@Email`이 이미 건다.** `@Size(max = 100)`과 별개로 동작하므로 따로 적지 않는다
- **TLD와 비ASCII를 추가로 막지 않는다.** 1차 범위 밖이다 — 막아야 할 요구가 생기면 그때 정본을 고친다. 지금 막으면 YAGNI이고, 국제화 도메인을 쓰는 사용자를 임의로 배제한다

### 2.1 비밀번호의 "특수문자"

```
!"#$%&'()*+,-./:;<=>?@[\]^_`{|}~
```

**ASCII 출력 가능 문자만 허용하고 공백을 금지한다.** 집합을 비워 두면 `[^A-Za-z0-9]`로 읽혀 한글 한 글자도 특수문자로 통과한다 — 틀린 동작은 아니지만 "특수문자"의 통념과 다르고 서비스마다 다르게 구현된다.

세 조건을 각각 1자 이상 요구한다: 영문(`A-Za-z`), 숫자(`0-9`), 위 집합.

### 2.2 닉네임의 "한글"이 무엇인가

**완성형 음절과 호환 자모를 모두 받는다.**

| 범위 | 유니코드 | 예 |
| --- | --- | --- |
| 완성형 음절 | U+AC00–U+D7A3 (`가`–`힣`) | `홍길동` |
| 호환 자모 — 자음 | U+3131–U+314E (`ㄱ`–`ㅎ`) | `ㅋㅋ`, `ㅎㅎ` |
| 호환 자모 — 모음 | U+314F–U+3163 (`ㅏ`–`ㅣ`) | `ㅠㅠ` |

**자모를 받는 이유는 둘이다.** 하나는 `ㅋㅋ`·`ㅎㅎ`·`ㅠㅠ`가 실제로 쓰이는 닉네임이라는 것이다. 다른 하나는 거부 메시지다 — 완성형만 받으면 `ㅋㅋ`가 거부되는데, §2가 항목당 메시지를 하나로 고정했으므로 나가는 문구는 "닉네임은 2~10자여야 합니다."다. **입력이 2자인데 길이를 탓한다.**

**`ㅏㅏ`처럼 모음만으로 된 닉네임도 통과한다.** 받아들이는 비용이다 — 닉네임은 표시 이름이고 식별자가 아니다.

공백과 구두점은 받지 않는다. `닉 네임`·`nick!`은 거부다.

> **메시지 논거는 여기서 멈춘다. 비대칭이라는 것을 적어 둔다.** `nick!`은 5자인데 거부 메시지는 똑같이 "닉네임은 2~10자여야 합니다."다. 같은 논거를 끝까지 밀면 공백·구두점도 받거나 메시지를 둘로 갈라야 한다. **가르지 않는다.** 둘로 가르면 §2의 표가 항목당 메시지 하나라는 모양을 잃고, 입력 하나가 같은 필드에 `fieldErrors` 두 건을 만든다 — `가`는 길이와 문자 집합을 동시에 어긴다(측정값). 그 두 건은 [../api-contract.md §2.3](../api-contract.md)이 **중복 확인 응답**에 정한 "해당 필드 1건"과 어긋난다. **지금은 비용으로 받아들인다.** 자모 허용은 위의 첫째 이유만으로도 선다. 메시지 분리가 필요해지면 §2와 §2.3을 함께 개정한다.

**등록과 중복 확인이 같은 규칙을 쓴다** — [../api-contract.md §2.3](../api-contract.md)이 중복 확인에 생성 규칙을 적용하라고 정하고, 형식 오류에 `available: true`를 돌려주는 것을 금지한다.

> **이 절이 없어서 구현이 범위를 정했다.** M-05 구현 워커가 완성형만 받는 정규식을 쓰고 그 판단을 코드 주석에만 남겼고, 리뷰가 "정본에 없는 값을 정했다"로 올렸다([../plan/phase1.md §2.6](../plan/phase1.md) #1). §2.0·§2.1이 같은 종류의 모호함을 미리 못박아 둔 자리에 **"한글"만 비어 있었다.**

## 3. 비즈니스 규칙

| # | 규칙 | 담당 |
| --- | --- | --- |
| 1 | 탈퇴한 계정(`account.deleted = true`)의 이메일은 재가입에 재사용할 수 없다. 행이 남고 `uk_account_email`이 UNIQUE이므로 자연히 보장된다 | auth |
| 2 | 비밀번호는 어떤 응답에도 포함하지 않는다. 내부 API 응답도 마찬가지다 | auth |
| 3 | **"계정만 있고 프로필이 없는 상태"는 정상이다.** 그 상태에서 로그인·재발급·로그아웃·계정 탈퇴가 모두 가능하다. 글·댓글 작성만 막힌다 | 공통 |
| 4 | 비밀번호 변경·계정 탈퇴 시 Refresh Token을 삭제한다. **두 연산은 한 로컬 트랜잭션이다** | auth |
| 5 | **`account.deleted` 검사는 기능별로 한다.** 로그인·재발급은 **거부**한다 — 검사하지 않으면 탈퇴 계정이 토큰을 계속 갱신한다. `GET`·`PATCH /accounts/me*`는 **404 `AU001`**, `DELETE /accounts/me`는 멱등이므로 **204**다. 결론이 기능마다 다르므로 **한곳에 모아 일괄 거부할 수 없다**([../api-contract.md §2.2](../api-contract.md)의 표) | auth |
| 6 | 프로필의 세 상태(미등록 / 활성 / 탈퇴)를 구분한다. 미등록과 탈퇴를 같은 "없음"으로 처리하면 탈퇴한 프로필이 재생성된다 | member |
| 7 | 프로필 등록은 `accountId` 기준 멱등이다. `account_id`는 **검증된 JWT의 `sub`에서만** 가져온다. 요청 본문의 식별자를 신뢰하지 않는다 | member |
| 8 | 프로필 soft delete 시 `nickname`을 NULL로 비운다. `"탈퇴한 회원"`은 **응답 시 변환이지 저장이 아니다** | member |
| 9 | **로그인은 이메일 단위로 연속 5회 실패하면 15분 잠긴다.** 없는 이메일도 똑같이 잠긴다. 자동으로 풀리고 비밀번호 재설정으로도 풀린다. §12. 1차 판은 「2차 범위다. 1차에서 구현하지 않는다」 였고 2026-11-11 `D-19` 가 설계했다 | auth |
| 10 | 탈퇴 회원의 게시글은 board-service가 스냅샷 닉네임을 그대로 노출한다. 1차에서 board에 알리지 않는다 | 공통 |
| 11 | **이메일 인증 전에는 로그인할 수 없다.** 비밀번호가 맞은 뒤에만 「인증 필요」를 드러낸다. 이 규칙이 생기기 전의 계정(ADMIN seed 포함)은 인증된 것으로 소급한다. §11 (2026-11-11 `D-19`) | auth |
| 12 | **무인증 공개 경로 일부에 IP·이메일 단위 요청 수 제한을 둔다**(429 `C009`). 계정 열거를 막지 못하고 비용만 올린다. 대상·키·응답은 [../security.md §10](../security.md) (2026-11-11 `D-19`) | auth·member |

**폐기된 규칙** — 이전 v2의 규칙 3 "닉네임 변경 시 새 Access Token을 함께 반환한다"는 폐기됐다. JWT Claim에 `nickname`이 없으므로([../api-contract.md §6](../api-contract.md)) 토큰이 낡을 이유가 사라졌다. 근거는 [../adr/0012](../adr/0012-auth-as-separate-service.md) §3이다.

## 4. MR-01 상세 — 가입은 3단계다

```
1. POST /api/v1/accounts     (auth,   무인증)  email, password  -> accountId
     (2차) 커밋 뒤 인증 메일 -> 사용자가 링크를 연다
     POST /api/v1/accounts/email-verification/confirm  (auth, 무인증)  token   <- MR-14, §11.2
2. POST /api/v1/auth/login   (auth,   무인증)  -> accessToken, refreshToken
3. POST /api/v1/members      (member, 인증)    nickname
```

**2026-11-11 `D-19` 부터 1과 2 사이에 이메일 인증이 낀다**(규칙 11, 사용자 결정 — [../plan/phase2.md §5.1](../plan/phase2.md)). **단계 번호는 그대로 둔다.** 인증은 2단계(로그인)의 전제 조건이고 계정도 프로필도 만들지 않는다. 번호를 바꾸면 그 번호를 붙인 자리([../api-contract.md §9.1](../api-contract.md), [../security.md §4](../security.md))가 함께 흔들린다.

**화면은 계정 생성 직후 로그인하지 않는다.** 「메일을 확인하세요」 안내로 끝나고, 사용자가 링크로 인증한 뒤 로그인하면 프로필 등록으로 간다. 1단계의 요청·응답 계약(201, 중복이면 409 `AU002`)은 바뀌지 않는다 — 바뀐 것은 1단계 뒤에 로그인이 될 수 있느냐이다. 계정 생성 뒤 바로 로그인하던 화면의 흐름([../plan/phase2.md](../plan/phase2.md) §7.2 `F-04`)은 그 시점의 계약을 따른 것이다.

**가입은 3단계, 탈퇴는 2단계다.** 로그인이 가입에만 끼기 때문이다 — 탈퇴는 이미 인증된 상태에서 시작한다(§8). 단계 번호는 위 블록의 1·2·3이며 [../api-contract.md §9.1](../api-contract.md)이 1·2·3을 열거하고 [../security.md §4](../security.md)의 흐름도가 "가입 1단계"·"가입 3단계"를 붙인다.

**원자성 논의에서 중요한 것은 단계 수가 아니라 두 DB에 걸친 쓰기가 둘이라는 점이다.** 2단계(로그인)도 쓰기는 한다 — `sp_auth`에 RefreshToken을 남긴다([../security.md §4](../security.md)). 다만 계정도 프로필도 만들지 않으므로 가입의 원자성에는 걸리지 않는다.

**원자적 가입을 요구하지 않는다.** 분산 트랜잭션을 피하는 대신 "계정만 있는 상태"를 정상 상태로 받아들인다(규칙 3).

3단계는 멱등이다. 응답만 유실된 클라이언트가 재시도해도 중복 생성·덮어쓰기가 없다. 상태별 응답은 [../api-contract.md §3](../api-contract.md)에 있다.

**미완료 가입 계정을 정리하지 않는다.** auth는 프로필 존재를 모르므로 스스로 판단할 수 없다. 이메일은 계정 생성 시점에 선점되고 해제되지 않는다. 1차의 알려진 제약이다.

> **2차에도 정리하지 않는다. 다만 선점의 결과가 달라진다**(2026-11-11 `D-19`). 남의 이메일로 계정을 만들면 그 계정은 인증되기 전에는 로그인할 수 없다(규칙 11). 그 메일의 주인은 가입이 409 `AU002` 로 막히지만 **비밀번호 재설정으로 그 계정을 되찾는다** — 재설정 메일은 그 주소로 가고, 재설정 확인이 인증도 채운다(§11.4). 인증되지 않은 채 남은 계정을 지우는 것은 이번 범위 밖이다.
>
> **남는 위험 — 사전 탈취.** 메일의 주인이 그 계정의 인증 메일에서 확인을 누르면 계정이 인증되어, 만든 자가 정한 비밀번호로 로그인되는 계정이 된다. 그래서 인증 메일에 「가입하지 않았다면 이 메일을 무시하세요」 를 적는다(§11.2). 이미 눌렀다면 주인은 위의 재설정으로 비밀번호를 바꿔 되찾는다 — 그 계정의 Refresh Token 이 지워지고, 이미 발급된 Access Token 은 만료까지 남는다(§11.4). 만든 자가 그 사이 계정을 탈퇴시키면 되찾을 수 없고 그 이메일은 다시 쓸 수 없다(§3 규칙 1).

## 5. MR-07 상세 — 내 정보는 두 곳에 있다

| 무엇 | 어디 |
| --- | --- |
| 이메일, 가입일 | `GET /api/v1/accounts/me` (auth) |
| 닉네임 | `GET /api/v1/members/me` (member) |

**member는 이메일을 반환할 수 없다.** 소유하지 않기 때문이다. 화면 하나에 둘 다 필요하면 클라이언트가 두 번 호출한다. member가 auth를 호출해 합치지 않는다 — 호출 방향은 `board → member` 하나뿐이다([../adr/0012](../adr/0012-auth-as-separate-service.md) §1).

`GET /api/v1/members/me`는 **프로필이 없거나 탈퇴했으면 404 `M001`**이다([../api-contract.md §3.1](../api-contract.md)). 프로필이 없으면 오류가 아니라 가입 3단계 미완료를 뜻하고, 클라이언트는 프로필 등록으로 안내한다. 이 응답으로는 둘을 가를 수 없다 — 가르는 것은 `GET /api/v1/members/{accountId}`의 `deleted`다.

## 6. MR-05·MR-06 상세 — 재발급의 경합과 로그아웃

재발급은 **RefreshToken 조회와 `account.deleted` 확인을 같은 트랜잭션에서** 한다. 회전은 조건부 UPDATE(affected rows 확인)로 처리한다.

그렇게 하지 않으면 다음이 성립한다.

```
R1) 재발급:  RefreshToken 조회      -> 존재, 계정 활성
D1) 탈퇴:    account.deleted = true;  RefreshToken 삭제;  COMMIT
R2) 재발급:  옛 행 삭제; 새 행 INSERT;  COMMIT      <- 삭제한 행이 되살아난다
```

R2 이후 탈퇴한 계정에 새 RefreshToken(14일)이 생겨, **"탈퇴 후 최대 30분"이라는 경계가 무너진다.**

### 6.0 만료는 `exp` claim이 판정한다

[../security.md §4](../security.md)가 재발급을 **"서명·만료 검증 + 저장값 일치 확인"** 두 단계로 적었다. 둘의 책임이 다르다.

| 무엇을 보는가 | 어디서 |
| --- | --- |
| 만료 | **Refresh Token의 `exp` claim** |
| 동일성(이 토큰이 이 계정의 현재 세션인가) | `refresh_token.token` 저장값. 유예 안이면 `previous_token` 도(§6.3) |

**`refresh_token.expires_at`은 판정에 읽지 않는다.** 운영 가시성과 2차의 만료 행 정리를 위해 보관하며, 회전 때 함께 갱신한다. `rotated_at` 은 판정에 읽지만 만료가 아니라 **유예의 시작**이다(§6.3). **`expires_at` 을 판정에 쓰면 `exp`와 두 개의 진실이 생긴다** — 어긋날 때 어느 쪽이 맞는지 정할 근거가 없다.

### 6.1 "0행이면 회전 실패"는 JDBC 설정에 의존한다

조건부 UPDATE의 판정이 **드라이버가 found rows를 돌려주는 것**에 기대고 있다. 측정값이다.

```sql
UPDATE refresh_token SET token = :new WHERE account_id = :id AND token = :current
```

| 경우 | MySQL (Connector/J 기본) | H2 |
| --- | --- | --- |
| 값이 바뀌는 회전 | 1 | 1 |
| **값이 같은 회전** | **1** | **1** |
| 저장값과 다른 토큰 | 0 | 0 |
| **값이 같은 회전 + `useAffectedRows=true`** | **0** | — |

**`useAffectedRows=true`를 쓰지 않는다.** 그 설정은 *변경된* 행을 돌려주므로, **같은 값으로 회전할 때 0행이 되어 정당한 재발급이 거부된다.** JDBC URL에 추가하지 않는다([../tech-stack.md §4.3](../tech-stack.md)).

"값이 같은 회전"이 실제로 일어나는 이유는 §6.2다.

### 6.2 같은 초에 발급한 두 토큰은 문자열이 같다 — 1차의 알려진 한계

JWT Claim에 `jti`가 없고 `iat`가 초 단위이므로([../api-contract.md §6](../api-contract.md)), **같은 계정이 같은 초에 두 번 발급받으면 토큰이 완전히 같다.** `exp`도 `iat`에서 유도되므로 같다.

그 1초 안에서는 **"이전 Refresh Token은 무효"가 문자 그대로 성립하지 않는다.** 이전 토큰이 곧 새 토큰이다. 2026-11-11 `D-17` 뒤로는 그 밖에서도 직전 토큰이 회전 뒤 10초 동안 유예를 받는다(§6.3) — 그쪽은 한계가 아니라 정한 규칙이다.

| | |
| --- | --- |
| 보안 영향 | **없다.** 이전 토큰을 가진 자는 새 토큰을 가진 것과 같고, 그는 어차피 그것을 갖고 있었다 |
| 실질 영향 | 거의 발생하지 않는다 — 다만 **근거가 "클라이언트가 없다" 가 아니다**(아래) |
| 테스트 영향 | **있다.** 회전 전후를 비교하는 테스트는 발급 경로로 서로 다른 값을 만들 수 없다 ([../conventions.md §9.2](../conventions.md) 예외) |

> **"재발급하는 클라이언트가 없다" 는 근거를 걷었다.** 2026-10-20 에 프론트엔드가 생겼고([../overview.md §3.3](../overview.md)) 그 화면에는 **손으로 누르는 재발급 버튼**이 있다 — 로그인 직후 1초 안에 누를 수 있다(2026-10-27 부터는 개발 빌드에만 있다, [../plan/phase2.md](../plan/phase2.md) §7.2 `F-01`). 그래서 그 조건은 "없다" 가 아니라 **"하지 않는다"** 였다 — 그때 자동 재발급은 `exp` 경과 뒤에만 일어났다. **2026-10-27 부터는 자동 재발급도 1초 창에 들어갈 수 있다.** 화면이 Access Token 을 메모리에만 두고 새로고침할 때 Refresh Token 으로 다시 받으므로([../plan/phase2.md](../plan/phase2.md) §7.2 `F-02`), 새로고침의 재발급이 직전 발급과 같은 초에 들 수 있다. **그때 그 재발급은 거부되지 않는다** — 값이 같은 회전이고 §6.1 의 표대로 1행이다. **위의 보안 영향은 그대로 없다** — 이 한계가 걸리는 것은 회전 전후를 비교하는 **테스트**이고, 그 줄은 바뀌지 않는다. [plan/phase1.md](../plan/phase1.md) D-08 이 이 자리를 찾았다(그 항목의 리뷰어가 열거 밖에서 집었다).

**1차에서 `jti`를 넣지 않는다.** [../api-contract.md §6](../api-contract.md)의 claim 집합은 세 서비스가 공유하는 계약이고 AU-04·AU-06이 `containsOnlyKeys`로 고정했다. 보안 이득이 없는 변경에 완료된 두 항목을 되돌릴 이유가 없다.

**재검토 조건** — Refresh Token을 저장소 대조 없이 신뢰해야 할 때, 또는 한 계정에 여러 세션(기기별 토큰)을 허용할 때. 그때는 `jti`를 넣거나 Refresh Token을 JWT가 아닌 불투명 난수로 바꾼다 — 후자가 표준에 가깝다. 저장소 대조가 최종 판정이므로 JWT 형식이 주는 이득이 없다.

### 6.3 직전 토큰의 재사용 유예 — 회전 응답을 잃은 클라이언트

**회전이 커밋됐는데 그 응답이 클라이언트에 닿지 않으면 클라이언트는 옛 토큰만 갖는다.** 예: 빠르게 두 번 새로고침하면 첫 페이지의 재발급이 서버에서 회전을 커밋했는데 페이지 이탈로 응답이 버려지고, 둘째 페이지는 `sessionStorage` 의 옛 Refresh Token 을 보낸다. 2026-11-11 `D-17` 전에는 그 요청이 저장값과 달라 `A002` 를 받고 세션이 끝났다. **사용자가 2026-11-11 에 유예를 두기로 정했다**([../plan/phase1.md](../plan/phase1.md) `D-17`).

| 경우 | 결과 |
| --- | --- |
| 제시된 토큰이 저장값과 같다 | 지금처럼 회전한다. 회전이 성공하면 **같은 UPDATE 가** `previous_token` 에 제시된 토큰을, `rotated_at` 에 회전 시각을 넣는다 |
| 저장값과 다르고 `previous_token` 과 같으며, 판정 시각이 `rotated_at` + **10초** 이하다 | **다시 회전하지 않는다.** 200 `TokenResponse` 로 **새 Access Token 과 지금 저장된 Refresh Token(그대로)**을 준다. 계정 활성 검사는 회전과 같다 |
| 그 밖(유예 밖, 어느 쪽과도 다르다, 행이 없다) | `A002`. 사유를 구분해 내보내지 않는 규칙은 그대로다([../api-contract.md §2.1](../api-contract.md)) |

- **유예 응답은 `previous_token`·`rotated_at` 을 바꾸지 않는다.** 그래서 창이 밀리지 않는다 — 유예는 회전 한 번에 10초다
- **로그인은 `previous_token`·`rotated_at` 을 비운다.** 새 세션이므로 옛 세션의 토큰이 유예로 새 세션을 얻지 못한다
- 비밀번호 변경·계정 탈퇴와 행을 지운 로그아웃(§6.4) 뒤에는 행이 없다. **행이 없으면 유예도 없다**
- 직전 토큰은 하나뿐이다. 10초 안에 회전이 두 번 일어나면 그보다 앞의 토큰은 유예를 받지 않는다

**구현이 지킬 요건** — 방법은 구현이 정한다.

- **유예 판정은 최신 커밋 값을 읽는다.** 같은 토큰으로 재발급 두 건이 겹치면 둘째의 조건부 UPDATE 는 첫째의 회전을 보고 0행을 받는다(UPDATE 는 최신 값을 본다 — 첫째가 커밋 전이면 기다린다). 그 뒤의 판정을 MySQL InnoDB 의 REPEATABLE READ 일관 읽기로 하면 **트랜잭션의 첫 일관 읽기 때 정해진 스냅샷**을 본다. 그 읽기가 첫째의 커밋보다 앞섰으면 첫째의 회전이 보이지 않고 둘째가 `A002` 가 된다 — 이 유예가 고치려는 경우가 그대로 남는다. 최신 커밋 값으로 판정하면 판정보다 먼저 커밋된 행 삭제(탈퇴·로그아웃·비밀번호 변경)는 행이 없어 `A002` 이고, §6 머리의 R1/D1/R2 가 지키는 탈퇴 경계가 유예 경로에서도 유지된다
- **이 요건은 테스트 DB(H2)에서 통과하는 것으로 확인되지 않는다.** 실 MySQL 에서 동시 재발급으로 본다
- **판정 시각은 회전 시각을 기록한 것과 같은 앱 시계의 값이고 자르지 않는다.** 그 위에서 유예는 회전부터 10초에서 1마이크로초 미만 짧을 수 있고 앱 시계 기준으로 길어지지 않는다. `rotated_at` 의 정밀도(`DATETIME(6)`)와 저장 방식은 [../domain-model.md §2.2](../domain-model.md)가 적는다

**보안 대가는 [../security.md §4.2](../security.md)가 적는다** — 유예 안에서는 탈취된 직전 토큰도 지금 세션의 토큰을 얻는다.

### 6.4 로그아웃은 제시한 세션의 행만 지운다 (MR-06)

**계정당 1행이므로 행 하나가 세션 하나다**([../domain-model.md §2.2](../domain-model.md)). 2026-11-11 `D-17` 전에는 로그아웃이 Access Token 의 `sub` 로 그 계정의 행을 통째로 지웠다. 같은 계정의 새 로그인이 행을 바꾼 뒤 옛 세션의 로그아웃이 늦게 처리되면 **새 세션의 Refresh Token 이 지워졌다.**

- 로그아웃은 인증(Access Token)을 그대로 요구하고 **본문으로 `refreshToken` 을 받는다**([../api-contract.md §2.1](../api-contract.md))
- 행은 `account_id = sub` 이면서 **저장된 `token` 이나 `previous_token` 이 제시값과 같을 때만** 지운다. 서명은 검증하지 않는다 — 문자열 대조가 판정이다
- **`previous_token` 일치에는 시간 제한이 없다.** 같은 세션 사슬이기 때문이다 — 예: 로그아웃을 보내기 직전에 다른 요청의 재발급이 회전했으면 화면이 가진 토큰이 직전 토큰일 수 있다. 로그인이 `previous_token` 을 비우므로(§6.3) 옛 세션의 토큰은 새 세션의 행에 맞지 않는다
- **대조가 삭제의 조건이다.** 대조한 뒤 따로 지우면 그 사이 커밋된 로그인의 행을 지울 수 있다 — 회전이 조건부 UPDATE 인 것과 같은 이유다
- 맞지 않거나 행이 없으면 **아무것도 하지 않고 204** 다. 멱등은 그대로다
- `refreshToken` 필드가 누락·`null`·빈 문자열이면 **400 `C001`** 이다

## 7. MR-08 상세 — 닉네임 변경

```
PATCH /api/v1/members/me   { "nickname": "새닉네임" }

1. 닉네임 중복 검사 — **자기 행은 제외한다. 기준은 `accountId`다** (M003)
2. member.nickname 갱신
3. 갱신된 프로필 반환
```

**토큰을 반환하지 않는다.** 일반적인 수정 API와 같다.

**중복 검사는 자기 행을 제외한다.** 현재 닉네임을 그대로 보내도 200이다. 제외하지 않으면 사전 검사가 자기 행을 찾아 409 `M003`을 낸다 — 자기가 쓰고 있는 값을 "이미 사용 중"이라고 거부하는 셈이고, 바꾸지 않은 필드를 함께 보내는 평범한 수정 화면이 막힌다. `uk_member_nickname`은 이 경우 깨지지 않는다(같은 행을 같은 값으로 쓴다). 막는 것은 사전 검사뿐이므로 **제외는 사전 검사 쪽에서 해야 한다.**

**제외 기준은 `accountId`다. 값 동일성이 아니다.** 세 스키마의 콜레이션이 `utf8mb4_general_ci`여서([../tech-stack.md §4.1](../tech-stack.md)) **대소문자를 구분하지 않는다.** `abc`를 쥔 사람이 `ABC`로 바꾸면 값은 다른데 조회는 자기 행을 찾는다. `uk_member_nickname`은 같은 행이므로 그 UPDATE를 허용하는데 사전 검사만 409 `M003`을 낸다 — 위 문단이 금지한 것의 변종이다. `accountId`로 제외하면 콜레이션과 무관해진다.

> **이 입력은 정본 테스트 URL로는 만들 수 없다. 그러나 기준은 고정할 수 있다.** H2는 데이터 비교가 대소문자를 구분하고(`IGNORECASE`를 켜지 않았다), [../tech-stack.md §5.3](../tech-stack.md)의 `CASE_INSENSITIVE_IDENTIFIERS`는 **식별자(테이블명)** 에만 적용된다. 그래서 "`ABC`가 자기 행에 걸린다"는 상황 자체는 운영에서만 일어난다.
>
> **하지만 그 상황을 리포지터리 경계에서 주입할 수 있다.** 값 동일성 조회가 `true`를 돌려주게 해 두고 변경이 여전히 성공하는지 보면, `accountId` 기준 구현에서는 통과하고 값 비교 구현에서는 409 `M003`으로 실패한다 — M-08 리뷰가 그 테스트를 만들어 양쪽을 측정했다. **그러므로 이 기준을 지키는 것은 주석이 아니라 그 테스트다.** 다만 올바른 구현에서는 그 스텁이 호출되지 않으므로 **사실상 경계 관측**이고 한 방향으로만 반증 가능하다 — 그 한계는 테스트 자신이 적는다.
>
> 더 충실한 방법은 별도 인메모리 스키마에 `IGNORECASE=TRUE`를 더해 콜레이션을 실제로 비구분으로 만드는 것이다. M-08 리뷰가 만들어 돌려 보았고 동작했다. **그래도 지금 쓰지 않는다** — §5.3이 "이 URL을 그대로 쓴다. `<스키마>`만 서비스별로 바꾼다"로 정했으므로 두 번째 URL 형태를 쓰려면 그 절을 먼저 개정해야 한다. 필요해지면 명시적 결정으로 한다.

**사전 검사와 UPDATE 사이에 타인이 그 닉네임을 등록하면 409 `M003`이다.** [../api-contract.md §2.3](../api-contract.md)이 생성 경로에 정한 것과 같다 — 최종 판정은 UNIQUE 제약이다. **500으로 내보내지 않는다.** 클라이언트가 잘못한 것이 없는데 마지막 그물이 `log.error`를 남겨 흔한 경합이 경보가 된다([../conventions.md §6.1](../conventions.md)의 로그 수준 분리). 다만 **`uk_member_nickname` 위반만 `M003`이고 그 밖의 무결성 위반은 다시 던진다** — M-05에서 전부 `M003`으로 돌린 구현이 서버 결함을 업무 오류로 위장했다.

**탈퇴한 프로필은 수정할 수 없다. 404 `M001`이다**([../api-contract.md §3.1](../api-contract.md)). 조회와 같은 결론이다.

이전 v2는 "새 Access Token을 함께 반환"하도록 요구했다. Claim에 `nickname`이 있어서 낡을 수 있었기 때문이다. 이제 Claim에 없으므로 **요구 자체가 소멸했다.** member는 개인키를 갖지 않으므로 토큰을 발급할 수도 없다.

닉네임 변경이 과거 게시글에 반영되지 않는 것은 여전히 **의도된 동작**이다([board.md §3](board.md) 규칙 4, [../adr/0003](../adr/0003-writer-snapshot.md)).

## 8. MR-10 상세 — 탈퇴는 2단계다. 계정이 먼저다

```
1. DELETE /api/v1/accounts/me   (auth)    비밀번호 재확인
                                          -> account.deleted = true + RefreshToken 삭제
                                             [한 로컬 트랜잭션]
2. DELETE /api/v1/members/me    (member)  프로필 deleted = true, nickname = NULL
```

둘 다 멱등이다(이미 삭제됐으면 204).

**순서를 바꾸지 않는다.** 프로필을 먼저 지우면 (a) member는 비밀번호를 갖지 않으므로 **재확인이 구조적으로 불가능해지고**, (b) 중간 실패 시 프로필이 비가역으로 파괴된 채 계정은 영구히 살아 있게 된다. 전체 비교는 [../adr/0012](../adr/0012-auth-as-separate-service.md) §5에 있다.

**2단계는 1단계와 같은 로그인의 Access Token으로 수행한다.** 클라이언트의 로그인이 그대로면 지금 토큰이고(기다리는 사이 재발급됐으면 받은 토큰이다 — 1단계가 보낸 토큰은 만료됐을 수 있다), 그 사이 그 로그인이 끝났거나(예: 로그아웃) 다른 로그인으로 바뀌었으면 1단계가 실제로 보낸 토큰이다(1단계가 만료(401 `A003`)로 재발급받아 다시 보냈으면 그때 받은 토큰이다). 다른 로그인의 토큰으로 보내면 그 계정의 프로필이 지워지므로, 그 토큰을 알 수 없으면 2단계를 보내지 않고 탈퇴를 실패로 끝낸다. member는 계정 상태를 모르므로(오프라인 검증) 토큰이 유효한 동안 통과한다.

**탈퇴 완료는 2단계까지다.** 다만 이것은 클라이언트 측 규약이며 서버가 강제하지 못한다. 2단계가 수행되지 않으면 프로필 행이 남아 닉네임이 선점된 채로 남는다. 1차에는 이를 관측·정리하는 수단이 없다(알려진 제약).

## 10. 기본 관리자 계정 — seed가 두 DB에 걸친다

ADMIN은 **계정과 프로필을 모두** 가져야 한다. 두 스키마에 각각 seed를 넣는다.

| 스키마 | 스크립트 | 내용 |
| --- | --- | --- |
| `sp_auth` | `V3__seed_admin_account.sql` | `account` 1행 |
| `sp_member` | `V2__seed_admin_profile.sql` | `member` 1행 |

### 10.1 두 seed가 공유하는 값 — 정본

| 값 | 확정값 |
| --- | --- |
| `account.id` / `member.account_id` | **`1`** |
| `account.email` | **`admin@example.com`** |
| `account.role` | `ADMIN` |
| `member.nickname` | **`관리자`** |
| `created_at` / `updated_at` | **`NOW()`** — seed 적용 시각 |

`NOW()`를 쓰는 이유는 고정 상수를 박으면 "언제 만들어진 계정인가"가 거짓이 되기 때문이다. 두 컬럼은 `NOT NULL`이므로([../domain-model.md §1.1](../domain-model.md)) 생략할 수 없다. seed는 `@CreatedDate` 감사를 거치지 않는다 — JPA가 아니라 SQL이다.

**`account.id`를 AUTO_INCREMENT에 맡기지 않는다.** 두 스키마가 서로를 조회할 수 없으므로 member의 seed가 참조할 값이 결정적이어야 한다. `INSERT INTO account (id, ...) VALUES (1, ...)`처럼 명시한다.

두 seed의 일치는 통합 검증에서 확인한다([../plan/integration.md](../plan/integration.md) I-01).

**ADMIN 은 인증된 계정이다**(2026-11-11 `D-19`). 인증 컬럼(`account.email_verified_at`)을 더하는 마이그레이션이 그 시점의 모든 행을 `created_at` 으로 채우므로 ADMIN seed 도 포함된다([../domain-model.md §7](../domain-model.md)). **`V3` 는 고치지 않는다** — 적용된 마이그레이션이다([../plan/phase1.md §2.4](../plan/phase1.md)). 빈 DB 에서도 `V3` 가 먼저 돌고 소급이 뒤에 돌므로 결과가 같다.

### 10.2 비밀번호 — seed 스크립트에 넣지 않는다

**평문도 해시도 커밋하지 않는다.** 해시를 커밋하면 공개 저장소에 ADMIN 자격증명이 남고, 아무도 교체하지 않은 채 배포될 수 있다.

**Flyway placeholder로 주입한다.**

```sql
-- V3__seed_admin_account.sql
INSERT INTO account (id, email, password, role, deleted, created_at, updated_at)
VALUES (1, 'admin@example.com', '${adminPasswordHash}', 'ADMIN', false, NOW(), NOW());
```

```yaml
# application.yml — 기본값을 두지 않는다
spring:
  flyway:
    placeholders:
      adminPasswordHash: ${ADMIN_PASSWORD_HASH}
```

**YAML만으로는 기동이 실패하지 않는다. 가드가 필요하다.**

`spring.flyway.placeholders`는 `@ConfigurationProperties` 바인딩이고, **Spring은 해석되지 않은 placeholder를 리터럴 문자열로 남긴다**([../tech-stack.md §4.3](../tech-stack.md)이 `DB_PASSWORD`로 설명한 그 동작이다). 따라서 환경변수가 없으면 Flyway는 `"${ADMIN_PASSWORD_HASH}"`라는 **문자열을 값으로 받아** 마이그레이션에 성공하고, `account.password`에 그것이 그대로 저장된다.

실측 결과다.

| 경로 | 결과 |
| --- | --- |
| Flyway에 placeholder를 **아예 주지 않음** | 마이그레이션 실패 — `No value provided for placeholder` |
| **Spring YAML로 주되 환경변수가 없음** | **마이그레이션 성공.** `password = "${ADMIN_PASSWORD_HASH}"` |

> `@Value`는 미해결 placeholder에 `PlaceholderResolutionException`을 던지지만(`JWT_PRIVATE_KEY_LOCATION`이 그렇다), `@ConfigurationProperties` 바인딩은 리터럴을 통과시킨다. **같은 `${}` 문법인데 경로에 따라 동작이 다르다.**

**`FlywayConfigurationCustomizer`로 가드를 둔다.** `migrate()`보다 반드시 먼저 돌고, 값의 출처와 무관하게 Flyway가 실제로 쓸 값을 본다.

```java
@Bean
FlywayConfigurationCustomizer adminPasswordHashValidator() {
	return config -> {
		String hash = config.getPlaceholders().get("adminPasswordHash");
		// 해석되지 않은 placeholder 는 "${ADMIN_PASSWORD_HASH}" 리터럴로 들어온다
		if (!StringUtils.hasText(hash) || hash.startsWith("${")) {
			throw new IllegalStateException("ADMIN_PASSWORD_HASH 가 없다 ...");
		}
	};
}
```

**예외 메시지에 해시를 넣지 않는다**([../conventions.md §8](../conventions.md)).

해시 생성은 `./gradlew bcrypt -Ppassword=...`로 한다([../tech-stack.md §4.2.1](../tech-stack.md)).

- 로컬 해시는 `application-local.yml`에 넣는다 (gitignore 대상)
- **운영 해시는 개발용과 다른 값이어야 한다**
- `member`의 seed는 비밀번호를 갖지 않으므로 placeholder가 필요 없다

#### 테스트 프로파일 — BCrypt 모양을 쓰지 않는다

테스트는 가드를 통과해야 기동되므로 값이 **반드시 있어야 한다.** 그 값을 `src/test/resources/application-test.yml`에 커밋하게 된다.

**BCrypt 모양(`$2a$...`)을 쓰지 않는다.** 실제 자격증명이 아니어도 시크릿 스캐너에 걸리고, 위에서 "해시를 커밋하지 않는다"고 정한 것과 모양이 같아 읽는 사람이 구분할 수 없다.

```yaml
# src/test/resources/application-test.yml
spring:
  flyway:
    placeholders:
      adminPasswordHash: test-not-a-hash
```

가드는 `hasText`와 `"${"`로 시작하는지만 보고 **형식을 보지 않는다.** `account.password`는 `VARCHAR(60) NOT NULL`에 CHECK가 없으므로 짧은 마커가 그대로 들어간다.

**규칙의 범위는 저장소 전체다.** 커밋되는 어떤 파일에도 BCrypt 모양 문자열을 두지 않는다.

**검사할 때 경로를 좁힌다.** 저장소 전체를 `$2[aby]$`로 긁으면 `application-local.yml`의 **실제 ADMIN 해시가 출력에 찍힌다.** 그 파일은 gitignore 되어 있어 규칙 위반은 아니지만, 비밀 값을 로그·보고서·대화에 남기지 않는다. 커밋 대상만 보려면 `git grep` 또는 `--include`로 범위를 준다.

ADMIN seed 값만 막으면 저장소에 "진짜처럼 보이는 것"과 "가짜"가 섞여, 시크릿 스캐너 경보가 뜰 때마다 사람이 하나씩 판별해야 한다. **0건이면 판별이 필요 없다.**

| 필요한 것 | 어떻게 |
| --- | --- |
| 저장·조회만 보는 픽스처 | BCrypt 모양이 아닌 마커 (`test-not-a-hash-...`). 그 테스트는 비밀번호를 맞추지 않는다 |
| **실제 해시가 필요한 테스트** | **런타임에 `PasswordEncoder`로 인코딩한다.** 리터럴을 적지 않는다 |
| `V3`에 해시가 없는지 검색 | 패턴을 문자 클래스(`[aby]`)로 **조립**한다. 리터럴로 적으면 검색 테스트가 자기 파일에 걸린다 |

리터럴 해시를 적는 것보다 런타임 인코딩이 나은 이유는 따로 있다 — 해시는 salt 때문에 매번 다르므로, 리터럴을 적으면 "이 해시가 이 평문에서 나왔다"를 아무도 검증할 수 없다.

**커밋된 픽스처에서 읽은 값의 모양을 되읽지 않는다.** 그 단언은 순환이라 실질 정보가 없다 — 치환 여부는 `"${"`가 없는지로 이미 확인된다.

**런타임에 `PasswordEncoder`가 만든 값에 형식을 단언하는 것은 순환이 아니다.** 오히려 그쪽이 형식을 고정할 자리다 — **애플리케이션의 `PasswordEncoder` 빈**이 만든 해시가 `$2[aby]$10$`로 시작하는지 보면 §1의 `strength = 10`까지 함께 고정된다. 빈의 타입만 확인하는 테스트는 strength를 보지 못한다.

`bcrypt` 태스크의 출력 형식은 **관측으로 확인한다.** 개발 유틸리티이고, JUnit에서 Gradle 서브프로세스를 띄우는 테스트는 무겁고 깨지기 쉽다.

| 항목 | 규칙 |
| --- | --- |
| 모양 | 32바이트 암호학적 난수를 base64url(패딩 없음)로 쓴 문자열. 메일의 링크에 실린다 |
| 저장 | **그 문자열의 SHA-256 만 저장한다.** 원문은 메일 밖에 남지 않는다 |
| 목적 | 이메일 인증(`EMAIL_VERIFICATION`)과 비밀번호 재설정(`PASSWORD_RESET`). 한 목적의 토큰은 다른 목적의 확인에 쓰이지 않는다 |
| 수명 | 발급부터 **인증 24시간, 재설정 30분** |
| 한 번만 | 확인이 그 토큰을 쓴 것으로 바꾼다. 다시 쓰면 무효다 |
| 새 요청 | 같은 계정·같은 목적의 토큰을 새로 만들면 **앞 토큰을 지운다** — 마지막 메일의 링크만 산다 |
| 실패 | 없음·만료·사용됨·목적 다름·탈퇴 계정을 가르지 않고 **400 `AU007` 하나다** |

**구현이 지킬 요건** — 방법은 구현이 정한다.

- **한 번만 쓰는 판정은 조건부 UPDATE 하나다.** 「그 해시·그 목적이고, 쓰이지 않았고, 만료 전」 인 행에 사용 시각을 쓰고 **1행일 때만** 성공이다. 읽어서 확인한 뒤 쓰지 않는다 — 같은 토큰의 동시 확인 둘이 모두 성공한다
- 만료 판정의 시각은 앱 시계(주입한 `Clock`)다. DB 의 `NOW()` 를 쓰지 않는다 — §6.3 의 유예 판정과 같은 선택이다
- 같은 계정·같은 목적의 발급 둘이 겹치면 서로의 「앞 토큰 지우기」를 보지 못해 둘 다 남을 수 있다. **둘 다 같은 메일함으로 가므로 노출이 늘지 않는다** — 받아들인다

### 11.2 MR-14 이메일 인증

| 메일을 보내는 때 | 조건 |
| --- | --- |
| 가입(`POST /api/v1/accounts`) | 계정 INSERT 가 **커밋된 뒤** |
| 재발송(`POST /api/v1/accounts/email-verification`) | 그 이메일의 계정이 **활성이고 아직 인증되지 않았을 때만.** 없거나 탈퇴했거나 이미 인증된 계정이면 보내지 않는다 — **응답은 어느 경우든 202 다** |

**확인**(`POST /api/v1/accounts/email-verification/confirm`, 본문 `token`)은 한 트랜잭션이다.

```
1) 토큰 사용 처리 (§11.1 의 조건부 UPDATE)          0행이면 400 AU007
2) 그 계정이 탈퇴했으면 되돌린다                    400 AU007 — 토큰 오류와 같은 응답
3) email_verified_at 이 NULL 이면 지금 시각으로 채운다. 이미 인증됐으면 그대로 둔다
<- 204
```

- **확인은 로그인하지 않는다.** 토큰을 주지 않는다 — 화면이 로그인으로 안내한다
- **인증 메일은 「가입하지 않았다면 이 메일을 무시하세요」 를 적는다.** 남이 그 주소로 만든 계정을 주인이 인증해 주지 않게 한다(§4)
- **확인은 무인증이다.** 링크를 연 브라우저가 로그인되어 있지 않아도 된다
- 이미 쓴 링크를 다시 열면 `AU007` 이다. 화면은 「이미 인증했다면 로그인하라」 를 함께 보인다

### 11.3 MR-15 비밀번호 재설정 요청

`POST /api/v1/accounts/password-reset`(본문 `email`)은 **언제나 202 다** — 입력 형식 오류(400 `C001`)와 요청 수 제한(429 `C009`)만 예외다.

| 그 이메일의 계정 | 메일 |
| --- | --- |
| 활성, 인증됨 | 재설정 메일 |
| 활성, 미인증 | 재설정 메일 — 확인이 인증도 채운다(§11.4) |
| 탈퇴 | 보내지 않는다 |
| 없음 | 보내지 않는다 |

- **요청을 받은 스레드는 계정을 조회하지 않는다.** 입력 검증과 요청 수 제한을 지나면 발급 작업을 넘기고 202 를 돌려준다. 계정 조회·토큰 발급·메일은 그 작업이 한다(§11.5). 그래서 응답 시간이 계정의 유무로 갈리지 않는다([../security.md §12](../security.md)). **재발송(§11.2)도 같은 모양이다**
- **메일은 계정에 저장된 주소로 보낸다.** 요청에 실린 문자열로 보내지 않는다 — 계정 조회는 `account.email` 의 콜레이션으로 비교해 대소문자를 가리지 않으므로(§7 이 닉네임에서 같은 성질을 적었다) 저장된 것과 다른 표기로도 같은 계정을 찾는다. 요청의 표기로 보내면 콜레이션이 같다고 보는 다른 주소로 링크가 갈 수 있다. 같은 이유로 이메일 키의 요청 수 제한(소문자로 바꾼 문자열, [../security.md §10](../security.md))은 한 계정에 가는 메일 수를 묶지 못한다 — §11.5 의 계정 id 상한이 묶는다
- 요청만으로는 기존 세션·잠금·비밀번호가 바뀌지 않는다 — 바뀌는 것은 확인(§11.4) 때다

### 11.4 MR-16 비밀번호 재설정 확인

`POST /api/v1/accounts/password-reset/confirm`(본문 `token`, `newPassword`) → 204.

`newPassword` 는 §2 의 비밀번호 규칙이다. 위반은 400 `C001`(`fieldErrors` 에 `newPassword`)이고 **토큰을 쓰기 전에** 거른다 — 규칙을 어긴 입력이 링크를 소모하지 않는다.

```
한 로컬 트랜잭션
1) 토큰 사용 처리 (§11.1 의 조건부 UPDATE)          0행이면 400 AU007
2) 그 계정이 탈퇴했으면 되돌린다                    400 AU007
3) 비밀번호를 새 값의 BCrypt 해시로 바꾼다
4) 그 계정의 refresh_token 행을 지운다              <- 비밀번호 변경(§3 규칙 4)과 같다
5) 그 계정 이메일의 로그인 잠금을 푼다              <- §12.2
6) email_verified_at 이 NULL 이면 지금 시각으로 채운다
<- 204
```

- **한 트랜잭션인 이유** — 일부만 커밋되면 비밀번호는 바뀌었는데 옛 Refresh Token 이 14일간 살거나, 토큰은 쓰였는데 비밀번호가 그대로인 상태가 남는다
- **6 이 있는 이유** — 재설정 링크를 연 것이 그 주소를 가졌다는 증명이다. 남의 이메일로 선점된 계정을 메일의 주인이 되찾는 경로다(§4)
- **탈퇴 검사가 같은 트랜잭션인 이유** — 요청과 확인 사이에 탈퇴가 커밋되면 닫힌 행에 쓰기가 닿는다. 닫힌 행에는 쓰지 않는다([../api-contract.md §2.2](../api-contract.md))
- **이미 발급된 Access Token 은 만료까지 남는다** — 비밀번호 변경과 같은 창이다([../security.md §5.3](../security.md))
- **확인은 로그인하지 않는다** — 토큰을 주지 않는다

### 11.5 메일 발송

| 규칙 | 이유 |
| --- | --- |
| **커밋 뒤에 보낸다** | 되돌려진 가입에 메일이 나가지 않는다. 트랜잭션 안에서 원격 호출을 하지 않는다([../architecture.md §3](../architecture.md)) |
| **요청 스레드와 따로 보낸다**(비동기) | SMTP 의 응답 시간이 API 의 응답 시간이 되지 않는다. 재설정·재발송은 응답 시간이 계정 유무로 갈리지 않는다(§11.3) |
| **실패해도 다시 보내지 않는다** | 로그를 남기고 끝낸다. 사용자가 재발송·재설정을 다시 요청한다. 로그에는 토큰·링크·비밀번호를 남기지 않는다 — 계정 id 와 목적, 실패의 종류만 |
| **한 계정에 보내는 수에 상한을 둔다** | 계정 id·목적마다 시간당 3통(인스턴스 메모리). 발급 작업이 계정을 찾은 뒤, 앞 토큰을 지우기 전에 본다. 넘으면 발급·발송하지 않고 WARN 을 남긴다 — 응답은 이미 202 라 계정의 존재와 무관하고, 마지막으로 보낸 링크가 산다. 인스턴스 수만큼 곱해진다([../security.md §10.1](../security.md)) |
| **발송 대기열에 상한을 둔다** | 가득 차면 그 작업을 버리고 WARN 을 남긴다. SMTP 가 느려질 때 메모리가 쌓이지 않는다([../tech-stack.md §4.7](../tech-stack.md)) |
| **링크는 화면의 주소다** | `{FRONTEND_BASE_URL}/verify-email#token=<토큰>`, `{FRONTEND_BASE_URL}/reset-password#token=<토큰>`. 토큰은 fragment(`#`)에 싣고 그 화면이 POST 로 보낸다([../security.md §12](../security.md)). 기준 주소는 설정이고 요청의 `Host` 로 만들지 않는다 |

발급 작업은 자기 트랜잭션에서 계정을 읽고, 계정 id 의 발송 상한을 보고, 앞 토큰을 지우고, 새 토큰을 넣고, **그 트랜잭션이 커밋된 뒤** 메일을 보낸다. 가입은 계정 INSERT 의 커밋 뒤에 그 작업을 넘긴다.

## 12. MR-04 상세 — 로그인 잠금 (2차)

**2026-11-11 `D-19` 가 설계했다.** 사용자가 정한 것은 이메일(소문자 정규화) 단위·연속 5회 실패·15분 잠금·자동 해제와 재설정 해제·401 새 코드다([../plan/phase2.md §5.1](../plan/phase2.md)). 저장 모양과 갱신 문장은 [../domain-model.md §2.5](../domain-model.md), 대가는 [../security.md §11](../security.md)이 적는다.

### 12.1 판정 순서

```
POST /api/v1/auth/login
0) IP 요청 수 제한                        넘으면 429 C009 (security.md §10)
1) 이메일·비밀번호 중 하나가 비었다,      401 AU003. 계정을 조회하지 않고 세지 않는다
   또는 이메일이 100자를 넘는다
2) 계정 조회(활성만) + BCrypt 비교 정확히 1회   계정이 없거나 탈퇴면 더미 해시와 비교한다
3) 잠금 상태를 읽는다                     잠겨 있으면 401 AU005. 비밀번호가 맞든 틀리든 같다. 세지 않는다
4) 계정 없음·탈퇴·비밀번호 불일치          실패를 센다. 이번 실패로 5회가 되거나 그 사이 다른 시도가 잠갔으면 401 AU005, 아니면 401 AU003
5) 비밀번호가 맞고 미인증                  카운터를 0 으로. 403 AU006
6) 성공                                   카운터를 0 으로. 200 TokenResponse
```

- **3 이 2 뒤에 있다.** 잠긴 경로도 BCrypt 를 한 번 한다 — 응답 시간으로 계정의 존재를 드러내지 않는 [../security.md §4.1](../security.md)의 규칙이 이 경로에도 적용된다. **잠금 응답이 비밀번호에 따라 갈리지 않아야 잠긴 동안 추측을 확인하는 수단이 되지 않는다**
- **잠금이 인증 여부보다 먼저다.** 잠긴 동안에는 맞는 비밀번호로도 `AU006` 을 보지 못한다
- **5 가 4 뒤에 있다.** `AU006` 은 비밀번호가 맞은 뒤에만 나온다(§3 규칙 11)
- **키는 입력 이메일의 ASCII 대문자만 소문자로 바꾼 값이다.** 그 밖의 표기는 키 컬럼의 콜레이션이 계정 조회와 같은 기준으로 합친다(§12.2 의 요건). **`Locale` 에 따른 소문자 변환을 쓰지 않는다** — 비ASCII 의 변환은 글자를 바꾸거나 늘릴 수 있어(예: U+0130 `İ` 는 `Locale.ROOT` 에서 `i` + U+0307 이 된다. §2.0 이 비ASCII 를 받는다) 계정 조회가 같은 계정으로 볼 수 있는 입력이 콜레이션도 다르게 보는 키가 되고, 그만큼 한 계정의 카운터가 갈라져 잠금을 피한다. 없는 이메일·탈퇴 계정도 같은 규칙으로 센다 — 없는 이메일이 잠기지 않으면 잠금 여부가 계정의 존재를 알려준다
- **이메일이 100자를 넘으면 계정을 조회하지 않는다** — 401 `AU003` 이고 세지 않는다(1). 키 컬럼의 폭이다 — 키는 입력과 길이가 같다. 저장된 이메일은 100자 이하라 그런 입력이 계정을 찾는 길은 콜레이션이 같게 보는 표기(예: PAD SPACE 콜레이션의 끝 공백, UCA 콜레이션에서 무시되는 문자 — 어느 콜레이션인지는 [../domain-model.md §2.5](../domain-model.md) 대로 `information_schema` 로 확인한다)뿐이고, 그 길로 계정을 찾으면서 세지 않으면 잠금 없이 추측할 수 있다. 판정은 입력의 길이만 보므로 계정의 존재를 드러내지 않는다
- **잠긴 동안의 시도는 세지 않고 잠금을 늘리지 않는다.** 잠긴 뒤 15분이 지나면 풀린다

### 12.2 카운터

| 사건 | 카운터 |
| --- | --- |
| 실패(§12.1 의 4) | +1. **마지막 실패에서 24시간이 지났으면 1부터 다시 센다** |
| 그 실패로 5회가 됐다 | 15분 잠금을 걸고 0 으로 |
| 비밀번호가 맞았다(§12.1 의 5·6) | 0 |
| 비밀번호 재설정 확인(§11.4) | 0, 잠금을 푼다 |
| `PATCH /me/password`·`DELETE /me` 의 `AU004` | **세지 않는다** — 대가는 [../security.md §11](../security.md) |

**「연속」 은 성공·재설정 사이의 실패다.** 24시간 조건은 몇 주에 걸친 띄엄띄엄한 실패가 쌓여 잠기지 않게 하고, 판정이 오래된 행을 지우는 작업의 시점에 기대지 않게 한다 — 지워진 행과 24시간 지난 행이 같은 결과를 낸다.

**구현이 지킬 요건** — 방법은 구현이 정한다.

- **증가는 원자적이다.** `failed_count = failed_count + 1` 의 조건부 UPDATE(행이 없으면 INSERT)다. **읽고 비교한 뒤 쓰지 않는다** — 동시 실패가 증가를 잃으면 5를 넘는 추측이 잠금 없이 지난다
- **5회 판정은 증가와 같은 트랜잭션에서, 증가가 잡은 행 락 아래에서 한다.** 그래야 동시 실패 중 정확히 하나가 잠금을 건다
- **실패의 카운트는 로그인 트랜잭션과 다른 트랜잭션에서 커밋된다.** `login()` 은 `@Transactional` 이고 실패 응답은 예외라 그 트랜잭션은 되돌려진다 — 같은 트랜잭션에서 세면 카운트도 되돌려진다. 예: `REQUIRES_NEW` 를 다른 빈에 둔다 — 같은 클래스 안의 호출은 프록시를 지나지 않아 전파 설정이 먹지 않는다. **미인증의 맞는 비밀번호(§12.1 의 5)가 카운터를 0 으로 하는 것도 같다** — `AU006` 도 예외라 로그인 트랜잭션과 함께 되돌려진다
- **잠금 판정(§12.1 의 3)은 최신 커밋 값을 읽는다.** 로그인 트랜잭션이 BCrypt 전에 연 일관 읽기 스냅샷으로 읽으면 그 사이 커밋된 잠금을 보지 못한다 — §6.3 의 유예 판정과 같은 문제다
- 판정 시각은 앱 시계(주입한 `Clock`)다
- **이미 판정을 지난 요청은 그 뒤에 커밋된 잠금에 막히지 않는다.** 그래서 동시에 판정을 지나는 시도는 5회를 넘겨 평가될 수 있고, 그 수는 IP 요청 수 제한이 묶는다. 카운터 자체는 하나도 잃지 않아야 한다 — **동시 실패에서 카운터와 잠금이 시도 수와 맞는지는 실 MySQL 측정 대상이다**([../plan/phase2.md §5.4](../plan/phase2.md))
- **키의 동치는 계정 조회와 같아야 한다.** 계정 조회는 `account.email` 의 콜레이션으로 비교해 대소문자를 가리지 않는다. 키의 소문자 변환은 ASCII 대소문자만 맞추므로(§12.1), 키 컬럼을 `account.email` 과 같은 콜레이션으로 두어 UNIQUE 가 계정 조회와 같은 기준으로 키를 합치게 한다([../domain-model.md §2.5](../domain-model.md)). 대소문자 밖에서 콜레이션이 같다고 보는 표기(콜레이션에 따라 악센트·끝 공백 등)가 키를 가르지 않는지는 **실 MySQL 측정 대상이다** — H2 는 데이터를 대소문자를 구분해 비교한다(§7 의 블록인용, [../plan/phase2.md §5.4](../plan/phase2.md))

## 13. MR-13 상세 — 회원 목록 (ADMIN, 2차)

**2026-11-11 `D-19` 가 설계했다.** 계정 목록은 auth, 닉네임은 member 에 있다.

```
1. GET /api/v1/accounts?page=&size=&sort=&email=&role=&deleted=   (auth,   ADMIN)  -> 계정 한 페이지
2. GET /api/v1/members?accountIds=<1 의 id 들>                     (member, ADMIN)  -> 그 계정들의 프로필
   화면이 accountId 로 합친다
```

- **화면이 두 번 부른다.** MR-07(§5)과 같은 이유다 — member 가 auth 를 부르지 않는다. 호출 방향은 `board → member` 하나다([../adr/0012](../adr/0012-auth-as-separate-service.md) §1)
- 계정에 프로필이 없으면(가입 3단계 미완료) 2의 결과에 그 id 가 없다 — 화면이 「프로필 없음」 으로 그린다
- **닉네임 검색은 범위 밖이다.** 닉네임은 member 에, 계정의 페이징은 auth 에 있어 한쪽에서 거른 결과로 다른 쪽을 페이징할 수 없다
- **ADMIN 판정은 각 서비스의 Service 계층이 Claim 의 `role` 값으로 한다(auth 는 enum, member 는 문자열).** 아니면 403 `A004` 다([../security.md §5.1](../security.md))
- 1과 2 사이에 닉네임 변경·탈퇴가 커밋되면 화면은 두 시점의 값을 합친다 — 두 서비스에 걸친 읽기라 한 시점이 아니다. 관리 화면의 표시로 받아들인다
- **2가 주는 값은 공개 조회와 같다.** 닉네임·가입일·탈퇴 여부는 `GET /api/v1/members/{accountId}` 가 누구에게나 한 건씩 준다([../api-contract.md §3.1](../api-contract.md)). ADMIN 으로 묶는 것은 개인정보 보호가 아니라 일괄 조회를 공개 경로로 열지 않는 것이다

요청·응답은 [../api-contract.md §2.5](../api-contract.md)·§3.2 가 적는다.
