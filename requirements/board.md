## 3. 작성자 정보 처리 — 핵심 규칙

작성자 닉네임은 member-service 소유 데이터이므로 **DB 조인이 불가능하다.** 작성 시점의 값을 복제 저장한다.

**`writer_id`는 JWT Claim에서, `writer_nickname`은 member의 내부 API에서 얻는다.** JWT Claim에 `nickname`이 없기 때문이다([../adr/0012](../adr/0012-auth-as-separate-service.md) §3).

```
POST /api/v1/posts
  JWT Claim { sub: "3", role: "USER" }
    1) POST /internal/v1/members/bulk  { accountIds: [3] }     <- 트랜잭션 밖
       -> 200 { members: [{ accountId: 3, nickname: "홍길동", deleted: false }] }
    2) BEGIN
       INSERT INTO post (writer_id, writer_nickname, ...) VALUES (3, '홍길동', ...)
       COMMIT
```

| 규칙 | 내용 |
| --- | --- |
| 1 | `writer_id`는 **검증된 JWT의 `sub`에서만** 가져온다. 요청 본문에서 받지 않는다 |
| 2 | `writer_nickname`은 **내부 API 응답에서만** 가져온다. 요청 본문의 닉네임을 신뢰하지 않는다 |
| 3 | **조회 키도 JWT의 `sub`다.** 본문의 `writerId`로 조회하지 않는다 |
| 4 | `writer_id`에 FK 제약을 걸지 않는다 |
| 5 | `sp_member`·`sp_auth`를 조회하지 않는다. 같은 MySQL 인스턴스에 있어도 크로스 스키마 조인 금지 |
| 6 | 닉네임 변경이 과거 글에 반영되지 않는 것은 **의도된 동작**이다. 1차에서 해결하지 않는다 |
| 7 | **수정 시 스냅샷을 갱신하지 않는다.** 작성 당시 표시를 보존한다. 그래서 수정 경로는 member를 호출하지 않는다 |
| 8 | 원격 호출은 **DB 트랜잭션 밖에서 먼저** 한다([../architecture.md §5](../architecture.md)) |

배경과 대안 비교는 [../adr/0003-writer-snapshot.md](../adr/0003-writer-snapshot.md)에 있다. 취득 경로가 바뀐 이유는 [../adr/0012](../adr/0012-auth-as-separate-service.md) §6이다. 2차 해소 방안은 [../adr/0010-kafka-for-nickname-sync.md](../adr/0010-kafka-for-nickname-sync.md)를 본다.

### 3.0 프로필이 없으면 쓸 수 없다

**활성 프로필이 있어야 글·댓글을 생성할 수 있다.** 계정만 만들고 프로필을 등록하지 않은 사용자는 `S002`(403)로 거부된다.

실패 판정은 **응답 본문으로만** 한다. HTTP 404를 "프로필 없음"으로 해석하지 않는다 — 경로 오설정이나 내부 API 키 거부가 업무 오류로 위장되어 전 사용자의 쓰기가 조용히 멈춘다. 전체 표는 [../api-contract.md §5.1](../api-contract.md)에 있다.

**member 장애 시 새 글·댓글 작성이 중단된다.** 이것은 [../adr/0012](../adr/0012-auth-as-separate-service.md)가 비용으로 수용한 것이다. 조회·수정·삭제는 영향받지 않는다.

**확인과 커밋 사이에 창이 있다.** 프로필 확인 뒤 커밋 전에 탈퇴가 커밋되면 탈퇴한 프로필의 글이 생성될 수 있다. 원격 호출을 트랜잭션 안에 넣을 수 없으므로(규칙 8) 이 창은 닫을 수 없다. **"탈퇴 후 작성 불가"는 보장이 아니라 통상 동작이다.**

### 3.1 부수 효과 — 작성자 검색이 가능하다

`writer_nickname`이 `sp_board`에 있으므로 작성자 닉네임 검색(P-03의 `searchType=WRITER`)을 로컬 `LIKE`로 처리한다. member-service 호출이 필요 없다.

## 4. 입력 검증

| 항목 | 규칙 |
| --- | --- |
| title | 1~200자, 공백만으로 채울 수 없음 |
| content (게시글) | 1~10,000자 |
| content (댓글) | 1~500자 |
| page | 0 이상 |
| size | 1~50. 초과 시 50으로 절삭 |
| category (작성·수정 본문) | `NOTICE`·`FREE`·`QNA` 중 하나 또는 생략. 생략하면 작성은 `FREE`, 수정은 지금 값을 유지한다(§8) |
| category (목록 쿼리) | 같은 셋 중 하나 또는 생략 |
| parentId (댓글 작성 본문) | 생략하거나 같은 글의 활성 최상위 댓글 id(§12) |
| 첨부 파일 | 요청당 하나. 5MB 이하, JPEG·PNG·GIF·WebP(파일 내용으로 판정), 파일명 1~255자(§11) |

**잘못된 `category` 의 코드는 들어온 자리에 따라 갈린다.** 쿼리 파라미터면 enum 바인딩이 실패해 400 `C002` 이고(`sort` 와 같다), 본문이면 JSON 해석이 실패해 400 `C001` 이다([../conventions.md §6.1](../conventions.md)의 표). 같은 값이 두 코드를 받는 것은 결함이 아니다 — 그 표가 바인딩 실패의 종류로 코드를 가른다.

## 5. 비즈니스 규칙

| # | 규칙 |
| --- | --- |
| 1 | 삭제된 게시글·댓글(`deleted = true`)은 목록·상세에서 제외한다. **예외 — 활성 답글이 있는 삭제된 최상위 댓글은 자리만 남는다**(§12) |
| 2 | 삭제된 댓글은 "삭제된 댓글입니다"로 표시할 수 있도록 행을 남긴다. 그 표시를 쓰는 것이 답글이다(§12) |
| 3 | 게시글 삭제 시 하위 댓글(답글 포함)을 함께 논리 삭제한다. 첨부와 좋아요 행은 남긴다(§10·§11) |
| 4 | `comment_count`·`like_count`·`attachment_count`는 음수가 될 수 없다 |
| 5 | 소유자 검증은 Service 계층에서 한다([../security.md §5.1](../security.md)) |
| 6 | ADMIN은 삭제만 가능하고 수정은 불가하다. **첨부 업로드·삭제와 카테고리 변경도 수정이다** — 글 작성자만 한다 |
| 7 | 조회수 어뷰징 방지(동일 사용자 24h 1회)는 **1차에는** 2차 범위였다. 2026-11-11 `D-18` 이 §9 로 설계했다 |
| 8 | 게시글·댓글 **생성**에는 활성 프로필이 필요하다(§3.0). 수정·삭제에는 필요하지 않다. **좋아요와 첨부에도 필요하지 않다** — 작성자 스냅샷을 저장하지 않으므로 member 를 호출하지 않는다(§10·§11) |
| 9 | **공지(`NOTICE`)는 ADMIN 만 쓰고, 공지로 바꾸거나 공지에서 뺀다**(§8) |

## 6. P-03 상세 — 검색

QueryDSL `BooleanExpression`으로 동적 조건을 조합한다.

| searchType | 대상 컬럼 |
| --- | --- |
| `TITLE` | `title` |
| `CONTENT` | `content` |
| `TITLE_CONTENT` | `title` OR `content` |
| `WRITER` | `writer_nickname` |

- `keyword`가 없으면 조건을 적용하지 않는다(전체 목록)
- `searchType`만 있고 `keyword`가 없으면 검증 오류(`C001`)
- **`keyword`만 있고 `searchType`이 없어도 같다** — 400 `C001`. 한쪽을 조용히 무시하지 않는다([../api-contract.md §4.1](../api-contract.md))
- **공백만인 `keyword`는 "없음"으로 정규화한다.** 조합 검증보다 먼저다
- 정렬은 `sort` 화이트리스트 Enum으로만 받는다. 컬럼명 직접 입력 금지

## 7. 권한

[../security.md §5.2](../security.md)의 권한 매트릭스를 따른다. **권한 판정은 JWT Claim의 `sub`·`role`만으로 한다.** 권한을 다른 서비스에 되묻지 않는다.

**작성자 스냅샷 취득(§3)은 권한 판정이 아니다.** 생성 경로에서 member를 호출하는 것은 닉네임을 얻기 위해서이며, 그 부수 효과로 활성 프로필이 확인된다. 수정·삭제·관리자 기능은 Claim만으로 판정하므로 member를 호출하지 않는다.

**검증은 오프라인이다.** 탈퇴나 권한 박탈이 기존 Access Token에 즉시 반영되지 않는다. 최대 노출은 토큰 만료까지이며, 잔여 권한은 그 `role`이 가진 모든 변경 권한이다 — **ADMIN이면 타인 글·댓글 삭제를 포함한다**([../adr/0012](../adr/0012-auth-as-separate-service.md) 포기 목록 1).

## 8. P-11 상세 — 카테고리

**결정은 사용자가 2026-11-11 에 내렸다**([../plan/phase2.md §5.1](../plan/phase2.md)). 값과 응답 모양은 [../api-contract.md §4.1](../api-contract.md)·§4.3 이 정본이다.

| 값 | 뜻 |
| --- | --- |
| `NOTICE` | 공지. **ADMIN 만 쓴다** |
| `FREE` | 자유. **기본값이다** — 작성 때 고르지 않으면 이것이고, 카테고리가 생기기 전의 글도 이것이다 |
| `QNA` | 질문 |

| 규칙 | 내용 |
| --- | --- |
| 작성 | 본문의 `category` 는 선택이다. 생략하면 `FREE` |
| 수정 | 본문의 `category` 는 선택이다. **생략하면 지금 값을 유지한다** — 필수로 두면 카테고리를 모르는 클라이언트의 수정이 깨진다([../adr/0008](../adr/0008-api-versioning.md)의 "필수 요청 파라미터 추가") |
| 공지 권한 — 작성 | `NOTICE` 로 쓰려는 요청자의 `role` 이 `ADMIN` 이 아니면 **403 `P003`** |
| 공지 권한 — 수정 | 카테고리가 **`NOTICE` 로 바뀌거나 `NOTICE` 에서 다른 값으로 바뀔 때** 요청자가 `ADMIN` 이 아니면 **403 `P003`.** 바뀌지 않는 수정(생략하거나 같은 값)은 이 판정을 거치지 않는다 |
| ADMIN 과 남의 글 | **ADMIN 도 남의 글을 공지로 바꿀 수 없다** — 수정은 작성자 본인만이다(§5 규칙 6). ADMIN 이 공지로 쓰는 것은 자기 글이다 |
| 목록 필터 | `GET /api/v1/posts?category=` 는 선택이다. 생략하면 **모든 카테고리**이고 공지도 들어간다. `GET /api/v1/posts/me` 는 이 파라미터를 받지 않는다 — P-08 은 `writer_id` 기준 페이징만 요구한다 |
| 공지 고정 | 전체 목록 첫 페이지 위의 최근 공지는 **화면이 `category=NOTICE` 목록으로 따로 받는다.** 몇 개를 보일지는 화면이 정한다(예: 최근 3개). 서버에 "고정" 상태는 없다 |

**판정 순서.** 작성은 `P003` 을 member 호출보다 **먼저** 판정한다 — Claim 만으로 정해지는 거부에 원격 호출을 쓰지 않는다. 그래서 프로필이 없는 USER 가 공지로 쓰면 `S002` 가 아니라 `P003` 이다. 수정은 [../api-contract.md §4.4](../api-contract.md)의 순서(없는 글 → 소유권)를 지난 뒤에 `P003` 을 본다.

**`P003` 은 `P002` 와 다른 것을 말한다.** `P002` 는 "남의 글" 이고 `P003` 은 "자기 글이지만 공지를 다룰 역할이 아니다" 다.

## 9. P-05 상세 — 조회수 중복 판정 (2차)

**1차의 P-05 는 상세 조회마다 +1 이었다.** 2026-11-11 사용자 결정으로 **같은 조회자·같은 글은 24시간에 한 번만 센다**([../plan/phase2.md §5.1](../plan/phase2.md)). 저장소를 DB 로 정한 이유는 [../adr/0014](../adr/0014-view-count-dedup.md)에 있다.

### 9.1 조회자

| 요청 | 조회자 | 판정 키 |
| --- | --- | --- |
| 유효한 Access Token 이 있다 | 그 계정 | `a:` + `accountId` |
| `Authorization` 이 없다 | 그 접속 | `i:` + `HMAC-SHA256(비밀키, remoteAddr)` 의 소문자 hex |
| 토큰이 있는데 유효하지 않다 | — | **401 그대로다.** 익명으로 낮추지 않는다 |

- **상세 조회는 인증을 선택으로 받는다.** 토큰이 없으면 계정 없이 진행하고, 토큰이 있으면 지금의 검증을 그대로 지난다 — 잘못된 토큰은 필터 체인이 401 로 막고(프레임워크 동작 — 코드 읽기. `permitAll` 경로에 잘못된 토큰을 보내는 테스트는 2026-11-11 에 없었고, 2026-11-12 `D-20` 이 [B-16](../plan/phase2-board.md)의 테스트 대상으로 세웠다), claim 계약 위반(`sub` 누락·`role` 이 열거 밖)은 401 `A002` 다([../tech-stack.md §2.1](../tech-stack.md)의 board 집행 지점). **선택적 인증이 그 검증을 건너뛰는 통로가 되면 안 된다**
- **`remoteAddr` 는 TCP 연결의 상대 주소다.** `X-Forwarded-For` 같은 헤더를 믿지 않는다 — 클라이언트가 마음대로 쓰므로 그것을 믿으면 요청마다 새 조회자가 된다. 그래서 서버가 그 헤더로 `remoteAddr` 를 바꾸는 설정을 켜지 않는다([../tech-stack.md §4.5](../tech-stack.md)). 게이트웨이를 들이면 다시 본다([../adr/0014](../adr/0014-view-count-dedup.md))
- **원 IP 를 저장하지 않는다.** 저장하는 것은 HMAC 이고 비밀키는 환경이 준다. 개인정보 처리는 [../security.md §9](../security.md)가 적는다

### 9.2 판정

**집계는 같은 판정 키·같은 글에 대해 "마지막으로 집계된 조회부터 24시간" 안에 한 번이다.** 24시간 안의 조회는 그 창을 밀지 않는다 — 창을 미는 쪽이면 12시간마다 보는 사람은 영영 다시 세지지 않는다.

| 상황 | 집계 |
| --- | --- |
| 이 키로 이 글을 처음 본다 | +1 |
| 마지막 집계에서 24시간 안이다 | 하지 않는다 |
| 마지막 집계에서 24시간이 지났다 | +1, 그 시각이 새 기준이 된다 |
| 같은 키의 동시 조회 | 한 번만 +1 |

- **작성자 자신의 조회도 센다.** 사용자 결정이 "동일 사용자 24h 1회" 만 정했다
- **같은 사람이 로그인 전과 뒤에 보면 두 조회자다** — 판정 키가 다르다
- **응답의 `viewCount` 는 판정이 반영된 값이다.** 집계되지 않은 조회도 200 이고 그때의 값을 돌려준다. 읽는 시점의 요건은 §9.3
- 시각은 앱 시계(`LocalDateTime.now()`)로 정한다. DB 의 `NOW()` 를 쓰지 않는다 — [../domain-model.md §2.2](../domain-model.md)가 재사용 유예에서 같은 선택을 했다

### 9.3 구현 요건

| 요건 | 이유 |
| --- | --- |
| **판정은 조건부 UPDATE 먼저다.** 조건은 "그 키·그 글의 행이 있고 기준 시각이 24시간 전 이하" 이고, 1행이면 집계한다. **0행이면 그 (글, 판정 키) 행이 있는지 읽는다** — 있으면 24시간 안이므로 집계하지 않고 INSERT 하지 않는다. **없을 때만 INSERT 하고** 성공하면 집계한다. 그 INSERT 의 UNIQUE 충돌은 같은 키의 동시 조회에서만 나고 집계하지 않는다 | 행이 없을 때와 24시간 안일 때를 한 문장으로 가를 수 없다. 24시간 안의 재조회가 통상 경로이므로 그 경로는 읽기로 가르고 충돌을 내지 않는다. 경합의 최종 판정은 UNIQUE 제약이다 |
| **집계될 때만 `view_count` 를 좁은 UPDATE 로 +1 한다.** 그 +1 도 판정 트랜잭션 안이다 | 1차 B-11 이 전체 컬럼 UPDATE 의 소실 갱신을 고친 수단이다([../domain-model.md §6](../domain-model.md)) |
| **UNIQUE 충돌이 상세 조회를 500 으로 만들지 않는다** | 충돌은 정상 결과("이미 셌다")다. 그런데 JPA 에서 제약 위반 예외가 트랜잭션을 rollback-only 로 만들면 응답 직전의 커밋이 실패한다. 판정을 상세 조회와 **다른 트랜잭션**에 두면 충돌한 판정 트랜잭션은 쓴 것이 없으므로 되돌려도 잃는 것이 없다 — 수단은 구현이 고르되, 충돌 뒤에 200 이 나가는 것을 테스트가 본다 |
| **응답의 `viewCount` 는 판정 커밋 뒤에 시작된 읽기에서 얻는다**(예: 판정 트랜잭션을 상세 읽기 트랜잭션보다 먼저 끝낸다). 판정 전에 연 스냅샷에서 읽지 않는다 | MySQL 의 기본 격리(반복 읽기)에서는 트랜잭션의 첫 읽기가 스냅샷을 정하므로, 판정 전에 읽기를 시작한 트랜잭션은 판정이 커밋한 +1 을 보지 못한다. H2 의 기본 격리 수준은 확인 필요다 — MySQL 과 다르면 H2 테스트가 이것을 잡지 못한다. 실 MySQL 측정 대상이다([../plan/phase2.md §5.4](../plan/phase2.md)) |
| **`INSERT IGNORE`·`ON DUPLICATE KEY UPDATE` 로 판정하지 않는다.** 쓰려면 실 MySQL 측정을 먼저 한다 | 둘 다 영향 행 수로 결과를 읽어야 하는데 그 값이 H2 와 MySQL 에서 같다는 근거가 없다(MySQL 은 `ON DUPLICATE KEY UPDATE` 에서 갱신된 행을 2 로 센다). 테스트(H2)가 녹색인데 운영의 판정이 틀릴 수 있다 |
| **판정 행에 FK 를 두지 않는다**([../domain-model.md §4.5](../domain-model.md)) | FK 검사의 공유 락을 잡은 뒤 같은 `post` 행에 좁은 UPDATE 의 배타 락을 요청하면, 같은 글을 동시에 본 두 트랜잭션이 서로를 기다릴 것으로 본다(승격 교착, 추정) |
| **오래된 판정 행을 주기적으로 지운다** | 기준 시각이 24시간을 넘은 행은 없는 행과 판정이 같다 — 다음 조회는 어느 쪽이든 +1 이다. 그래서 지워도 결과가 바뀌지 않고, 지우지 않으면 행이 조회자·글 쌍마다 쌓인다. 주기와 설정은 [../tech-stack.md §4.5](../tech-stack.md) |

> **경합의 UNIQUE 충돌이 남기는 로그도 측정 대상이다.** 충돌은 정상 결과인데 Hibernate 가 그 SQL 예외를 ERROR 로 로그할 수 있다(추정). 그러면 [../conventions.md §6.1](../conventions.md)의 「마지막 그물만 `error`」 와 어긋나 정상 경합이 ERROR 경보가 되고, 그것을 피하려고 로그를 통째로 끄면 진짜 제약 위반이 조용해진다([../AGENTS.md](../AGENTS.md) 불변식 9). 실제 로그 수준을 재고 그 결과로 다룬다([../plan/phase2.md §5.4](../plan/phase2.md)).

> **판정 순서가 만드는 락은 측정 대상이다.** MySQL 의 반복 읽기 격리에서 **없는 행을 찾는 UPDATE 는 간격 락**을 잡을 수 있고, 같은 간격에 INSERT 하려는 다른 트랜잭션과 교착할 수 있다 — 같은 글을 **처음** 보는 서로 다른 조회자가 동시에 들어올 때다(추정). 순서를 뒤집어 INSERT 를 먼저 하면 그 교착은 사라지는 대신, 충돌한 INSERT 가 잡는 공유 락 때문에 **같은 조회자**의 동시 조회끼리 교착할 수 있다(추정). 위 표는 오케스트레이터 기본값(UPDATE 먼저)을 적었다. **어느 쪽이 실제로 교착하는지는 실 MySQL 에서 재고**([../plan/phase2.md §5.4](../plan/phase2.md)), 측정이 뒤집으면 순서를 바꾼다 — 판정의 결과(위 §9.2 표)는 순서와 무관하게 같다. 교착이 나면 그 요청은 1차의 교착과 같은 한계로 남는다([../nfr.md §1](../nfr.md)).

> **알려진 한계.** 비로그인 판정은 IP 단위라 **같은 IP 뒤의 여러 사람이 한 조회자**가 된다(예: 사무실·학교의 공용 NAT). 개발 서버의 프록시 모드에서는 비로그인 요청이 모두 그 프록시의 주소로 오므로 **한 조회자**로 보이고, 로컬의 직접 모드도 같은 PC 의 브라우저들이 같은 주소다. 반대로 IP 를 바꾸며 다시 오는 비로그인 조회는 막지 못한다.

> **댓글을 쓴 뒤 화면이 상세를 다시 받아 조회수가 오르던 동작이 사라진다.** 같은 계정의 재조회가 24시간 안이기 때문이다. 1차에는 그 재조회가 매번 +1 이었다.

**형식 판정의 매직 바이트**

| 형식 | 파일 앞부분 | 저장·서빙하는 `Content-Type` |
| --- | --- | --- |
| JPEG | `FF D8 FF` | `image/jpeg` |
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `image/png` |
| GIF | `GIF87a` 또는 `GIF89a` (ASCII) | `image/gif` |
| WebP | 0~3바이트 `RIFF`, 8~11바이트 `WEBP` (ASCII) | `image/webp` |

**매직 바이트는 앞부분만 본다.** 머리만 맞고 나머지가 이미지가 아닌 파일도 통과한다 — 그런 파일은 브라우저가 이미지로 그리지 못할 뿐이고, 서빙이 판정한 이미지 형식과 `nosniff` 로만 나가므로 다른 형식으로 해석되지 않는다([../security.md §8](../security.md)). 형식 판정 라이브러리(예: Tika)를 들이지 않는 것이 결정이다 — 네 형식의 머리는 위 표로 판정된다.

**파일 쓰기와 DB 커밋은 원자적이지 않다.** 파일을 먼저 쓰고, DB 트랜잭션이 실패하면 그 파일을 지운다(best effort). 그래도 지우지 못하거나 그 사이에 프로세스가 죽으면 **어느 행도 가리키지 않는 파일**이 남는다. 첨부 삭제와 글 삭제도 파일을 남긴다. **그런 파일을 정리하는 것은 이번 범위 밖이다** — 남는 용량은 [../nfr.md §4](../nfr.md)가 적는다.

**판정 순서.** 인증(401) → multipart 해석과 크기(`file` 파트 없음 `C001`·`C008`, 핸들러 전에 난다) → 0바이트 파일(400 `C001`) → 없는·삭제된 글(404 `P001`) → 작성자인가(403 `P002`) → 형식(400 `AT002`)·파일명(400 `C001`) → 개수(409 `AT003`, 미리 세어 보든 아니든 이 자리다 — [../domain-model.md §6.2](../domain-model.md)). 삭제는 없는 첨부(404 `AT001`, 그 글이 지워졌어도 같다) → 작성자인가(403 `P002`) 다 — 없는 것이 먼저인 이유는 [../api-contract.md §4.4](../api-contract.md)와 같다.

**확인과 커밋 사이에 창이 있다.** 부모가 활성인지 확인한 뒤 커밋 전에 부모가 지워지면 삭제된 부모 아래에 답글이 생길 수 있다. 그 답글은 활성이므로 부모 자리가 「삭제된 댓글입니다」 로 남는다 — §3.0 의 프로필 창처럼 **"삭제된 댓글에 답글 불가" 는 보장이 아니라 통상 동작이다.** 부모 행을 잠그면 닫을 수 있지만 그 비용을 들일 만한 피해가 아니다. [B-17](../plan/phase2-board.md)(2026-11-12 `D-20` 이 세웠다)이 댓글 삭제를 `post` 먼저로 고치면([domain-model.md §6](../domain-model.md)) 두 경로가 `post` 의 배타 락에서 한 줄로 서므로, 부모 확인을 그 락 뒤의 잠금 읽기로 옮기는 것만으로 닫힌다 — 그때 다시 본다.

> **답글 수에 상한이 없다.** 최상위 댓글 하나에 답글이 많으면 목록 응답이 그만큼 커진다. 사용자 결정이 "답글은 전부 싣는다" 이고 이번 범위는 그대로 둔다 — 크기가 문제가 되면 답글 페이징을 명시적 결정으로 더한다.
