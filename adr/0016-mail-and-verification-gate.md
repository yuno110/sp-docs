# 0016. 메일 발송과 미인증 계정의 로그인 차단

## 상태
accepted (2026-11-11, 사용자 결정. 설계는 `D-19`)

## 맥락

1차에는 이메일 인증도 비밀번호 찾기도 없었다. 가입한 이메일이 그 사람의 것인지 아무도 확인하지 않았고, 비밀번호를 잊으면 계정을 되찾을 길이 없었다. 2026-11-11 사용자가 둘을 2차 범위로 정했다([../plan/phase2.md §5.1](../plan/phase2.md)). 둘 다 **메일을 보내야** 한다 — auth 가 처음으로 서비스 밖의 시스템에 의존한다.

정할 것이 둘이었다. 메일을 어떻게 보내는가, 그리고 미인증 계정에게 무엇을 막는가.

| 미인증 계정에게 막는 것 | 얻는 것 | 치르는 것 |
| --- | --- | --- |
| **로그인** | 판정이 auth 한 곳에 있다. 토큰이 있으면 인증된 계정이다 — 다른 서비스는 아무것도 몰라도 된다 | SMTP 가 멈추면 새 가입자가 로그인하지 못한다. 가입 흐름에 한 단계가 낀다 |
| 글쓰기만 | 가입 직후 둘러볼 수 있다 | **인증 여부를 board·member 가 알아야 한다** — Claim 에 싣거나(토큰 계약 [../api-contract.md §6](../api-contract.md)을 다시 연다) 서비스가 auth 를 물어야 한다(호출 방향 `board → member` 하나를 깬다, [0012](0012-auth-as-separate-service.md)). Claim 에 실으면 인증 뒤에도 옛 토큰이 만료까지 미인증을 말한다. 세 서비스의 검증·인가를 다시 열어야 한다 |

| 발송 방식 후보 | 문제 |
| --- | --- |
| 요청 트랜잭션 안에서 보낸다 | 되돌려진 가입에 메일이 나간다. SMTP 지연이 DB 커넥션을 쥔다 — 트랜잭션 안의 원격 호출을 금지했다([../architecture.md §3](../architecture.md)) |
| 커밋 뒤 요청 스레드에서 보낸다 | SMTP 지연이 응답 시간이 된다. 재설정 요청의 응답 시간이 계정 유무로 갈린다 |
| outbox 테이블 + 재시도 | 메일이 확실히 나간다. 새 테이블·스케줄러·재시도 정책이 생긴다 — 사용자가 재요청할 수 있는 메일에 비해 크다 |
| **커밋 뒤 비동기, 실패는 로그** | 응답과 SMTP 가 떨어진다. 잃은 메일은 사용자가 다시 요청한다 |

## 결정

- **미인증 계정은 로그인할 수 없다.** 비밀번호가 맞은 뒤에만 403 `AU006` 을 준다. 글쓰기만 막는 대안은 Claim 계약과 세 서비스의 검증을 다시 열므로 고르지 않았다 — 사용자 결정이다
- **메일은 auth 가 SMTP 로 보낸다.** 의존성은 `spring-boot-starter-mail` 하나다([../tech-stack.md §3.2](../tech-stack.md))
- **커밋 뒤, 요청 스레드 밖에서 보낸다. 실패해도 다시 보내지 않는다** — 로그를 남기고 사용자가 재발송·재설정을 다시 요청한다([../requirements/member.md §11.5](../requirements/member.md))
- **운영은 환경이 주는 SMTP, 로컬과 실제 서비스 e2e 는 Mailpit 이다.** Mailpit 은 실행 파일 하나로 띄운다 — Docker 를 쓰지 않는 [0005](0005-no-docker-in-mvp.md)를 지킨다([../tech-stack.md §4.7](../tech-stack.md))
- 메일 설정은 기본값이 없고 비면 기동이 실패한다. 링크의 기준 주소는 설정이고 요청의 `Host` 로 만들지 않는다
- **1차의 계정은 인증된 것으로 본다.** 마이그레이션이 `email_verified_at` 을 `created_at` 으로 채운다([../domain-model.md §7](../domain-model.md))

## 결과

- **SMTP 가 멈추면 새 가입자의 활성화와 잠긴·잊은 사용자의 회복이 멈춘다.** API 는 실패하지 않으므로 조용히 멈춘다 — 발송 실패의 로그가 유일한 신호다([../nfr.md §2](../nfr.md))
- 가입 흐름이 바뀐다. 화면은 계정 생성 뒤 자동 로그인하지 않고 「메일을 확인하세요」 를 보인다([../plan/phase2.md §5.3](../plan/phase2.md))
- 메일 링크의 토큰이 자격이 된다 — 통제는 [../security.md §12](../security.md)
- auth 가 바깥 주소 둘(SMTP, 화면의 기준 주소)을 안다. 다른 서비스는 여전히 모른다([../architecture.md §6](../architecture.md))
- 남의 이메일로 선점된 미인증 계정은 이메일의 주인이 재설정으로 되찾는다([0012](0012-auth-as-separate-service.md)의 포기 목록 2 의 블록인용)
- 메일을 잃으면 사용자가 다시 요청해야 한다. 잃은 수는 로그로만 센다

## 재검토 조건

- **메일 유실이 사용자 불편으로 관측되면** — outbox 와 재시도를 들인다
- **미인증 상태로 둘러보기가 요구되면** — 글쓰기만 막는 대안을 다시 본다. 그때 Claim 계약과 세 서비스의 인가를 함께 연다
- **SMTP 제공자가 발송 한도를 두면** — 발송 작업의 계정 id 상한과 요청 수 제한의 이메일 키([../security.md §10](../security.md)·§10.1)를 함께 본다
- **auth 를 여러 인스턴스로 늘리면** — 계정 id 발송 상한이 인스턴스 수만큼 곱해지고([../security.md §10.1](../security.md)) 정리 작업과 함께 실행 위치를 다시 본다
