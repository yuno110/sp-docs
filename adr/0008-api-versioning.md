# 0008. API 경로 버저닝

## 상태
accepted

## 맥락

엔드포인트 경로를 `/posts`로 할지 `/api/v1/posts`로 할지 정해야 했다.

## 결정

**`/api/v1` 접두어를 사용한다.** 내부 API도 `/internal/v1/**`로 같은 규칙을 적용한다.

## 근거

### `/api` — 용도 구분

애플리케이션이 노출하는 것은 API만이 아니다. `/actuator/**`, `/swagger-ui/**`, 정적 리소스가 함께 있다. 접두어가 있으면 Spring Security에서 `/api/**`만 인증 대상으로 묶기 쉽고, 게이트웨이·Nginx 라우팅 규칙이 한 줄로 끝난다.

### `/v1` — 호환성 파괴 변경 대비

배포된 클라이언트가 있는 상태에서 응답 구조를 바꿔야 하는 경우를 가정한다.

```json
// 현재
{ "id": 12, "writerId": 3, "writerNickname": "홍길동" }

// 변경 요구
{ "id": 12, "writer": { "id": 3, "nickname": "홍길동" } }
```

그냥 바꾸면 기존 클라이언트가 깨진다. 웹은 새로고침하면 되지만 **모바일 앱은 사용자가 직접 업데이트해야 하고 하지 않는 사용자가 남는다.** 두 버전을 병행 운영하다가 v1 사용자가 줄면 폐기한다.

**처음부터 넣는 이유**: 나중에 붙이면 `/api/posts`(암묵적 v1)와 `/api/v2/posts`가 뒤섞여 일관성이 깨진다. 처음 넣는 비용은 사실상 0이다.

**MSA에서 더 중요한 이유**: 서비스가 독립 배포되므로 board만 v2로 올리고 member는 v1을 유지하는 부분 진화가 가능하다. 버전 경로가 없으면 두 서비스의 API 변경 시점을 강제로 맞춰야 한다.

## 버전 상향 기준

| 상향 필요 (호환성 파괴) | 상향 불필요 (하위 호환) |
| --- | --- |
| 필드 삭제·이름 변경 | 응답에 필드 추가 |
| 타입 변경 (문자열 → 객체) | 새 엔드포인트 추가 |
| 필수 요청 파라미터 추가 | 선택 파라미터 추가 |
| 응답 구조·의미 변경 | 내부 구현 변경 |

실무에서 v2까지 가는 경우는 드물고 대부분 하위 호환 변경으로 해결된다. `/v1`은 그럼에도 대비해 두는 저비용 보험이다.

> **2026-11-11 `D-18` 이 이 표의 예외를 하나 두었다.** 2차의 댓글 목록([../api-contract.md §4.5](../api-contract.md))은 페이징 단위가 최상위 항목이 되고 `totalElements` 의 뜻이 바뀌며, 삭제된 댓글의 자리가 `writerId`·`writerNickname`·`content` 를 `null` 로 싣는다 — 위 표로는 **응답 구조·의미 변경**이다. 그래도 `/v1` 안에 둔다. 이 표의 근거는 업데이트하지 않는 클라이언트인데, 그때 이 API 를 부르는 클라이언트는 이 변경과 함께 바뀌는 `sp-frontend` 하나였다. **외부 클라이언트나 업데이트하지 않는 클라이언트가 생기면 이 예외를 다시 본다** — 그 뒤의 같은 종류 변경은 위 표를 따른다.
