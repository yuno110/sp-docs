# 0002. 저장소 분리와 문서 전용 저장소

## 상태
accepted

## 맥락

두 서비스를 단일 저장소(monorepo)에 둘지, 저장소를 나눌지 정해야 했다. 초기 검토에서는 1인 개발 규모를 근거로 단일 저장소를 권장했다.

## 결정

**서비스별 저장소로 분리한다.** 문서는 별도의 문서 전용 저장소에 둔다.

| 저장소 | 내용 |
| --- | --- |
| `yuno110/sp-member` | member-service 코드 + `docs/checklist.md` |
| `yuno110/sp-board` | board-service 코드 + `docs/checklist.md` |
| `yuno110/sp-docs` | 정본 문서, 작업 계획 |

## 근거

- 사용자가 이미 두 저장소를 생성하고 푸시했다. 실제 운영 환경에 가까운 구성이다
- MSA의 독립 배포 원칙과 저장소 경계가 일치한다
- **워커 병렬 작업에 유리하다.** member 워커와 board 워커가 서로 다른 저장소에서 작업하므로 충돌 지점이 없다

문서를 별도 저장소로 둔 이유:
- 두 서비스가 정본을 대칭으로 참조할 수 있다. 어느 한쪽에 두면 비대칭이 생긴다
- 두 저장소에 복제하면 코드 복제와 같은 동기화 문제가 문서에 생긴다
- 문서 저장소는 빌드·배포 파이프라인이 없어 추가 비용이 사실상 0이다

## 결과

- 작업 상태(`checklist.md`)를 한 곳에 모을 수 없게 되었다. **항목별로 원본을 하나로 두는 방식**으로 해결한다. M-xx 상태는 member 저장소, B-xx 상태는 board 저장소에 있다([../plan/README.md](../plan/README.md))
- 두 서비스에 걸친 변경(예: JWT Claim 스펙)을 한 커밋으로 묶을 수 없다. 계약 지점을 문서에 먼저 확정하고 양쪽이 따르는 방식으로 대응한다([../api-contract.md §5](../api-contract.md))
- `AGENTS.md`를 두 저장소에 복제해야 한다. 프로젝트 무관한 행동 원칙이라 거의 바뀌지 않아 비용이 낮다
- 워커가 저장소 2~3개를 봐야 한다. 문서 저장소는 읽기 전용이라 부담이 작다

## 재검토 조건

두 서비스에 걸친 변경이 잦아 계약 조율 비용이 커지면 단일 저장소를 재검토한다.
