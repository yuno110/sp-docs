# 0014. 조회수 중복 판정 — DB 테이블과 접속 주소의 HMAC

## 상태
accepted (2026-11-11, 사용자 결정. 설계는 `D-18`)

## 맥락

1차의 조회수는 상세 조회마다 +1 이었다. 새로고침만으로 오른다. 2026-11-11 사용자가 **같은 조회자·같은 글은 24시간에 한 번** 세기로 정했다([../requirements/board.md §9](../requirements/board.md)). 두 가지를 정해야 했다 — 판정 기록을 어디에 두는가, 비로그인 조회자를 무엇으로 가르는가.

| 저장소 후보 | 얻는 것 | 치르는 것 |
| --- | --- | --- |
| Redis(키 만료) | 만료가 저절로 된다. DB 쓰기가 없다 | 새 인프라·의존성. 로컬·테스트에 대역이 필요하다. 집계(`post.view_count`)와 판정이 다른 저장소에 있어 한 트랜잭션이 아니다 |
| **DB 테이블** | 이미 있는 MySQL. UNIQUE 제약이 동시 판정의 최종 심판이 된다. 테스트가 H2 로 돈다 | 상세 조회가 쓰기를 한다. 만료를 직접 지워야 한다 |

| 비로그인 식별 후보 | 문제 |
| --- | --- |
| 쿠키·로컬 저장소의 임의 id | 지우면 새 조회자다. 판정을 클라이언트가 쥔다 |
| 원 IP | 개인정보를 그대로 저장한다 |
| IP 의 해시 | IPv4 는 공간이 작아 전수 대입으로 되돌릴 수 있다 |
| **IP 의 HMAC** | 키 없이는 되돌릴 수 없다. 키를 바꾸면 기존 행이 무의미해진다(대가는 한 번 더 세는 것뿐) |

## 결정

- **판정 기록은 board DB 의 `post_view` 테이블이다**(Redis 를 들이지 않는다). 모양은 [../domain-model.md §4.5](../domain-model.md), 판정 순서와 구현 요건은 [../requirements/board.md §9](../requirements/board.md)
- **로그인 조회자는 `accountId`, 비로그인 조회자는 접속 주소의 HMAC-SHA256** 으로 가른다. 키는 환경이 주고 기본값이 없다([../tech-stack.md §4.5](../tech-stack.md))
- **접속 주소는 TCP 연결의 상대 주소다. `X-Forwarded-For` 를 믿지 않는다** — 게이트웨이가 없는 지금([0009](0009-gateway-deferred.md)) 그 헤더는 클라이언트가 마음대로 쓰는 값이다
- 오래된 판정 행은 주기 작업이 지운다

## 결과

- 상세 조회가 판정 행을 쓴다. 같은 글의 동시 조회가 락을 다툰다 — 교착 가능성과 측정은 [../requirements/board.md §9](../requirements/board.md)
- 같은 NAT 뒤의 비로그인 사용자들이 한 조회자가 된다. 개발 서버의 프록시를 거치면 모든 비로그인 요청이 한 조회자다
- IP 를 바꾸는 비로그인 조회는 막지 못한다 — 어뷰징을 없애는 것이 아니라 새로고침 수준의 부풀림을 막는 것이다
- 판정 키의 개인정보 처리는 [../security.md §9](../security.md)

## 재검토 조건

- **게이트웨이·리버스 프록시를 들일 때** — 모든 요청의 상대 주소가 프록시가 된다. 그때는 신뢰할 프록시를 정하고 그 프록시가 쓴 전달 헤더만 믿는 설정으로 바꿔야 한다
- **Redis 를 다른 이유로 들일 때** — 판정을 옮길지 다시 본다
- **상세 조회의 쓰기가 성능 문제로 측정될 때**([../nfr.md §1](../nfr.md))
