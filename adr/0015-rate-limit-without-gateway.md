# 0015. 게이트웨이 없는 요청 수 제한 — 인스턴스 메모리와 접속 주소

## 상태
accepted (2026-11-11, 사용자 결정과 오케스트레이터 기본값. 설계는 `D-19`)

## 맥락

1차의 `check-email`·`check-nickname` 은 무인증·무제한이었고 그것이 계정 열거를 열어 두었다([../security.md §4.1](../security.md)). 2026-11-11 사용자가 **가입의 409 `AU002` 를 유지하고 IP 단위 요청 수 제한(429)을 건다**고 정했다. 2차의 설계가 메일을 보내는 경로(재설정·재발송)와 로그인 잠금을 더하므로, 메일 폭탄과 여러 이메일에 걸친 로그인 시도도 같은 수단으로 묶어야 했다. 대상·한도는 [../security.md §10](../security.md)이 적는다.

제한을 어디에 두는가가 정할 것이었다.

| 후보 | 얻는 것 | 치르는 것 |
| --- | --- | --- |
| API Gateway 에서 | 한 자리에서 모든 서비스를 센다. 인스턴스 수와 무관하다 | 게이트웨이가 없다 — 2차로 미뤘다([0009](0009-gateway-deferred.md)). 이 결정을 위해 들이기에는 크다 |
| Redis 의 공유 카운터 | 인스턴스가 늘어도 한도가 그대로다 | 새 인프라·의존성. 로컬·테스트에 대역이 필요하다. [0014](0014-view-count-dedup.md)가 같은 이유로 들이지 않았다 |
| 제한 라이브러리(예: Bucket4j) | 토큰 버킷 등 정교한 알고리즘 | 의존성이 하나 는다. 고정 창 하나면 카운터 배열 하나로 충분하다 |
| **서비스 인스턴스의 메모리** | 새 의존성이 없다. 시계를 주입하면 테스트가 창을 움직일 수 있다 | 인스턴스마다 따로 센다. 재기동하면 사라진다 |

키를 무엇으로 하는가도 정해야 했다. 게이트웨이가 없으므로 클라이언트가 서비스에 직접 붙고, `X-Forwarded-For` 는 클라이언트가 마음대로 쓰는 값이다.

## 결정

- **제한은 auth·member 의 인스턴스 메모리에 둔다.** 고정 창, 주입한 `Clock`, **규칙마다 고정 크기의 버킷 카운터** — 키는 기동마다 새로 만든 비밀의 HMAC 으로 버킷을 고른다. 새 의존성을 들이지 않는다([../tech-stack.md §4.6](../tech-stack.md))
- **IP 키는 `request.getRemoteAddr()` 다 — IPv4 는 주소 그대로, IPv6 는 /64 로 묶는다. `X-Forwarded-For` 를 믿지 않는다.** auth·member 도 `server.forward-headers-strategy: none` 이다 — [0014](0014-view-count-dedup.md)와 같은 판단이다
- 넘으면 **429 `C009`** 와 `Retry-After`. `C009` 는 공통 코드다([../api-contract.md §8.1](../api-contract.md))
- **이 제한이 열거를 막지 않고 비용만 올린다는 것을 정본에 적는다**([../security.md §10.1](../security.md))

## 결과

- 인스턴스를 늘리면 한도가 인스턴스 수만큼 곱해진다([../nfr.md §4](../nfr.md))
- 재기동하면 카운터가 사라진다. 배포 직후에는 한도가 비어 있다
- 고정 창의 경계에서 짧은 시간에 한도의 두 배까지 지난다
- 공유 주소 뒤의 정상 사용자가 함께 429 를 받는다. 주소를 여럿 가진 자에게는 한도가 곱해진다
- 메모리는 키 수와 무관하게 고정이다. 같은 버킷에 떨어진 서로 다른 클라이언트는 한도를 나눈다(드문 거짓 양성). 그 규칙의 모든 클라이언트를 막으려면 창마다 버킷 수 × 한도의 요청이 필요하다 — 키를 많이 만드는 것만으로는 막지 못한다([../security.md §10](../security.md))
- **리버스 프록시 뒤에 두면 모든 사용자가 프록시의 주소 하나를 나눈다** — 이 결정은 서비스에 클라이언트가 직접 붙는다는 전제 위에 있다
- 로그인 잠금은 이 결정과 별개로 DB 에 있다 — 인스턴스 수와 무관하다([../domain-model.md §2.5](../domain-model.md))

## 재검토 조건

- **API Gateway 나 리버스 프록시를 들이면** — 제한을 그쪽으로 옮길지 정하고, 신뢰할 프록시를 정해 그 프록시가 붙인 주소만 믿는다. `forward-headers-strategy` 와 [0014](0014-view-count-dedup.md)를 함께 본다
- **auth·member 를 여러 인스턴스로 늘리면** — 곱해진 한도를 받아들일지, 공유 카운터로 옮길지 정한다
- **Redis 를 다른 이유로 들이면** — 카운터를 그리로 옮기는 비용이 작아진다
- **제한이 정상 사용자를 막는 것이 관측되면**(예: 공유 주소의 429, 버킷을 채우는 요청량) — 한도·키·버킷 수를 다시 본다. 그 요청량이 서비스에 닿는 것 자체는 이 제한기가 아니라 게이트웨이·인프라가 다룰 일이다
