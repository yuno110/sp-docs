# 0012. auth를 별도 서비스로 분리

## 상태
accepted — [0006](0006-auth-inside-member-service.md)을 대체한다

## 맥락

[0006](0006-auth-inside-member-service.md)은 auth를 member-service 내부 패키지로 두기로 했다. 근거는 네 가지였다.

1. 이메일·비밀번호·role이 `member` 테이블에 있으므로, 분리하면 **모든 로그인마다** auth → member 동기 호출이 생긴다
2. 회원가입이 분산 트랜잭션이 된다
3. 회원 탈퇴가 한 트랜잭션에 묶이지 못한다
4. 운영 대상이 1.5배가 된다

그 후 사용자가 auth를 별도 서비스로 분리하기로 결정했다. 근거는 **학습 목적**과 **지금이 가장 싸다**는 두 가지다. M-01·B-01(스캐폴딩)만 완료된 시점이라 코드 이전 비용이 사실상 없다.

[0001](0001-msa-adoption.md) 근거 3행이 이미 학습 목적을 MSA 채택의 명시적 근거로 인정하고 있다. 같은 근거를 auth 분리에 적용하는 것은 이 프로젝트의 자기 논리와 모순되지 않는다. 0006의 재검토 조건(소셜 로그인·SSO·외부 IdP)은 아직 발생하지 않았으므로, 이 결정은 **재검토 조건의 충족이 아니라 전제의 변경**에 따른 것이다.

설계안은 두 차례 독립 검토를 받았다. 검토에서 나온 결함은 전부 아래 결정 내용에 반영했다.

## 결정

**auth를 `auth-service`로 분리하여 서비스를 셋으로 한다.** 계정(인증 주체)은 auth가, 프로필(표시 정보)은 member가 소유한다.

## 0006 근거의 정산

해결했다고 주장하지 않는다. 각각의 현재 상태는 이렇다.

| 0006의 근거 | 현재 |
| --- | --- |
| 로그인마다 동기 호출 | **해소.** auth가 email·password·role을 소유하므로 로그인 경로에 member가 없다 |
| 가입이 분산 트랜잭션 | **회피.** 원자적 가입이라는 요구 자체를 포기했다(§4). 대가로 "계정만 있는 상태"를 정상 상태로 운영한다 |
| 탈퇴가 한 트랜잭션에 묶이지 못함 | **미해결.** 2단계 + 멱등 재시도로 피해를 가역적·시간 제한적인 것으로 바꿨을 뿐이다(§5) |
| 운영 대상 1.5배 | **그대로 남는다** |

반대로 0006이 지불하던 비용 중 사라지는 것도 있다.

- 0006 §예외 — `member`가 `auth.repository.RefreshTokenRepository`를 참조하던 **단방향 규칙 위반이 소멸한다.** 비밀번호 변경·탈퇴 시의 토큰 무효화가 전부 auth 내부 연산이 되기 때문이다
- `requirements/member.md` MR-08의 "닉네임 변경 시 새 Access Token 반환" 요구가 **소멸한다.** Claim에 `nickname`이 없으면 토큰이 낡을 이유가 없다(§3)

## 결정 내용

### 1. 서비스와 소유 데이터

| 서비스 | 포트 | 스키마 | 소유 테이블 |
| --- | --- | --- | --- |
| `auth-service` | 8083 | `sp_auth` | `account`, `refresh_token` |
| `member-service` | 8081 | `sp_member` | `member` (프로필) |
| `board-service` | 8082 | `sp_board` | `post`, `comment` |

크로스 스키마 조인과 서비스 간 FK는 여전히 금지다([0001](0001-msa-adoption.md)).

**전역 식별자는 `accountId`다.** auth가 발급하고 세 서비스가 공유한다. `member.account_id`는 `UNIQUE NOT NULL`, `post.writer_id`·`comment.writer_id`는 `accountId`를 논리 참조한다.

호출 방향은 **`board → member` 하나뿐이다.** auth는 다른 서비스를 호출하지 않고, 다른 서비스도 auth를 런타임에 호출하지 않는다. 토큰 검증은 공개키로 오프라인 수행한다.

### 2. 키와 서명

| 서비스 | 보유 키 | 가능한 일 |
| --- | --- | --- |
| auth | 개인키 | 발급·검증 |
| member | 공개키 | 검증만 |
| board | 공개키 | 검증만 |

**공개키 배포 지점이 1곳에서 2곳으로 늘어난다.** member와 board가 각각 `classpath:jwt-public.pem`을 갖는다.

### 3. JWT Claim

`sub`(accountId), `role`, `iss`(`auth-service`), `iat`, `exp`. **`nickname` claim은 없다.**

auth는 닉네임을 소유하지 않으므로 넣을 수 없다. 이것이 [0003](0003-writer-snapshot.md)의 "Claim에서 스냅샷을 얻는다"는 취득 경로를 깬다. 대체 경로는 §6이다. **0003의 목적(조회 경로 원격 호출 0회)은 그대로 유지된다.**

### 4. 가입 — 2단계, 멱등

```
1. POST /api/v1/accounts        (auth,   무인증)   email, password  → accountId
2. POST /api/v1/auth/login      (auth,   무인증)   → accessToken, refreshToken
3. POST /api/v1/members         (member, 인증)     nickname
                                                   account_id는 JWT sub에서만 가져온다
```

**"계정만 있고 프로필이 없는 상태"를 정상 상태로 인정한다.** auth는 프로필 없이도 로그인·재발급·로그아웃·계정 탈퇴를 허용한다.

3단계는 `accountId` 기준으로 멱등이다. 응답만 유실된 클라이언트가 재시도해도 중복 생성이나 덮어쓰기가 일어나지 않는다.

| 기존 상태 | 응답 |
| --- | --- |
| 행 없음 | 201 생성 |
| 프로필 있음, 닉네임 동일 | 200 기존 반환 |
| 프로필 있음, 닉네임 상이 | 409 `M006` |
| 탈퇴한 프로필 | 409 `M007` |

1단계는 `email` UNIQUE이므로 중복 시 409 `AU002`다. 재시도하는 클라이언트는 2단계로 진행하면 된다.

### 5. 탈퇴 — 가입의 역순 2단계, **계정 먼저**

```
1. DELETE /api/v1/accounts/me   (auth)   비밀번호 재확인 → deleted = true
                                         + 해당 계정 RefreshToken 삭제   [한 로컬 트랜잭션]
2. DELETE /api/v1/members/me    (member) 프로필 soft delete
```

둘 다 멱등이다(이미 삭제됐으면 204).

**순서가 결정의 핵심이다.** 분산 트랜잭션을 쓸 수 없으므로 중간 실패를 없앨 수는 없다. 대신 **중간 실패가 안전한 쪽으로 떨어지도록** 순서를 정한다.

| | 계정 먼저 (채택) | 프로필 먼저 (기각) |
| --- | --- | --- |
| 중간 실패 상태 | 계정 삭제, 프로필 살아 있음 | 프로필 삭제, 계정 살아 있음 |
| 비밀번호 재확인 | **파괴적 동작 앞에 있다** | member는 비밀번호가 없으므로 **불가능** |
| 로그인 | 즉시 막힌다 | 영구히 된다 |
| 파괴된 것 | 없다 | 프로필. **복구 불가** |
| 자연 수렴 | AT 만료(30분) 후 완전 잠금 | 없음. 영구히 이 상태 |

프로필 먼저를 택하면 `requirements/member.md` MR-10의 **비밀번호 재확인이 구조적으로 사라진다.** member가 비밀번호를 갖지 않기 때문이다. 그 경우 AccessToken을 탈취한 공격자가 `DELETE /api/v1/members/me` 한 번으로 피해자의 프로필을 비밀번호 없이 비가역으로 파괴할 수 있다. 계정 먼저는 이 경로를 막는다.

**2단계는 1단계에서 이미 받아 둔 AccessToken으로 수행한다.** member는 계정 상태를 모르므로(오프라인 검증) 토큰이 유효한 동안 통과한다. 2단계가 끝내 수행되지 않으면 member DB에 프로필 행이 남지만, 그 계정으로 새 토큰을 얻을 수 없으므로 인증에는 쓰이지 않는다. 남는 실질 영향은 **닉네임이 선점된 채로 남는 것**이며, 이를 수용한다(§8).

**탈퇴 완료의 의미:** 2단계까지 끝나야 완료다. 1단계만 끝난 상태를 "탈퇴 완료"라고 응답하지 않는다. 다만 이것은 **서버 측 보장이 아니라 클라이언트 측 규약**이다. 서버는 클라이언트가 2단계를 완주하는지 강제할 수도 관측할 수도 없다.

### 6. 닉네임 스냅샷 — 쓰기 시 조회

board는 **글·댓글 생성 시에만** member의 내부 API를 호출하고 결과를 스냅샷한다. 조회 경로는 원격 호출이 0회로 유지된다.

- 조회 키는 **검증된 JWT의 `sub`**다. 요청 본문의 `writerId`·`nickname`을 신뢰하지 않는다
- 닉네임의 기준 시점은 **member가 응답한 시점**이다. 게시글 커밋 시점의 최신 닉네임이 아니다
- 원격 호출은 **board DB 트랜잭션 밖에서 먼저** 수행한다(`architecture.md` §5)
- **수정 시 스냅샷을 갱신하지 않는다.** 작성 당시 표시를 보존한다([0003](0003-writer-snapshot.md), `requirements/board.md` §3 규칙 4와 일치)
- 내부 API는 **벌크 하나만** 둔다. 쓰기 경로는 1건짜리 벌크 호출을 한다. 단건 전용 API를 따로 만들지 않는다(`requirements/member.md` §5)

**실패 의미론은 응답 본문으로 판정한다. HTTP 404를 업무 의미로 쓰지 않는다.**

| member 응답 | board 처리 | 응답 |
| --- | --- | --- |
| 200, 결과에 `deleted = false` | 진행 | — |
| 200, 결과에서 제외됨(프로필 미등록) | 업무 오류. 재시도 무의미 | 403 `S002` |
| 200, 결과에 `deleted = true` | 업무 오류. 재시도 무의미 | 403 `S002` |
| 그 밖의 모든 응답 — 4xx, 5xx, 타임아웃, 본문 파싱 실패 | **인프라 오류. 경보 대상** | 503 `S001` |

벌크 API가 "존재하지 않는 id는 결과에서 제외한다"는 기존 계약(`api-contract.md` §4)을 그대로 쓰므로, **404가 업무 의미를 갖지 않는다.** 경로 오설정·내부 API 키 거부·미처리 예외가 전부 마지막 행으로 떨어져 503이 되고, "프로필 없음"으로 위장되지 않는다. 이 성질이 벌크를 고른 이유다.

타임아웃은 `nfr.md` §3의 **connect 1초 / read 3초**를 따른다. 1차에서는 재시도·서킷브레이커를 두지 않는다.

### 7. 프로필 보유가 필요한 동작

| 동작 | 프로필 필요 | member 호출 |
| --- | --- | --- |
| 글·댓글 조회 | 아니오 (공개) | 없음 |
| 글·댓글 **생성** | 예 | **있음** |
| 글·댓글 수정 | 아니오 | 없음 (`writer_id == sub` 확인만) |
| 글·댓글 삭제 | 아니오 | 없음 (`writer_id == sub` 확인만) |
| 관리자 삭제 | 아니오 | 없음 (`role == ADMIN` 확인만) |

수정·삭제가 member에 의존하지 않는 것은 §6의 "수정 시 스냅샷을 갱신하지 않는다"에서 따라온다. **member 장애 시 새 글만 막히고 기존 글의 수정·삭제는 계속 된다.**

### 8. 계정 상태 검사

**auth의 로그인·재발급은 `account.deleted = false`를 검사한다.**

재발급은 RefreshToken 조회와 상태 확인을 같은 트랜잭션에서 하고, 회전은 조건부 UPDATE(affected rows 확인)로 처리한다. 그렇지 않으면 탈퇴와 재발급이 겹칠 때 삭제된 RefreshToken이 되살아나, 탈퇴한 계정이 14일간 토큰을 갱신할 수 있다.

이것은 새 범위가 아니다. `plan/phase1.md` M-06 완료 기준의 "탈퇴 회원은 로그인할 수 없다"가 auth로 이동한 것이다.

## 결과

### 스키마

`member` 테이블에서 `email`·`password`·`role`이 빠지고 `account_id`가 들어온다. `refresh_token`은 auth로 옮겨가고 FK 대상이 `account.id`가 된다.

**`member.nickname`은 NULL을 허용한다.** soft delete 시 NULL로 비운다. `uk_member_nickname`이 UNIQUE이므로, 탈퇴 행이 닉네임을 붙들고 있으면 (a) 그 닉네임이 영구 소각되고 (b) `"탈퇴한 회원"`으로 마스킹해 저장하는 구현에서는 **두 번째 탈퇴가 UNIQUE 위반으로 500이 난다.** 재생성 차단은 `account_id` UNIQUE가 이미 맡고 있으므로 닉네임을 비워도 tombstone은 깨지지 않는다.

**`"탈퇴한 회원"`은 응답 시 변환이지 저장이 아니다.**

### 정면으로 개정되는 규칙

**`architecture.md` §5 금지표의 "board → member 동기 호출을 쓰기 경로에 배치"를 해제한다.** 사유란에 적힌 "member 장애가 게시글 작성 실패로 전파"는 여전히 참이고, §6은 그것을 비용으로 수용한다.

이 금지는 **서비스가 둘일 때만 지킬 수 있던 규칙**이다. 닉네임이 Claim에 있었기 때문이다. Claim에서 빠지면 쓰기 경로에서 닉네임을 얻을 방법은 동기 호출뿐이다. 검토 과정에서 검토한 대안 둘은 모두 기각했다.

| 대안 | 기각 사유 |
| --- | --- |
| member가 auth에 닉네임을 복제하고 Claim에 다시 넣는다 | 복제 상태가 늘고, 이미 발급된 토큰의 닉네임은 갱신되지 않는다. 쓰기 호출 하나를 없애려고 동기화 문제를 들인다 |
| 스냅샷을 포기하고 조회 시 벌크로 해소한다 | 쓰기는 독립해지지만 [0003](0003-writer-snapshot.md)의 목적 자체가 사라진다. `nfr.md` §1이 그 위에 서 있다 |

`plan/integration.md` I-02의 완료 기준 "member 중지 중에도 유효 토큰으로 게시글 작성 → 201"은 **"→ 503 `S001`"로 개정된다.**

### 확인–커밋 사이의 창

§6이 원격 호출을 트랜잭션 밖으로 강제하므로, 프로필 확인 시점과 게시글 커밋 시점 사이에 창이 생긴다. 그 사이에 탈퇴가 커밋되면 **탈퇴한 프로필의 글이 생성될 수 있다.**

이 창은 닫을 수 없다. 닫으려면 원격 호출 결과를 트랜잭션 안에서 재확인해야 하는데 `architecture.md` §5가 그것을 금지한다. **따라서 "탈퇴 후 새 글 작성이 막힌다"는 보장이 아니라 통상 동작이다.** 보장이 필요해지면 2차에서 board 쪽 사후 정리를 건다.

### 다른 ADR에 미치는 영향

- [0003](0003-writer-snapshot.md) — 스냅샷 취득 경로가 Claim에서 내부 API 호출로 바뀐다. 파생 규칙 "닉네임 변경 시 새 토큰 발급"은 폐기된다. 목적과 저장 구조는 유지된다
- [0007](0007-shared-code-policy.md) — 재검토 조건 "서비스가 3개째가 될 때"가 발동한다. 재검토 결과는 0007에 기록한다
- [0010](0010-kafka-for-nickname-sync.md) — 2차 이벤트 키가 `memberId`에서 `accountId`로 바뀐다

### 1차에서 포기하는 것

정직하게 적는다. 아래는 "해결됨"이 아니라 "감수함"이다.

1. **AccessToken 즉시 취소를 보장하지 않는다.** 탈퇴 후 최대 30분(AT 만료)까지 기존 토큰이 서명 검증을 통과한다. 그 사이의 잔여 권한은 **해당 `role`이 가진 모든 변경 권한**이다. 탈퇴자가 ADMIN이면 `security.md` §5.2에 따라 **타인의 글·댓글 삭제를 포함한다.** 즉시 차단이 요구가 되면 2차에서 블랙리스트나 introspection을 도입한다
2. **미완료 가입 계정을 정리하지 않는다.** auth는 프로필 존재를 모르므로 스스로 판단할 수 없다. 이메일은 계정 생성 시점에 선점되고 해제되지 않는다(`requirements/member.md` §3 규칙 1과 같은 방향이다)
3. **탈퇴 2단계가 수행되지 않으면 닉네임이 선점된 채 남는다.** 1차에는 관측·정리 수단이 없다
4. **탈퇴 시 board의 `writer_nickname`을 익명화하지 않는다.** 작성 시점 스냅샷이며 게시글의 일부로 본다(`requirements/member.md` §3 규칙 6, `architecture.md` §4.4와 일치)
5. **비동기 이벤트(outbox·Kafka)를 쓰지 않는다**([0010](0010-kafka-for-nickname-sync.md))

## 재검토 조건

- **탈퇴의 부분 실패가 실제로 관측되면** — 2차 이벤트(0010)로 2단계를 서버가 책임지도록 옮긴다
- **member 장애로 인한 글 작성 중단이 문제가 되면** — 스냅샷 포기(조회 시 벌크 해소)와 이벤트 복제 중 하나를 고른다. 0003의 재검토가 함께 필요하다
- **탈퇴 후 즉시 차단이 요구가 되면** — 토큰 블랙리스트 또는 introspection. 오프라인 검증만으로는 불가능하다
- **서비스가 4개째가 되면** — [0007](0007-shared-code-policy.md)의 공통 코드 복제 정책을 다시 본다
