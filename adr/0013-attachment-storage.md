# 0013. 첨부 파일 저장소 — 인터페이스 뒤의 로컬 디스크

## 상태
accepted (2026-11-11, 사용자 결정. 설계는 `D-18`)

## 맥락

2차 기능 확장에서 게시글에 이미지 첨부를 받는다([../requirements/board.md §11](../requirements/board.md)). 사용자가 올린 바이트를 어딘가에 두고 다시 내줘야 한다. 후보는 셋이다.

| 후보 | 얻는 것 | 치르는 것 |
| --- | --- | --- |
| DB(BLOB) | 행과 파일이 한 트랜잭션이다 | DB 크기·백업·버퍼 풀이 파일 크기를 떠안는다. 서빙이 DB 를 거친다 |
| 로컬 디스크 | 의존성·계정·비용이 없다. 로컬에서 바로 돈다 | 인스턴스마다 디스크가 따로라 수평 확장을 막는다. 파일 쓰기와 DB 커밋이 원자적이지 않다 |
| 객체 저장소(예: S3) | 인스턴스와 무관하다. 용량·내구성을 맡긴다 | 클라우드 계정·자격 증명·SDK 가 들어온다. 로컬·테스트에 대역이 필요하다 |

1차는 로컬 실행이고 컨테이너도 쓰지 않는다([0005](0005-no-docker-in-mvp.md)). board 는 한 인스턴스로 돈다.

## 결정

**저장소 인터페이스를 두고, 지금의 구현은 로컬 디스크 하나다.** 객체 저장소는 아래 재검토 조건에서 다시 본다.

- 서비스 코드는 인터페이스(저장·열기·지우기)만 알고 디스크 경로를 모른다. 패키지는 [../conventions.md §1.3](../conventions.md)의 `attachment/storage`
- 저장 이름은 서버가 만든 UUID 이다. 원본 파일명은 메타데이터로만 DB 에 둔다([../domain-model.md §4.6](../domain-model.md))
- 저장 루트는 환경이 주고 기본값이 없다([../tech-stack.md §4.5](../tech-stack.md))
- 파일을 먼저 쓰고 DB 가 실패하면 지운다(best effort). 지우지 못한 파일과 삭제된 첨부의 파일을 정리하는 것은 범위 밖이다

## 결과

- **board 를 여러 인스턴스로 늘릴 수 없다** — [../architecture.md §2](../architecture.md)의 Stateless 원칙과 [../nfr.md §4](../nfr.md)의 수평 확장에 예외가 생긴다. 지금 board 는 한 인스턴스이므로 실제 제약은 아니지만, 그 전제가 바뀌면 이 결정도 바뀐다
- 어느 행도 가리키지 않는 파일이 쌓일 수 있다. 용량 기준은 [../nfr.md §4](../nfr.md)
- 파일의 백업은 DB 백업에 포함되지 않는다 — 디스크를 따로 백업해야 한다
- 객체 저장소로 옮길 때 바뀌는 것은 인터페이스의 구현과 설정이다. 응답에 URL 을 싣지 않으므로([../api-contract.md §4.7](../api-contract.md)) 클라이언트 계약은 바뀌지 않는다 — 서빙을 저장소의 서명 URL 로 돌리기로 하면 그때 계약이 바뀐다

## 재검토 조건

- **컨테이너 전환** — 컨테이너의 파일시스템은 재시작에 남지 않으므로 볼륨을 붙이거나 이 결정을 바꿔야 한다([0005](0005-no-docker-in-mvp.md))
- **board 를 둘 이상의 인스턴스로 띄울 때**
- **게이트웨이나 CDN 을 들일 때** — 서빙 경로와 캐시 정책([../security.md §8](../security.md))을 함께 본다
