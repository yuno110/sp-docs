# 0004. JWT 서명 알고리즘 RS256

## 상태
accepted

## 맥락

JWT는 header.payload.signature 세 부분이다. payload는 **암호화가 아니라 Base64 인코딩**이므로 누구나 읽을 수 있고, 서명의 목적은 내용을 숨기는 것이 아니라 **위조를 탐지하는 것**이다. 공격자가 `"role":"USER"`를 `"role":"ADMIN"`으로 바꾸면 서명이 맞지 않아 거부된다.

여기서 선택지가 갈린다. **서명을 만드는 열쇠와 검증하는 열쇠가 같아야 하는가?**

member-service가 토큰을 발급하고 board-service가 검증한다. board-service가 검증하려면 무엇을 가져야 하는가.

## 결정

**RS256(비대칭키)을 사용한다.** member-service는 개인키로 서명하고, board-service는 공개키로 검증만 한다.

## 근거

**HS256(대칭키)의 문제**: 같은 비밀키로 서명하고 검증한다. board-service가 검증하려면 동일한 비밀키를 가져야 하는데, 그 키를 가진 쪽은 **토큰을 새로 만들 수도 있다.** 검증 능력과 발급 능력이 분리되지 않는다.

```
1. board-service에 취약점 발생 (사용자 입력을 대량 처리 → 공격면이 넓다)
2. 공격자가 JWT_SECRET 획득
3. { "sub":"1", "role":"ADMIN", "exp":<먼 미래> } 토큰을 직접 생성
4. member-service의 관리자 API 호출
5. 게시판 하나가 뚫렸는데 회원 시스템 전체가 뚫린다
```

MSA로 나눈 목적 중 하나인 사고 격리가 깨진다.

**RS256**은 개인키(서명)와 공개키(검증)가 분리된다. 인감도장과 인영 견본의 관계다. 공개키로는 유효한 서명을 만들 수 없으므로 같은 시나리오에서 피해가 board-service 안에서 멈춘다. **최소 권한 원칙** — board-service에 필요한 능력은 검증뿐이므로 검증만 가능한 열쇠를 준다.

| | HS256 | RS256 (채택) |
| --- | --- | --- |
| board가 갖는 것 | 비밀키 = 발급 권한 포함 | 공개키 = 검증만 |
| board 유출 시 | ADMIN 토큰 위조 → 전체 침해 | 위조 불가 → 국소화 |
| 공개키 Git 커밋 | 불가 | 가능 |
| 서비스 추가 시 | 비밀키 재배포, 유출면 증가 | 공개키만 배포 |

**성능은 판단 기준이 아니다.** RSA는 서명(개인키 연산)이 HMAC보다 느리지만 서명은 로그인·재발급 시에만 일어난다. 요청마다 발생하는 검증(공개키 연산)은 RSA에서도 빠르다. 부하 특성과 알고리즘 특성이 맞고, 실측도 요청당 밀리초 미만이다.

**비용이 작다.** 키 생성 1회(`openssl` 2줄)와 설정 몇 줄이다.

## 결과

- 키를 2개 관리해야 한다. 개인키는 환경변수로만 주입하고 커밋하지 않는다([../security.md §3](../security.md))
- 공개키는 설계상 공개돼도 안전하므로 board-service 리소스에 커밋한다
- **Spring Security 표준 기능을 쓸 수 있게 되었다.** `oauth2-resource-server`가 공개키 기반 검증을 제공하므로 JWT 필터를 직접 만들 필요가 없다 → [0007](0007-shared-code-policy.md)
- `kid` 헤더를 포함해 키 회전에 대비한다
- 2차에 JWKS 엔드포인트(`/.well-known/jwks.json`)로 공개키 자동 배포가 가능하다. RS256이어야 가능한 방식이다
