# 리뷰 정책

## 1. 원칙

**작성자와 리뷰어는 다른 워커여야 한다.** 자기가 쓴 코드를 자기가 승인하지 않는다.

**매 라운드 리뷰 워커를 새로 만든다.** 이전 라운드의 리뷰어를 재사용하지 않는다 — 자기가 지적한 것이 고쳐졌는지만 확인하게 되어 새로 생긴 결함을 놓친다.

재사용을 막으려면 **끝난 워커를 종료해야 한다.** 남겨두면 맥락이 작업 시점에 멈춘 채로 되살아난다([orchestration.md §5.5](orchestration.md)).

리뷰는 **커밋 전에** 한다([dev-workflow.md §1](dev-workflow.md)). 통과하지 못한 코드가 히스토리에 남지 않게 하기 위해서다. PR을 쓰지 않으므로 이 절차가 유일한 게이트다.

| 산출물 | 리뷰 대상 | 통과 조건 |
| --- | --- | --- |
| 구현 | 정본 문서와의 정합, 테스트, 완료 기준 충족 | `APPROVED` |
| 정본 문서 개정 | 결정·범위·계약과의 정합 | `APPROVED` |

## 2. 리뷰 워커에게 주는 것

```
저장소: yuno110/<member|board>
워크트리: <경로>
작업 항목: <ID>

리뷰 대상: git diff --cached (스테이징된 미커밋 변경)
판정 기준: sp-docs/plan/phase1.md 의 <ID> 항목 — 산출물·완료 기준·검증 표
절차: sp-docs/process/review-policy.md
```

**구현 워커의 설명이나 자기평가를 전달하지 않는다.** 리뷰어가 그 서술에 끌려가면 독립 판정이 되지 않는다. 코드와 정본 문서만 보고 판단하게 한다.

2라운드 이상이면 **이전 라운드의 finding 전문**을 함께 준다. 같은 결함이 남아 있는지 확인해야 하기 때문이다.

## 3. 리뷰 워커가 할 일

1. `git diff --cached`로 변경 전체를 본다 (신규 파일 포함)
2. `plan/phase1.md`의 해당 항목에서 **산출물·완료 기준·검증 표**를 읽는다
3. 항목의 "참조" 문서에서 값을 대조한다
4. `./gradlew test`를 **직접 실행**한다. 구현 워커의 보고를 믿지 않는다
5. §4 체크 항목을 확인한다
6. §5 형식으로 판정을 낸다

**리뷰어는 코드를 고치지 않는다.** 발견만 하고 수정은 수정 워커가 한다.

## 4. 체크 항목

- [ ] 완료 기준을 **모두** 충족했는가 (한 줄씩 대조). **충족 방식에 제한이 없다** — 리뷰어의 직접 관측으로도 된다
- [ ] 검증 표의 케이스가 **모두 테스트 코드로** 있는가. **관측으로 대체할 수 없다**

> **통합 항목(`plan/integration.md` I-01~I-05)은 예외다.** 그 검증표는 **실제 프로세스를 내리고 실제 DB에 쓰는 관측**으로만 성립하므로 구성상 테스트 코드가 될 수 없고, [../nfr.md §2](../nfr.md)가 "통합 검증 단계에서 **실제로 서비스를 내리고** 확인한다"로 그 방법을 직접 지시한다. 통합 항목의 리뷰어는 **보고가 참인지 재현**해서 판정한다 — 테스트 코드의 유무로 판정하지 않는다.
>
> 이 예외는 **통합 항목에만** 적용된다. `plan/phase1.md`의 `AU-xx`·`M-xx`·`B-xx`에는 위 항목이 그대로 적용된다(I-02 리뷰가 두 정본의 어긋남을 finding으로 올려 메운 것이다).
- [ ] 테스트가 실제로 통과하는가 (직접 실행해서 확인)
- [ ] `@Disabled`·주석 처리된 테스트가 없는가
- [ ] 단언이 약화되지 않았는가 (예: 값 비교를 `notNull`로 바꾸기)
- [ ] 값이 정본 문서와 일치하는가 (에러 코드, 컬럼명, 엔드포인트, 만료 시간)
- [ ] 산출물 목록 밖의 파일을 건드렸다면 그 이유가 타당한가 (범위 이탈인지, 항목을 끝내는 데 필요했는지)
- [ ] 완료된 항목의 완료 기준을 깨뜨리지 않았는가 ([../plan/phase1.md §2.6](../plan/phase1.md))
- [ ] [../conventions.md](../conventions.md) 위반이 없는가 (Entity `@Setter`, 필드 주입, Entity 노출)
- [ ] [../architecture.md §5](../architecture.md) 금지 사항 위반이 없는가
- [ ] [dev-workflow.md §4](dev-workflow.md)의 금지 사항 위반이 없는가
- [ ] 비밀 값이 스테이징에 포함되지 않았는가 (`private.pem`, `.env`, 하드코딩된 키)
- [ ] 미구현 경로가 조용히 통과하지 않는가 (mock·기본값으로 덮이지 않았는가)

### 4.1 변이 테스트는 반증 도구다. 증명이 아니다

**잡히지 않은 변이는 발견이다. 변이들이 모두 잡혔다는 것은 아무것도 증명하지 않는다.** 이 절의 앞 판은 그 반대를 적었다 — "변이 둘로 증명한다", "각 변이가 적어도 하나의 테스트에 잡히면 충족이다". **AU-08의 리뷰가 변이 하나로 그것을 반증했다.** 아래는 그 실측이다.

#### "한 로컬 트랜잭션"은 행위 관측만으로 확정되지 않는다

`requirements/member.md` §3 규칙 4가 금지하는 결함은 **"한쪽만 반영됨"**이다. 그것을 만드는 변이가 셋 있고, **서로 다른 테스트에 잡힌다.**

| 변이 | 무엇이 깨지나 | 잡는 테스트 |
| --- | --- | --- |
| **A** — `@Transactional` 제거 | 트랜잭션이 아예 없다 | 정상 경로 테스트들. 롤백 테스트는 **못 잡는다** |
| **B** — `@Transactional(noRollbackFor = …)` | 트랜잭션은 있고 원자성만 깨진다 | **롤백 테스트 하나뿐** |
| **C** — 연산마다 자기 `@Transactional` | **독립적으로 커밋되는 트랜잭션 둘** | **아무것도 못 잡는다** |

**C가 핵심이다.** A·B를 모두 잡는 스위트가 C를 통째로 통과시켰다(AU-08에서 191개 전부 통과). 운영에서는 두 번째 쓰기가 실패하면 첫 쓰기만 커밋된 상태가 남는다 — 비밀번호 변경이면 세션만 끊기고 비밀번호는 그대로, **탈퇴면 `deleted = true`가 커밋되고 토큰이 살아남는다.**

**왜 안 잡히나.** 정상 경로는 두 효과가 **여전히 둘 다 일어나므로** 통과한다. 롤백 테스트는 스파이가 가로채는 연산이 이 형태에서 **첫 쓰기**가 되므로 아무것도 커밋되지 않고, 두 단언이 **"한 트랜잭션이어서"가 아니라 "애초에 아무것도 쓰이지 않아서"** 통과한다.

**근본 원인 — "한 트랜잭션"과 "첫 트랜잭션이 롤백된 두 트랜잭션"은 관측상 구별되지 않는다.** 스파이에 실패를 주입하는 방식으로는 이 둘을 가를 수 없다. 측정값이다: 스텁 안에서 실제 DELETE를 실행한 뒤 throw해도 **그 DELETE가 되돌려진다** — `@Transactional` 어드바이스가 스파이 **바깥**에 감기므로 스텁이 이미 트랜잭션 안에서 돌고 있다(`rowsDeleted=1`, `txActive=true`, 다른 커넥션에서 `0`).

#### 그래서 요구하는 것 — 경계를 관측한다

**완료 기준에 "한 로컬 트랜잭션"이 있으면, 트랜잭션 경계 자체를 관측하는 테스트가 있어야 한다.** 행위 단언으로 대체할 수 없다.

| 관측 | 잡는 변이 |
| --- | --- |
| **한 번의 호출에 커밋이 정확히 한 번** (`PlatformTransactionManager` 스파이) | **A** · **C** |
| 실패 주입 시 두 효과가 **둘 다** 미반영 | **B** |

**`status.isNewTransaction()`이 참인 `commit`만 센다.** 필터가 없으면 **올바른 구현도 1을 넘을 수 있다** — `SimpleJpaRepository`의 `readOnly` 조회가 매니저의 `commit`을 함께 지나기 때문이다. AU-08 실측값:

| | 집계 |
| --- | --- |
| 올바른 구현 | **1** |
| 변이 C (연산마다 자기 트랜잭션) | **3** |
| 변이 A | 집계 전에 예외가 난다 (아래 블록인용) — **항목마다 다르다** |

> **"1을 넘는다"가 아니라 "넘을 수 있다"다.** 필터가 필요한 이유는 항목마다 성립하지 않는다 — B-07의 `delete`는 `SimpleJpaRepository` 상속 메서드를 하나도 부르지 않고 파생 쿼리와 `@Query`만 지나므로 **필터를 지워도 올바른 구현의 집계가 1 그대로다**(B-07 리뷰 실측). **그래도 필터는 둔다** — 이 절이 요구하는 형태이고, 조회가 상속 메서드로 바뀌는 순간 필터 없는 테스트는 올바른 구현에서 빨개진다. **다만 "필터가 없으면 1을 넘는다"를 그 자리의 근거로 적지 않는다** — 자기 항목에서 측정하지 않은 주장이 된다([../conventions.md §9.5](../conventions.md)).

**숫자를 예측값으로 쓰지 않는다.** 이 절의 앞 판은 A를 0회, C를 2회로 적었고 **둘 다 틀렸다.** 단언은 "정확히 한 번"에 걸고, 그 외의 수치는 측정해서 적는다.

> **변이 A 가 경계 관측을 빨갛게 만드는지도 항목마다 다르다.** B-08 에서는 A(템플릿 제거)가 예외를 내지 않고 **집계가 1 그대로**였다 — `saveAndFlush` 가 자기 물리 트랜잭션을 열기 때문이다(실측). A 는 다른 단언 넷이 잡았다. **그래서 A 를 경계 관측의 몫으로 기대하지 않는다.** 경계 관측은 **C 를 위한 것**이고, A 는 행위 단언이나 예외가 잡는다 — 어느 쪽이 잡는지는 측정해서 적는다.

> **같은 변이의 집계가 항목마다 다르다.** B-07의 변이 C는 **2**다(실측). AU-08과 하나 차이 나는 이유는 조회 경로다 — B-07이 쓰는 **파생 쿼리** `findByIdAndDeletedFalse`에는 `SimpleJpaRepository`의 기본 `@Transactional`이 적용되지 않아 그 조회가 트랜잭션을 **아예 열지 않는다**(아래 블록인용이 변이 A에 대해 같은 사실을 적는다).
>
> **앞 판이 AU-08의 C를 2라고 잘못 적었는데, 그 2가 B-07에서는 맞는 값이다.** 한 항목에서 틀린 숫자가 다른 항목에서는 맞을 수 있다 — 그래서 집계를 단언에 넣지 않고 "정확히 한 번"에만 건다. 조회가 파생 쿼리인지 `@Query`인지에 따라 바뀌므로 **구현을 보고 예측하지도 않는다.**

**리뷰어는 A·B·C 셋을 돌린다.** C가 잡히지 않으면 `CHANGES_REQUESTED`다.

#### 변이 C를 만드는 법 — 공유 메서드를 건드리지 않는다

파생 삭제(`deleteBy…`)는 활성 트랜잭션을 요구하므로, "연산마다 자기 트랜잭션"을 만들려면 경계를 어딘가에 줘야 한다. **리포지터리 메서드에 `@Transactional`을 붙이는 형태를 쓰지 않는다** — 그 메서드를 쓰는 **다른 항목의 테스트까지** `UnfinishedStubbingException`으로 터뜨린다(스파이가 트랜잭션 프록시로 감싸인다). 단언 실패가 아니므로 그 항목의 커버리지에 대한 정보가 아니고, 읽는 사람을 혼란시킨다. AU-09에서 측정됐다.

**대신 서비스 메서드 안에서 각 연산을 `TransactionTemplate`으로 감싼다.**

| | |
| --- | --- |
| 형태 | 서비스의 `@Transactional` 제거 + 두 연산을 각각 `tx.executeWithoutResult(…)` |
| `PlatformTransactionManager` 주입 | **필드 주입으로 넣는다** — `final`이 아니므로 Lombok의 생성자 시그니처가 그대로이고, `new 서비스(…)`를 쓰는 기존 테스트가 깨지지 않는다 |
| 결과 (AU-09 실측) | 실패 **2개, 둘 다 진짜 단언 실패.** 다른 항목의 테스트는 전부 통과 |

**변이를 넣으려고 테스트를 고쳐야 하면 그 변이 형태가 틀린 것이다.** 생성자 주입이나 별도 빈으로 하면 기존 생성자 테스트가 깨진다. 컨벤션(필드 주입 금지)을 어기는 것은 무관하다 — 변이는 의도된 결함이고 원복된다.

#### 실패할 수 없는 단언을 쓰지 않는다

스파이가 가로챈 연산의 **결과**를 단언하면 그 단언은 반증 불가능하다. AU-08의 예: `deleteByAccountId`를 `willThrow`로 가로채고 `refresh_token` 행 수가 1임을 단언했는데, DELETE가 발행될 자리가 없으므로 **어떤 구현에서도 1이다.** `@Transactional`이 아예 없을 때도 통과한다.

**검증표의 한 케이스가 두 효과를 요구하면, 각 효과의 단언이 따로 반증 가능한지 확인한다.** 통과하는 것으로는 부족하다 — 깨뜨려 보고 빨개지는지 본다.

**고치는 법 — 되돌릴 효과를 실제로 만든다.** 스텁이 그 연산을 **실제로 발행한 뒤** 예외를 던지면, 롤백될 것이 있으므로 단언이 일한다. AU-08에서는 스텁 안의 `JdbcTemplate` DELETE로 했다(`invocation.callRealMethod()`는 **불가** — Spring Data 리포지터리는 JDK 프록시라 `Cannot call abstract real method on java object!`가 난다). 올바른 구현에서 그 DELETE는 되돌려지고, 트랜잭션 경계가 없으면 그 자리에서 커밋되어 단언이 빨개진다.

> **이 기법은 변이 B 전용이다.** 변이 C를 잡는 데는 쓸 수 없다 — 위 "근본 원인"이 그 이유다. C는 경계 관측이 잡는다.

**주입한 효과가 실제로 일어났는지를 스텁 안에서 단언한다.** 영향 행 수를 버리면 **SQL이 어긋나 0행이 되었을 때 조용하다** — 되돌릴 효과가 없으므로 단언이 다시 반증 불가능해진다. AU-08에서 대조군으로 재현한 값이다: 가드 없이 SQL을 0행이 되게 어긋내니 **16개가 전부 통과했다.** 가드를 넣으면 그 자리에서 터진다.

> **잔여 한계 — 행 수는 보고 발행한 문장의 동등성은 보지 않는다.** `deleted == 1`은 "한 행이 지워졌다"일 뿐이고 "운영 코드가 지울 그 행"인지는 모른다 — **다른 키로 1행을 지우면 통과한다.** `callRealMethod()`가 불가능한 데서 나오는 구조적 한계이고 값싼 해결이 없다. **기계장치를 더 넣지 않고, 주입하는 SQL 옆에 그 문장의 짝이 어느 리포지터리 메서드인지를 주석으로 달아 다음 사람의 앵커로 삼는다.**

> 변이 A가 예상 밖의 지점에서 터질 수 있다. Spring Data의 파생 삭제(`deleteBy…`)는 `em.remove`로 처리되고 그것이 활성 트랜잭션을 요구하므로, `SimpleJpaRepository`의 기본 `@Transactional`이 **파생 쿼리 메서드에는 적용되지 않아** 즉시 예외가 난다(`No EntityManager with actual transaction available`). 조용히 사라지지 않는다 — 그래서 A는 쉽게 잡히고 B·C는 안 잡힌다.

> **`PageImpl` 은 마지막 페이지에서 `totalElements` 를 다시 계산한다.** `offset + pageSize > total` 이면 `offset + content.size()` 를 돌려준다. 그래서 **건수 쿼리의 조건을 제거해도 `totalElements` 단언이 통과한다** — 페이지가 꽉 차지 않았으면 반환값이 콘텐츠 크기에서 보정되어 건수 쿼리를 보지 않는다. B-06 실측: 삭제분 제외 테스트의 `totalElements` 단언이 건수 쿼리의 `deleted` 조건을 제거해도 **녹색이었다.** `size` 를 줄여 **페이지를 꽉 채운 뒤** 같은 변이가 빨개지는 것을 확인했다.
>
> **페이징 응답의 `totalElements` 를 단언하는 테스트는 페이지가 꽉 차는지 먼저 본다.** 꽉 차지 않으면 그 단언은 목록 쿼리를 두 번 보는 것이고 건수 쿼리는 관측되지 않는다.

#### 단언이 무엇을 못박는지 가르려면 "가릴 수 있는 구현" 을 넣는다

**결함을 넣는 변이는 단언이 *무엇을 잡는지* 보여 주지만 *무엇을 못박는지* 는 보여 주지 않는다.** 그것을 가르는 변이는 **결함을 넣지 않고 수단만 바꾸는 것**이다 — 단언이 요구하는 결과는 그대로 내면서 구현 수단을 비껴가는 쪽이다. 통과하면 그 단언이 못박는 것은 **결과**이고 **수단이 아니다.**

B-11 리뷰 실측이 그 모양이다. 끈 쪽에서 3개가 빨개지므로 `clearAutomatically` 가 관측되는 것처럼 보였는데, **응답 값을 다시 읽지 않고 그 자리에서 계산하면서 그 설정을 끈 변이**가 **276/276 녹색**이었다. 그 구현은 설정을 아예 쓰지 않는다. 즉 단언들이 못박는 것은 "응답이 증가 후 값을 싣는다" 이고 "응답을 DB 에서 다시 읽는다" 가 아니다 — **스위트는 그 설정을 고정하지 않는다.**

> **리뷰 지시에 쓸 문구.** "그 실패가 X 를 관측하는 것인지 **다른 것에 가려진 것인지** 판정해라" 가 이 변이를 떠올리게 한다(B-11 리뷰어의 보고). "변이가 잡혔는지" 만 묻는 지시는 이 종류를 부르지 않는다.

#### 변이를 돌릴 때 — 묵은 결과를 새 결과로 읽는 두 경로

**변이가 적용되지 않아 gradle 이 아예 돌지 않은 것과 `Task :test UP-TO-DATE` 는 다른 경로이고, 둘 다 묵은 `build/test-results` 를 새 결과로 읽게 만든다.** B-11 리뷰 실측: 변이 적용 스크립트가 `pattern count=0` 으로 죽어 `&&` 사슬이 끊겨 gradle 이 실행되지 않았는데, 결과 요약이 **직전 변이의 XML 을 읽어 글자까지 같은 값**을 새 변이의 결과로 냈다. `UP-TO-DATE` 사고는 "gradle 이 돌았지만 테스트를 건너뛴" 경우이고 이쪽은 **"gradle 이 아예 안 돈"** 경우다.

둘을 함께 막는 값싼 방법이 셋이다.

- 돌리기 전에 **결과 디렉터리를 지운다**(`build/test-results/test`). 지우면 안 돈 실행은 결과가 없다
- **변이 적용 스크립트가 패턴 수를 세어 1이 아니면 거기서 죽게** 만든다. 조용히 0건을 바꾸지 않는다
- **gradle 종료 코드와 `tests completed` 줄을 둘 다 기록한다.** 하나만 보면 위 두 경로를 구별할 수 없다

> **변이 패턴을 손으로 escape 하지 마라.** 위 사고의 발단은 한글 식별자를 바이트로 치환할 때 `요`(EC 9A 94)를 `용`(EC 9A A9)으로 잘못 적어 패턴이 0건이 된 것이다. 패턴은 **소스 인코딩으로 그대로** 쓴다.
>
> **비교 대상이 0건이면 `diff` 와 해시 비교는 통과한다.** I-04 실측: 세 저장소의 `ErrorCode` 에서 공통 코드 줄만 뽑아 대조하려 했는데 패턴이 **0줄**을 뽑았고, 빈 파일 셋을 `diff` 하니 차이가 없어 "3자 동일" 이 출력됐다. 빈 파일의 sha256(`e3b0c44298fc1c14…`)으로 알아챘다. **뽑은 줄 수를 세어 기대값이 아니면 거기서 죽는 가드를 명령에 함께 둔다** — 가드 없는 명령은 패턴이 어긋나는 순간 같은 거짓 통과를 만든다. 실패할 수 없는 단언과 같은 모양이고, 측정 도구 쪽에서 생긴다.
>
> **정규화 강도를 함께 적는다.** 같은 "3벌 동일" 이 주장의 세기가 다르다 — 패키지명만 바꾼 비교는 **주석까지 바이트 동일**을 뜻하고, 주석·빈 줄을 지운 비교는 **구조만** 뜻한다. 섞어 인용하면 약한 측정이 강한 주장으로 읽힌다(I-04 가 셋을 다른 강도로 쟀다).
>
> **0건은 패턴이 틀려도 나온다. 그래서 0 을 믿기 전에 패턴의 양성 대조를 세운다.** I-05 리뷰 실측: BCrypt 해시를 찾는 패턴을 `\$2[aby]\$[A-Za-z0-9./]{20,}` 로 썼는데 BCrypt 는 `$2a$10$…` 로 **cost 뒤에 `$` 가 또 온다.** 문자 클래스에 `$` 가 없어 거기서 멈추고 **0건**이 나왔다 — 로그에 해시가 **4건** 있는 상태였다. 리뷰어가 로거 이름을 교차 확인해서 잡았고, 그 뒤 **합성 문자열에 패턴이 적중하는 것을 먼저 보이고** 0 을 보고했다.
>
> **비밀 탐색의 0건은 특히 위험하다** — 같은 모양의 거짓 0 이 "비밀이 없다" 로 읽힌다. 패턴을 쓰는 쪽은 **적중해야 하는 입력**을 하나 만들어 함께 돌린다.

**테스트를 더하라는 규칙이 아니다.** 같은 결함을 두 번 보는 테스트를 넣지 않는다([../AGENTS.md](../AGENTS.md) 불변식 11). 경계 관측 하나가 A와 C를 함께 잡는다.

## 5. 판정

```
판정: APPROVED | CHANGES_REQUESTED

[CHANGES_REQUESTED인 경우 finding 목록]
#1 [blocker] <파일>:<라인>
   문제: ...
   근거: <정본 문서 경로 §절>
   수정 제안: ...
```

- 결과는 `APPROVED` 또는 `CHANGES_REQUESTED` 둘 중 하나다. 중간 값을 두지 않는다
- **blocker 또는 major가 하나라도 있으면 `CHANGES_REQUESTED`다**
- minor만 남으면 `APPROVED`로 판정하고 minor는 후속 정리로 기록한다
- **부분 반영이나 무응답을 승인으로 해석하지 않는다**

### 5.1 심각도

| 심각도 | 기준 |
| --- | --- |
| `blocker` | 정본 문서와 어긋남, 보안 결함, 데이터 손상 가능성, [dev-workflow.md §4](dev-workflow.md) 금지 사항 위반 |
| `major` | 완료 기준 미충족, 검증 표 케이스 누락, 아키텍처 원칙 위반(크로스 스키마 조인, 트랜잭션 내 원격 호출 등) |
| `minor` | 네이밍, 주석, 사소한 중복 |

### 5.2 판정 시 유의

- **완료 기준을 하나씩 대조한다.** "대체로 맞다"로 넘기지 않는다
- 테스트가 있다는 것과 **그 테스트가 검증 표의 케이스를 덮는다는 것**은 다르다
- 구현 워커가 "이건 나중에 하겠다"고 적어둔 것은 `major`다. 완료 기준에 있으면 지금 해야 한다
- 정본 문서가 틀렸다고 판단되면 코드를 통과시키지 말고 **그 사실을 finding으로 올린다.** 문서 개정은 별도 절차다

### 5.3 계획이 둘을 구분해 쓴다

**검증 표에는 테스트로 덮을 수 있는 것만 넣는다.** 넣으면 테스트가 강제되므로, 개발 유틸리티의 출력이나 사람이 한 번 보면 끝나는 것은 **완료 기준**에 둔다.

| 성격 | 어디에 |
| --- | --- |
| 코드 동작·응답·DB 상태 | 검증 표 |
| Gradle 태스크 출력, 파일 존재, 문서 일치 | 완료 기준 |

계획이 이것을 잘못 쓰면 구현이 무거운 테스트를 만들거나 `major`를 받는다. **리뷰어는 정본이 틀렸다고 보이면 통과시키지 말고 finding으로 올린다**(§5.2) — 그 판단이 계획을 고치는 입구다.

#### 검증표에 한 줄을 쓰기 전에 물을 것

**"테스트가 이것을 표현할 수 있는가"를 먼저 묻는다.** 이 실수가 1차에서 세 번 나왔고 셋 다 리뷰가 잡았다.

| 잘못 넣은 것 | 왜 테스트가 못 쓰나 |
| --- | --- |
| Gradle 태스크의 출력 | 빌드 산출물이고 테스트가 보는 대상이 아니다 |
| "탈퇴 직후 **발신 호출 없음**" | 호출이 없다는 것은 **의존성 부재**로 확인한다. 없는 호출을 관측하는 테스트는 아무것도 잡지 못한다 |
| `git log -p`·`git grep` 결과, 다른 항목이 소유한 동작 | 전자는 이력 조회이고, 후자는 **그 항목의 테스트가 이미 자기 기준으로 덮는다** |

**세 번 다 원인이 같다 — "확인할 것"을 떠올린 자리에 바로 적었다.** 확인할 값어치가 있다는 판단은 맞았고, 틀린 것은 **배치**다. 검증표는 "테스트가 이것을 증명한다"는 약속이므로, 증명할 수 없는 것을 넣으면 그 칸이 영구히 비거나 구현이 무의미한 테스트를 만든다.

**다른 항목이 소유한 동작은 특히 조심한다.** 그 동작의 특정 응답 코드를 이쪽 검증표에 못박으면, **소유자의 기준보다 좁은 주장**을 하게 된다 — 소유자의 테스트는 자기 기준에 맞게 느슨할 수 있고 그것이 옳다. AU-11이 `/actuator/env`를 401로 못박았으나 AU-04의 기준은 "노출되지 않는다"이고 그 테스트는 401·403·404를 모두 받는다. **느슨한 쪽이 맞았다.**

## 6. 라운드 상한

**리뷰 라운드는 최대 3회다.** 초과하면 BLOCKED로 보고하고 사람의 판단을 받는다.

3라운드로 수렴하지 않으면 코드가 아니라 **계획서나 정본 문서에 문제가 있을 가능성이 크다.** 계속 돌리면 워커들이 서로 다른 해석으로 코드를 밀고 당기게 된다.

## 7. 기록

- **리뷰 보고서 파일을 저장소에 남기지 않는다**
- 구현 리뷰 결과는 수정 워커에게 전달하고, 통과하면 그것으로 끝난다
- 진행 상태는 `docs/checklist.md`에만 적는다. 리뷰 라운드 수는 2회 이상일 때만 `· 리뷰 2라운드`로 표기한다
- 코드 사실을 인용할 때는 파일·라인을 함께 적는다
- 경위·처분 이력을 문서에 적지 않는다

## 8. 정본 문서 개정

**개정한 뒤 `python tools/check_refs.py`를 돌린다.** 깨진 참조가 있으면 종료 코드 1이다.

| 검사하는 것 | |
| --- | --- |
| 링크 대상 파일이 있는가 | `[...](other.md)` |
| 라벨의 절 번호가 대상에 있는가 | `[tech-stack.md §5.3](tech-stack.md)` |

> **그 표가 적은 것보다 도구가 덜 검사한다. I-03 2라운드 실측.** `tools/check_refs.py` 의 `main()` 이 `secs = SEC.findall(label); if not secs: continue` 로 **라벨에 `§` 가 없는 링크를 건너뛴다.** 그래서 **`[B-10](phase1.md)` 처럼 절 번호 없는 링크의 대상 파일 존재는 검사되지 않는다** — 실제로 그 깨진 링크가 `nfr.md` 에 들어갔고 `check_refs` 가 "link targets OK" 를 냈다.
>
> **`§` 없는 링크를 쓸 때는 대상 경로를 손으로 확인한다.** 루트 문서에서는 `plan/phase1.md`, `plan/`·`process/` 안에서는 `phase1.md`·`../tech-stack.md` 다 — 같은 파일을 가리키는 경로가 위치마다 다르다.
>
> **알려진 부채**: `../AGENTS.md` 를 가리키는 링크 여덟 개가 파일시스템상 존재하지 않는 경로다(`AGENTS.md` 는 세 구현 저장소에 있고 `sp-docs` 에는 없다). 관례로 굳었고 고치려면 여덟 곳을 손봐야 해서 1차에서 건드리지 않는다 — **새 링크를 그 관례로 더하지 않는다.**
| **개정 대상을 고쳤으면 `version` 도 올랐는가** | `HEAD` 와 비교하므로 **커밋 전에** 돌려야 의미가 있다 |

절을 지우거나 번호를 바꾸면 **다른 문서가 가리키던 주소가 조용히 죽는다.** 32편이 서로를 참조하므로 손으로 좇을 수 없다.

**도구는 존재만 본다. 옳은 절인지는 보지 않는다.** `§5`가 그 문서에 있으면 통과하므로, **규칙이 §6에 있는데 §5를 가리키는 참조는 잡히지 않는다.** AU-10에서 실제로 그런 참조 셋이 발견됐다(오프셋 규칙이 `tech-stack.md` §6에 있는데 세 곳이 §5를 가리켰다). 기계로 잡을 수 없는 종류이므로 **리뷰어가 근거를 따라가 실제로 그 내용이 있는지 확인한다.**

> 이 도구는 AU-09 리뷰까지 **세션 scratchpad에만 있었다.** D-01의 완료를 그것으로 판정했는데 저장소에 없었으므로, 그 판정은 누구도 재현할 수 없는 상태였다. 리뷰어가 "`check_refs.py`가 검사한다"는 내 전제를 확인하려다 파일이 없다는 것을 발견했다. **정본의 완료 기준이 가리키는 도구는 정본과 함께 커밋한다.**

`api-contract.md`, `domain-model.md`, `tech-stack.md`, `conventions.md`, `requirements/`, `adr/`의 변경은 개정이다.

- front matter의 `version`과 `updated`를 올린다. **`security.md` 도 같은 취급이다** — 세 서비스가 의존하는 계약이다. 누락은 도구가 잡는다(위 표 셋째 행)
- **구현 워커는 정본 문서를 고치지 않는다**([orchestration.md §7](orchestration.md)). 문서가 틀렸다고 판단되면 BLOCKED로 보고한다
- **`api-contract.md §6`(JWT Claim)는 세 서비스가 공유하는 계약이다.** 발급은 auth 하나, 검증은 member·board 둘이다. 개정 시 세 담당이 모두 확인한다
- **`api-contract.md §5`(내부 API)는 board와 member가 공유하는 계약이다.** 1차부터 쓰기 경로에서 호출된다
- 구현이 정본과 어긋나면 **코드를 고치거나 정본을 개정한다.** 코드에 맞춰 문서를 암묵적으로 재해석하지 않는다
- 설계 변경 수준의 개정은 **독립 리뷰 워커**를 붙인다. 제안자가 자기 제안을 검증하지 않는다
