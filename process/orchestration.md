# 워커 오케스트레이션

## 1. 실행 방식 — 워크트리

**워커마다 git worktree를 만들어 격리한다.** 별도 클론을 쓰지 않는다.

```bash
# member 저장소에서
git worktree add ../wt/agent-m1 -b worktree-agent-m1
git worktree add ../wt/agent-m2 -b worktree-agent-m2

git worktree list      # 전체 확인
git worktree remove ../wt/agent-m1   # 작업 종료 후 정리
```

| | 워크트리 (채택) | 별도 클론 |
| --- | --- | --- |
| `.git` | 공유 | 워커마다 별도 |
| 생성 | 즉시 (로컬 체크아웃) | 매번 전체 다운로드 |
| 디스크 | 작업 파일만 | N배 |
| 브랜치 확인 | `git worktree list` 한 번에 | 클론마다 따로 |
| 워커 간 커밋 참조 | 로컬에서 즉시 | push/fetch 필요 |

작업 디렉터리는 저장소 바깥(`../wt/`)에 둔다. 저장소 안에 두면 워커가 다른 워커의 작업 파일을 자기 산출물로 착각할 수 있다.

## 2. 워크트리가 격리하는 것과 못하는 것

| | |
| --- | --- |
| 격리된다 | 작업 파일, 브랜치, 빌드 산출물 |
| **격리되지 않는다** | **병합.** 두 워커가 같은 파일을 고치면 merge에서 충돌한다 |

그래서 충돌은 규칙이 아니라 **구조**로 막는다. 각 경로에 소유 항목을 하나씩 두고 워커는 자기 경로에만 쓴다. 경로 소유 지도와 공유 지점은 [../plan/phase1.md §2](../plan/phase1.md)에 있다.

**이 규칙은 여러 워커를 동시에 돌릴 때만 강제된다.** 저장소당 워커가 하나면 순차로 진행하므로 충돌할 상대가 없고, 경로를 넘는 것 자체는 문제가 아니다([../plan/phase1.md §2](../plan/phase1.md)).

## 3. 워커 역할

**1차는 구현 워커 2개로 시작한다.** 근거와 확대 조건은 [../plan/phase1.md §1.2](../plan/phase1.md)에 있다.

| 역할 | 저장소 | 담당 항목 |
| --- | --- | --- |
| member 워커 | `yuno110/sp-member` | M-01 ~ M-11 |
| board 워커 | `yuno110/sp-board` | B-01 ~ B-09 |
| 리뷰 워커 | 대상 저장소 (읽기 전용) | 항목마다 생성. **매 라운드 새로** |
| 수정 워커 | 대상 저장소 | `CHANGES_REQUESTED` 시 생성 |
| 통합 워커 | 두 저장소 + 실행 환경 | I-01 ~ I-04 (1차 완료 후) |

**리뷰 워커는 구현 워커와 달라야 한다**([review-policy.md §1](review-policy.md)). 구현 워커를 늘리는 것보다 리뷰 워커를 붙이는 쪽이 위험 대비 효용이 크다.

## 4. 배치

### 4.1 저장소 간 — 완전 병렬

```
member 워커 ──> M-01 ~ M-11     ┐
                                 ├── 서로 기다리지 않음
board 워커  ──> B-01 ~ B-09     ┘
                     │
              둘 다 done
                     │
              통합 워커 ──> I-01 ~ I-04   (순차)
```

저장소가 분리되어 있어 소스가 겹칠 수 없다. 계약이 [../api-contract.md §5](../api-contract.md)에 확정되어 있어 B-04가 M-04를 기다리지 않는다.

### 4.2 저장소 내부 — 1차는 순차

**한 저장소에 구현 워커 하나를 둔다.** 항목을 계획 순서대로 진행한다.

기반 단계(M-01~M-04, B-01~B-04)에서 순서 의존과 공유 상태를 제거해 두었으므로, 기능 단계는 앞 항목의 미완성에 걸려 멈추지 않는다([../plan/phase1.md §1.1](../plan/phase1.md)).

**확대는 측정 후에 정한다.** 늘린다면 member 저장소의 `member/*` ∥ `auth/*` 트랙 하나뿐이며, board는 임계 경로 밖이라 쪼개도 전체 소요가 줄지 않는다.

두 워커를 돌릴 경우에만 아래가 적용된다.

```bash
# member 트랙을 먼저 병합하고 auth 트랙이 리베이스한다
git checkout main
git merge worktree-agent-member
git merge worktree-agent-auth
./gradlew test                 # 병합 후 전체 테스트
```

**병합 후 전체 테스트를 다시 돌린다.** 각자의 워크트리에서 통과했어도 합친 뒤 깨질 수 있다. 특히 경로 매핑·인가 순서 같은 상호작용 결함은 각 워커의 `@WebMvcTest`로는 잡히지 않고 병합 후에만 드러난다.

### 4.3 작업 항목 하나의 사이클

구현 워커는 테스트 통과 후 **스테이징만 하고 턴을 끝낸다**([dev-workflow.md §3.7](dev-workflow.md)). 그 다음은 오케스트레이터가 워커를 만들어 돌린다.

```
오케스트레이터
    |
    +--> 구현 워커 생성 ──> 구현·테스트 ──> git add -A ──> 턴 종료
    |                                                        |
    |<-------------------------- 보고 ------------------------+
    |
    +--> 리뷰 워커 #1 생성 ──> git diff --cached 검토 ──> 판정
    |                                                        |
    |<-------------------------- 판정 ------------------------+
    |
    +-- APPROVED ──────────> 오케스트레이터가 커밋·푸시·done
    |
    +-- CHANGES_REQUESTED
            |
            +--> 수정 워커 생성 (finding 전문 전달) ──> 수정·테스트 ──> 턴 종료
            |
            +--> 리뷰 워커 #2 생성  (★ 새 워커. #1을 재사용하지 않는다)
                     |
                    ... 최대 3라운드. 초과 시 중단하고 사람 판단
```

**역할 분담**

| 단계 | 주체 |
| --- | --- |
| 상태 `todo` → `doing` | 구현 워커 |
| 구현·테스트·스테이징 | 구현 워커 |
| 상태 `doing` → `review` | 구현 워커 |
| 리뷰·수정 워커 생성 | **오케스트레이터** |
| 판정 수신과 분기 | **오케스트레이터** |
| 커밋·푸시 | **오케스트레이터** |
| 상태 `review` → `done` | **오케스트레이터** |

**커밋을 오케스트레이터가 하는 이유**: 구현 워커의 턴은 스테이징에서 끝났다. 다시 불러 커밋시키면 컨텍스트를 재구축해야 하고, 워커가 순서를 착각해 리뷰 전에 커밋할 위험이 생긴다. 커밋은 판단이 필요 없는 기계적 단계이며 `APPROVED` 판정을 가진 쪽은 오케스트레이터다.

**워커마다 새로 만드는 이유**

| 워커 | 이유 |
| --- | --- |
| 리뷰 워커 | 이전 라운드 리뷰어는 자기가 지적한 것만 확인하게 되어 새 결함을 놓친다 |
| 수정 워커 | 구현 워커는 자기 판단으로 그 코드를 썼다. 같은 시각으로 고치면 같은 실수를 반복한다 |

리뷰 워커는 **읽기만** 하므로 워크트리를 공유해도 충돌하지 않는다. 다만 리뷰 중에는 구현 워커가 파일을 고치지 않는다.

### 4.4 오케스트레이터 절차

작업 항목 하나마다 아래를 수행한다.

1. **구현 워커 생성** (§5.1 템플릿)
2. 보고를 받는다. `BLOCKED`면 사유를 읽고 사람 판단으로 넘긴다
3. **리뷰 워커 생성** (§5.2 템플릿). 라운드 번호를 센다
4. 판정을 받는다
   - `APPROVED` → 6으로
   - `CHANGES_REQUESTED` → 5로
5. **수정 워커 생성** (§5.3 템플릿, finding 전문 전달) → 보고 후 **3으로 돌아간다**
   - 3라운드를 초과하면 중단하고 사람 판단으로 넘긴다. 코드가 아니라 계획서나 정본 문서에 문제가 있을 가능성이 크다
6. **완료 처리** (§5.4) — 커밋·푸시·상태 갱신
7. 다음 작업 항목으로

**오케스트레이터가 판정을 뒤집지 않는다.** `CHANGES_REQUESTED`를 "사소해 보이니 넘어가자"로 처리하지 않는다. 심각도 판단은 리뷰 워커의 몫이고, 이의가 있으면 사람에게 올린다.

## 5. 워커 생성

### 5.1 구현 워커

```
작업 디렉터리: ../wt/agent-member   (워크트리)
지시: CLAUDE.md를 읽고 그 절차를 따라라.
```

워커가 하나면 담당 항목을 지정하지 않아도 된다. 체크리스트에서 `doing`·`review` 항목을 먼저 찾고, 없으면 다음 `todo`를 고른다.

**같은 저장소에 두 워커를 돌릴 때는 담당 항목이나 트랙을 명시적으로 지정한다.** 그러지 않으면 둘이 같은 항목을 집는다.

나머지는 워커가 스스로 한다.

```
CLAUDE.md 읽음
  → AGENTS.md (행동 원칙)
  → docs/checklist.md 에서 항목 확인, 상태를 doing으로
  → sp-docs/plan/phase1.md 에서 그 항목의 상세 확인
  → 항목의 "참조" 문서만 읽음
  → sp-docs/process/dev-workflow.md 절차대로 구현·테스트
  → git add -A (커밋하지 않음), 상태를 review로, 턴 종료
```

받는 보고는 [dev-workflow.md §3.7](dev-workflow.md) 형식이다.

### 5.2 리뷰 워커

```
저장소: yuno110/<member|board>
워크트리: <경로>
작업 항목: <ID>

리뷰 대상: git diff --cached (스테이징된 미커밋 변경)
판정 기준: sp-docs/plan/phase1.md 의 <ID> — 산출물·완료 기준·검증 표
절차: sp-docs/process/review-policy.md 를 따라 APPROVED 또는
      CHANGES_REQUESTED 로 판정하라. 테스트는 직접 실행해서 확인하라.
```

**구현 워커의 설명이나 자기평가를 전달하지 않는다.** 리뷰어가 그 서술에 끌려가면 독립 판정이 되지 않는다.

2라운드 이상이면 이전 라운드의 finding 전문을 함께 준다.

### 5.3 수정 워커

```
저장소: yuno110/<member|board>
워크트리: <경로>
작업 항목: <ID>

리뷰 finding:
<finding 전문 그대로>

지시: 위 finding을 해소하라. finding 범위 밖의 변경은 하지 않는다.
      수정 후 ./gradlew test 를 통과시키고 git add -A 로 스테이징만 한다.
      커밋하지 않는다.
절차: sp-docs/process/dev-workflow.md
```

### 5.4 완료 처리 (오케스트레이터가 직접)

`APPROVED`를 받은 뒤에만 수행한다.

**작업 항목 하나 = 커밋 하나다.** 체크리스트 갱신을 별도 커밋으로 내지 않는다.

```bash
cd <워크트리>
# 1) 체크리스트를 done 으로 바꾼다 (커밋 전에)
#    - [x] M-01 프로젝트 스캐폴딩 · 상태 done
# 2) 함께 스테이징하고 한 번에 커밋한다
git add -A
git status --short          # 스테이징 내용 확인
git commit -m "<type>(<scope>): <요약>"
git push origin HEAD
```

- 커밋 메시지 형식은 [../conventions.md §10](../conventions.md)
- 체크리스트에 커밋 해시를 적지 않는다. 자기 자신을 가리킬 수 없고, `git log`가 이미 기록이다

## 6. 체크리스트 충돌 회피

같은 저장소의 두 워커가 모두 `docs/checklist.md`를 수정한다. git은 **서로 다른 줄**의 변경을 자동 병합하므로 대개 문제없다.

| 규칙 | 이유 |
| --- | --- |
| 자기 항목의 줄만 고친다 | 다른 줄을 건드리면 충돌 |
| 파일을 재정렬·재포맷하지 않는다 | 전체 줄이 변경으로 잡힌다 |
| 항목을 추가·삭제하지 않는다 | 계획 개정이 먼저다 |
| 파일 상단 요약 문구를 갱신하지 않는다 | 두 워커가 같은 줄을 고치게 된다 |

## 7. 문서 저장소 접근

| 작업 | 권한 |
| --- | --- |
| 정본 문서 읽기 | 모든 워커 |
| 정본 문서 수정 | **구현 워커는 하지 않는다** |

구현 중 문서가 틀렸다고 판단되면 고치지 말고 BLOCKED로 보고한다([dev-workflow.md §4](dev-workflow.md)).

문서가 두 워커의 공유 지점이기 때문이다. 한 워커가 임의로 고치면 다른 워커가 이미 그 값으로 구현한 것과 어긋난다.

## 8. 금지

| 금지 | 이유 |
| --- | --- |
| 한 워크트리를 두 워커가 공유 | 서로의 파일을 덮어쓴다 |
| 담당 저장소 밖의 저장소 수정 | member 워커가 board를 고치지 않는다 |
| **동시 실행 중** 다른 워커가 쓰는 경로에 쓰기 ([../plan/phase1.md §2.5](../plan/phase1.md)) | 병합 충돌 |
| 공유 지점 파일을 동시에 수정 ([../plan/phase1.md §2.3](../plan/phase1.md)) | 병합 충돌 |
| 마이그레이션 번호를 임의로 정하기 ([../plan/phase1.md §2.4](../plan/phase1.md)) | 같은 번호 중복 |
| 완료된 항목의 완료 기준을 깨는 변경 ([../plan/phase1.md §2.6](../plan/phase1.md)) | 계획이 틀렸다는 신호다 |
| 다른 워커의 브랜치에 커밋 | |
| **리뷰 없이 커밋·푸시** | 게이트 우회 ([dev-workflow.md §4](dev-workflow.md) 금지 3) |
| **구현 워커가 자기 작업을 리뷰** | 작성자는 자기 실수를 보지 못한다 |
| 이전 라운드의 리뷰 워커 재사용 | 새 결함을 놓친다 |

## 9. 진행 확인

```bash
# 워크트리 상태
git worktree list

# 체크리스트
cat member/docs/checklist.md
cat board/docs/checklist.md
```

`blocked` 항목이 있으면 사유를 읽고 막힘을 푼다. 사유는 다음 작업자가 이어받을 수 있을 만큼 구체적이어야 한다([dev-workflow.md §4](dev-workflow.md)).
