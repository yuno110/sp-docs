# 개발 워크플로

작업 항목 하나를 시작해서 끝낼 때까지의 절차다. **모든 작업 항목이 이 절차를 따른다.**

**핵심: 리뷰를 통과하기 전에는 커밋하지 않는다.** 리뷰가 게이트다.

## 1. 전체 흐름

```
 [1] 작업 항목 선택                                     todo -> doing
      |
 [2] 참조 문서 읽기  (항목의 "참조" 필드에 적힌 것만)
      |
 [3] 산출물 구현
      |
 [4] 검증 테스트 작성  (항목의 "검증" 표를 테스트 코드로)
      |
 [5] ./gradlew test  ---실패---> 원인 분석 -> 수정 -> [5]로
      |                            (최대 3회. 초과 시 BLOCKED)
     통과
      |
 [6] 완료 기준 체크리스트 전 항목 확인
      |
 [7] git add -A  (스테이징만. 커밋하지 않는다)         doing -> review
      |           ── 여기까지 구현 워커. 턴 종료 ──
      |
 [8] ★ 리뷰 워커 생성 (매번 새 워커)          ── [8]부터 오케스트레이터 ──
      |
 [9] 판정
      |
      +-- CHANGES_REQUESTED --> [10] 수정 워커 생성 (새 워커)
      |                              수정 -> [5] 테스트 -> [8]로 (새 리뷰 워커)
      |                              최대 3라운드. 초과 시 BLOCKED
      |
      +-- APPROVED
            |
 [11] 커밋 & 푸시
      |
 [12] checklist.md 상태를 done 으로                    review -> done
      |           (구현·테스트·체크리스트가 한 커밋)
      |
 [13] 이 사이클에 만든 워커를 전부 종료
      |
 [14] 다음 작업 항목
```

**[8]~[13]은 구현 워커가 아니라 오케스트레이터가 수행한다.** 구현 워커는 [7]에서 턴을 끝내고 보고한다.

| 단계 | 주체 |
| --- | --- |
| [1]~[7] 구현·테스트·스테이징 | 구현 워커 |
| [8][9] 리뷰 워커 생성과 판정 수신 | 오케스트레이터 |
| [10] 수정 워커 생성 | 오케스트레이터 (수정은 수정 워커가) |
| [11][12] 커밋·푸시·상태 갱신 | 오케스트레이터 |
| [13] 워커 정리 | 오케스트레이터 ([orchestration.md §5.5](orchestration.md)) |

전체 절차는 [orchestration.md §4.4](orchestration.md)에 있다.

## 2. 상태 전이

`docs/checklist.md`의 상태는 아래 다섯이다.

| 상태 | 의미 | 진입 시점 |
| --- | --- | --- |
| `todo` | 시작 전 | 초기값 |
| `doing` | 구현·테스트 중 | [1] |
| `review` | **테스트 통과, 리뷰 사이클 안** (리뷰 중이거나 수정 중) | [7] |
| `done` | 리뷰 APPROVED + 커밋·푸시 완료 | [12] |
| `blocked` | 진행 불가 | 언제든 |

- `review`에서 `CHANGES_REQUESTED`가 나와도 **상태는 `review`를 유지한다.** 수정도 리뷰 사이클의 일부다
- 2라운드 이상이면 줄 끝에 `· 리뷰 2라운드`를 붙인다
- **`doing`에서 곧바로 `done`으로 가지 않는다.** 리뷰를 거치지 않은 항목은 완료가 아니다

## 3. 단계별 규칙

### 3.1 작업 항목 선택 [1]

1. 담당 저장소의 `docs/checklist.md`를 연다
2. `doing` 또는 `review` 항목이 있으면 **그것을 먼저 처리한다**
3. 없으면 계획 순서상 다음 `todo`를 고른다. **의존 항목이 모두 `done`이어야 한다**
4. 상태를 `doing`으로 바꾼다

의존 항목이 `done`이 아니면 건너뛰고 다음 후보를 본다. 의존을 무시하고 진행하지 않는다.

### 3.2 참조 문서 읽기 [2]

작업 항목에 적힌 **참조 문서와 절 번호만** 읽는다. 문서 전체를 읽지 않는다.

값(엔드포인트, 컬럼명, 에러 코드, 버전)은 반드시 정본에서 가져온다. 기억이나 추측으로 채우지 않는다.

### 3.3 구현 [3]

- 산출물 목록을 기준으로 작업한다. 항목을 끝내는 데 필요하면 목록 밖 파일도 고칠 수 있으나, **무엇을 왜 고쳤는지 보고에 적는다** ([../plan/phase1.md §2.5](../plan/phase1.md))
- [../conventions.md](../conventions.md)를 따른다
- 문서에 없는 값이 필요하면 임의로 정하지 말고 §5의 BLOCKED로 보고한다

### 3.4 테스트 작성 [4]

**구현과 같은 작업 단위에서 작성한다.** 나중에 몰아서 작성하지 않는다.

- 작업 항목의 "검증" 표에 있는 케이스를 **모두** 테스트 코드로 만든다
- 표에 없어도 동작 변경·버그 수정에는 재현 가능한 최소 회귀 테스트를 추가한다
- 커버리지를 채우기 위한 테스트는 만들지 않는다. 서드파티 동작을 재검증하지 않는다

### 3.5 테스트 실행 [5]

```bash
./gradlew test
```

실패하면 원인을 분석하고 수정한 뒤 다시 실행한다. **최대 3회까지 재시도한다.**

3회를 초과하면 중단하고 §5의 BLOCKED를 보고한다. 계획서의 가정이 틀렸을 가능성이 있으며, 계속 시도하면 코드를 망가뜨린다.

### 3.6 완료 기준 확인 [6]

작업 항목의 "완료 기준" 체크리스트를 **한 줄씩** 확인한다. 전부 충족해야 다음으로 간다.

일부만 충족했으면 리뷰로 넘기지 않는다. §6에 따라 부분 진행 상태를 기록한다.

### 3.7 스테이징과 인계 [7]

```bash
git add -A          # 스테이징만. 커밋하지 않는다
git diff --cached   # 리뷰 대상이 이것이다. 직접 확인한다
```

**커밋하지 않는 이유**: 리뷰를 통과하지 못한 코드가 히스토리에 남지 않게 한다. 스테이징해 두면 리뷰 워커가 `git diff --cached`로 신규 파일까지 포함한 전체 변경을 한 번에 볼 수 있다.

상태를 `review`로 바꾸고 **턴을 끝낸다.** 리뷰 중에는 파일을 더 고치지 않는다 — 리뷰 대상이 움직이면 판정이 무의미해진다.

보고에 아래를 포함한다.

```
작업 항목: <ID>
워크트리: <경로>
테스트: ./gradlew test 통과
완료 기준: 전 항목 충족
리뷰 대기 중 (git add -A 완료, 미커밋)
```

### 3.8 리뷰 [8][9]

**매 라운드 새 리뷰 워커를 만든다.** 절차와 판정 기준은 [review-policy.md](review-policy.md)에 있다.

- 리뷰 워커는 구현 워커·수정 워커와 **다른 워커**여야 한다
- 이전 라운드의 리뷰 워커를 재사용하지 않는다. 자기가 지적한 것만 확인하게 되어 새 결함을 놓친다

### 3.9 수정 [10]

`CHANGES_REQUESTED`가 나오면 **수정 워커를 새로 만든다.**

수정 워커에게 주는 것: 작업 항목 ID, 워크트리 경로, **리뷰 finding 전문**, 계획서의 완료 기준.

수정 후 [5] 테스트를 다시 돌리고, 통과하면 [8]로 돌아가 **새 리뷰 워커**의 판정을 받는다.

**리뷰 라운드는 최대 3회다.** 초과하면 중단하고 BLOCKED로 보고한다. 3라운드로 수렴하지 않으면 코드가 아니라 계획서나 정본 문서에 문제가 있을 가능성이 크다.

### 3.10 커밋과 상태 갱신 [11][12] — 오케스트레이터가 한다

**구현 워커의 턴은 [7]에서 끝났다.** 커밋·푸시·상태 갱신은 오케스트레이터가 수행한다([orchestration.md §5.4](orchestration.md)).

`APPROVED`를 받은 뒤에만 커밋한다.

- 작업 항목 하나 = 커밋 하나다. 구현·테스트·체크리스트 갱신이 한 커밋에 들어간다
- 커밋 메시지 형식은 [../conventions.md §10](../conventions.md)
- 리팩터링과 기능을 한 커밋에 섞지 않는다
- **체크리스트 갱신을 커밋에 포함한다.** 별도 커밋으로 내지 않는다. 작업 항목 하나가 커밋 하나다

**상태를 갱신하지 않은 채 다음 항목으로 넘어가지 않는다.**

## 4. 금지 사항

이 절의 항목을 어기면 작업이 완료된 것으로 보지 않는다.

| # | 금지 | 이유 |
| --- | --- | --- |
| 1 | 실패하는 테스트를 `@Disabled`·주석 처리로 넘기기 | 실패를 숨기는 것이다 |
| 2 | 테스트를 통과시키려고 단언(assertion)을 약화하기 | 같음 |
| 3 | **리뷰를 거치지 않고 커밋·푸시하기** | 게이트를 우회하는 것이다 |
| 4 | **자기 작업을 자기가 리뷰하기** | 작성자는 자기 실수를 보지 못한다 |
| 5 | 완료 기준 미충족 상태에서 `done`으로 표시 | 다음 작업이 잘못된 전제 위에 쌓인다 |
| 6 | 테스트를 나중에 몰아서 작성 | 검증 없이 쌓인 코드는 원인 추적이 불가능해진다 |
| 7 | 막힌 부분을 mock·더미·하드코딩으로 우회 | 문제를 덮는 것이다. 막히면 BLOCKED로 보고한다 |
| 8 | 문서에 없는 값을 임의로 정해서 진행 | 정본과 어긋난 구현이 된다 |
| 9 | **완료된 항목의 완료 기준을 깨는 변경** | 계획이 틀렸다는 뜻이다. 코드가 아니라 계획을 고친다 ([../plan/phase1.md §2.6](../plan/phase1.md)) |
| 10 | 의존 항목이 `done`이 아닌데 진행 | 순서가 있는 데는 이유가 있다 |
| 11 | 리뷰 중에 파일 수정하기 | 리뷰 대상이 움직이면 판정이 무의미하다 |

**7번이 특히 중요하다.** 외부 의존이 없거나 정보가 부족할 때 임시 값으로 통과시키면 나중에 그 코드가 진짜인지 가짜인지 구분할 수 없다. 실패는 명시적으로 드러내야 한다.

## 5. BLOCKED 보고

진행할 수 없으면 아래 형식으로 보고하고 멈춘다.

```
BLOCKED
- item: (작업 항목 ID)
- blocked_by: (무엇이 막고 있는가 — 문서에 없는 값 / 선행 항목 미완 /
               테스트 3회 실패 / 리뷰 3라운드 초과 등)
- done_so_far: (완료 기준 중 충족한 것과 충족하지 못한 것)
- required: (진행하려면 무엇이 필요한가)
```

그리고 `checklist.md`의 상태를 `blocked`로 바꾸고 줄 끝에 `· 사유: ...`를 붙인다.

**사유는 다음 작업자가 이어받을 수 있을 만큼 구체적으로 적는다.** 완료 기준을 절 단위로 쪼개서 어디까지 됐는지 적는다.

```
- [ ] AU-06 로그인 · 상태 blocked · 커밋 - · 사유: 완료 기준 넷 중 첫째(200 + TokenResponse)와
  둘째(비밀번호 불일치 401 AU003)는 충족. 셋째(탈퇴 계정 로그인 차단)는 Account 엔티티에
  deleted 조회 조건이 없어 막힘 — AU-03 산출물인데 AccountRepository에 해당 메서드가 없다.
  phase1.md §2.1에 따라 기반 경로를 고칠 수 없으므로 계획 판단 필요
```

## 6. 부분 완료의 처리

완료 기준 일부만 충족한 상태로 멈춰야 할 때가 있다(선행 항목 대기 등).

- 상태는 `done`이 아니라 `blocked`로 둔다
- 충족한 것과 못한 것을 사유에 적는다
- **구현하지 않은 부분을 구현한 것처럼 보이게 만들지 않는다.** 미구현 경로는 명시적으로 예외를 던지거나 기동을 실패시킨다
- 스테이징한 변경은 그대로 둔다. 다음 작업자가 이어받는다

## 7. 통합 검증 단계

여러 서비스에 걸친 검증은 개별 작업 항목이 아니라 통합 단계에서 한다([../plan/integration.md](../plan/integration.md)). 세 서비스가 모두 기동된 상태를 전제하므로 **순차로 진행**하며, 같은 리뷰 사이클을 적용한다.
