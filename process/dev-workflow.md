# 개발 워크플로

작업 항목 하나를 시작해서 끝낼 때까지의 절차다. **모든 작업 항목이 이 절차를 따른다.**

## 1. 전체 흐름

```
 [1] 작업 항목 선택
      |
 [2] 참조 문서 읽기  (항목의 "참조" 필드에 적힌 것만)
      |
 [3] 산출물 구현
      |
 [4] 검증 테스트 작성  (항목의 "검증" 표를 테스트 코드로)
      |
 [5] ./gradlew test  ------실패-----> [5a] 원인 분석 -> 수정 -> [5]로
      |                                    |
     통과                              3회 초과
      |                                    |
 [6] 완료 기준 체크리스트 전 항목 확인   [5b] 중단하고 BLOCKED 보고
      |
 [7] 커밋 & 푸시
      |
 [8] checklist.md 상태를 done으로 갱신  (같은 커밋 또는 직후)
      |
 [9] 다음 작업 항목
```

## 2. 단계별 규칙

### 2.1 작업 항목 선택

1. 담당 저장소의 `docs/checklist.md`를 연다
2. 상태가 `doing`인 항목이 있으면 **그것을 이어서** 한다
3. 없으면 계획 순서상 다음 `todo`를 고른다. **의존 항목이 모두 `done`이어야 한다**
4. 고른 항목의 상태를 `doing`으로 바꾼다

의존 항목이 `done`이 아니면 그 항목을 건너뛰고 다음 후보를 본다. 의존을 무시하고 진행하지 않는다.

### 2.2 참조 문서 읽기

작업 항목에 적힌 **참조 문서와 절 번호만** 읽는다. 문서 전체를 읽지 않는다.

값(엔드포인트, 컬럼명, 에러 코드, 버전)은 반드시 정본에서 가져온다. 기억이나 추측으로 채우지 않는다.

### 2.3 구현

- 산출물 목록에 있는 파일만 만든다. **범위를 넘지 않는다**
- [../conventions.md](../conventions.md)를 따른다
- 문서에 없는 값이 필요하면 임의로 정하지 말고 §4의 BLOCKED로 보고한다

### 2.4 테스트 작성

**구현과 같은 작업 단위에서 작성한다.** 나중에 몰아서 작성하지 않는다.

- 작업 항목의 "검증" 표에 있는 케이스를 **모두** 테스트 코드로 만든다
- 표에 없어도 동작 변경·버그 수정에는 재현 가능한 최소 회귀 테스트를 추가한다
- 커버리지를 채우기 위한 테스트는 만들지 않는다. 서드파티 동작을 재검증하지 않는다

### 2.5 테스트 실행

```bash
./gradlew test
```

실패하면 원인을 분석하고 수정한 뒤 다시 실행한다. **최대 3회까지 재시도한다.**

3회를 초과하면 중단하고 §4의 BLOCKED를 보고한다. 계획서의 가정이 틀렸을 가능성이 있으며, 계속 시도하면 코드를 망가뜨린다.

### 2.6 완료 기준 확인

작업 항목의 "완료 기준" 체크리스트를 **한 줄씩** 확인한다. 전부 충족해야 완료다.

일부만 충족했으면 완료가 아니다. §3에 따라 부분 진행 상태를 기록한다.

### 2.7 커밋

- 작업 항목 하나 = 커밋 하나를 원칙으로 한다
- 커밋 메시지 형식은 [../conventions.md §10](../conventions.md)
- 리팩터링과 기능을 한 커밋에 섞지 않는다

### 2.8 상태 갱신

`docs/checklist.md`의 해당 줄을 `[x]`와 `done`으로 바꾼다. **작업을 끝내고 상태를 갱신하지 않은 채로 다음 항목으로 넘어가지 않는다.**

## 3. 금지 사항

이 절의 항목을 어기면 작업이 완료된 것으로 보지 않는다.

| # | 금지 | 이유 |
| --- | --- | --- |
| 1 | 실패하는 테스트를 `@Disabled`·주석 처리로 넘기기 | 실패를 숨기는 것이다 |
| 2 | 테스트를 통과시키려고 단언(assertion)을 약화하기 | 같음 |
| 3 | 완료 기준 미충족 상태에서 `done`으로 표시 | 다음 작업이 잘못된 전제 위에 쌓인다 |
| 4 | 테스트를 나중에 몰아서 작성 | 검증 없이 쌓인 코드는 원인 추적이 불가능해진다 |
| 5 | 막힌 부분을 mock·더미·하드코딩으로 우회 | 문제를 덮는 것이다. 막히면 BLOCKED로 보고한다 |
| 6 | 문서에 없는 값을 임의로 정해서 진행 | 정본과 어긋난 구현이 된다 |
| 7 | 산출물 목록 밖의 파일을 함께 수정 | 범위 이탈. 다른 작업과 충돌한다 |
| 8 | 의존 항목이 `done`이 아닌데 진행 | 순서가 있는 데는 이유가 있다 |

**5번이 특히 중요하다.** 외부 의존이 없거나 정보가 부족할 때 임시 값으로 통과시키면 나중에 그 코드가 진짜인지 가짜인지 구분할 수 없다. 실패는 명시적으로 드러내야 한다.

## 4. BLOCKED 보고

진행할 수 없으면 아래 형식으로 보고하고 멈춘다.

```
BLOCKED
- item: (작업 항목 ID)
- blocked_by: (무엇이 막고 있는가 — 문서에 없는 값 / 선행 항목 미완 / 테스트 3회 실패 등)
- done_so_far: (완료 기준 중 충족한 것과 충족하지 못한 것)
- required: (진행하려면 무엇이 필요한가)
```

그리고 `checklist.md`의 상태를 `blocked`로 바꾸고 줄 끝에 `· 사유: ...`를 붙인다.

**사유는 다음 작업자가 이어받을 수 있을 만큼 구체적으로 적는다.** 완료 기준을 절 단위로 쪼개서 어디까지 됐는지 적는다.

```
- [ ] M-05 로그인 · 상태 blocked · PR - · 사유: 완료 기준 셋 중 첫째(이메일·비밀번호 검증)와
  둘째(Access/Refresh 발급)는 충족. 셋째(Refresh Token DB upsert)는 refresh_token 테이블이
  M-04 산출물인데 M-04가 done이 아니라 막힘. M-04 완료 후 재개
```

## 5. 부분 완료의 처리

완료 기준 일부만 충족한 상태로 커밋해야 할 때가 있다(선행 항목 대기 등).

- 상태는 `done`이 아니라 `blocked` 또는 `doing`으로 둔다
- 충족한 것과 못한 것을 사유에 적는다
- **구현하지 않은 부분을 구현한 것처럼 보이게 만들지 않는다.** 미구현 경로는 명시적으로 예외를 던지거나 기동을 실패시킨다

## 6. 통합 검증 단계

두 서비스에 걸친 검증은 개별 작업 항목이 아니라 통합 단계에서 한다([../plan/integration.md](../plan/integration.md)). 이 단계는 두 서비스가 모두 기동된 상태를 전제하므로 **순차로 진행**한다.
